# Engines: Pad Generation, G-code, Tuner, Tooling

## Pad Generation Data Flow

**Pad Generation**: User input → `parse_pad_list()` → `can_all_pads_fit()` check → `generate_svg()` or `generate_gcode()` → output files

**Sizing Calculations**: `get_disc_diameter()` in svg_engine.py applies material-specific offsets:
- Felt: pad_size - felt_offset
- Card: pad_size - (felt_offset + card_to_felt_offset)
- Leather: pad_size + 2*(felt_thickness + wrap) with star bonus for small pads
- Exact: pad_size unchanged
- Adhesive ring: the **nesting footprint**, not the cut (ring plus an outside number; see "Adhesive Rings"). The cut is the card disc and comes from `adhesive_ring_geometry`

**Per-Size-Range Settings**: Sizing rules, dart/star settings, engraving settings, and engraving placement each support a Universal/Range mode. In Universal mode, one set of values applies to all pad sizes. In Range mode, users define size ranges with different values. Four helper functions in config.py centralize this lookup — engines should always use these instead of reading raw `settings["dart_*"]` etc:
- `get_dart_settings_for_size(pad_size, settings)` → returns range dict or **None** (no match = no stars)
- `get_sizing_for_size(pad_size, settings)` → returns sizing dict (no match = **universal fallback**)
- `get_engraving_settings_for_size(pad_size, settings)` → returns engraving on/off + font sizes (universal fallback)
- `get_engraving_placement_for_size(pad_size, settings)` → returns placement mode/value per material (universal fallback)

Key difference: dart ranges return None on no match (opt-in), while the other three always return a dict (every pad needs values).

**Engraving font ranges and engraving placement ranges are two separate lists** (`engraving_settings_ranges` vs `engraving_placement_ranges`), each with its own Universal / Per Size Range switch in the Sizing Rules dialog, one section apart. That split is deliberate (the boundaries need not match, and both are in `SIZING_PRESET_KEYS`), but it hides the second one: a user set up font-size ranges, found no placement fields there, and asked for placement to be added to ranges on 2026-09-18 when it already existed a section down. A one-line pointer in the font-size range editor was added and removed again two days later: Matt looked at the dialog and judged the placement section obvious as it stands. Don't merge the two lists to "fix" this — it's a preset-schema change that breaks every saved preset.

**Darted leather engraving**: Leather pads with darts use the `darted_leather` key in `engraving_location` for placement (default 2.5mm from outside), separate from regular `leather` placement. The dart config's `engraving_on` flag still controls whether darted leather is engraved at all.

## Nesting

**Nesting Algorithm**: `_nest_discs()` implements greedy circle-packing, shared by both `can_all_pads_fit()` and `generate_svg()`. Supports both rectangular sheets and custom polygon shapes. `nest_pads()` is the public API for the preview window. Edge bias controls scan direction: cardinal (N/S/E/W) scan linearly from the edge, corners (NW/NE/SW/SE) use distance-from-corner scoring with smallest-first sort order for efficient corner packing. The bias itself comes from `nest_edge_bias(material, settings)`, the only place it is read: the Pad Maker's setting for pads, a fixed corner for Tooling's die inserts (see Tooling Tab).

**Vectorized scan paths (v2.40+)**: the radial-bias rectangle scan (`_scan_radial_numpy`) and both polygon scans (`_find_best_polygon_large_numpy`, `_find_best_polygon_small_numpy`) build a numpy candidate grid, compute distances/scores in one bulk op, mask occupied cells via per-pad bounding-box updates, then `argmin` to pick the closest valid cell. ~100× faster than the Python loop on real-world inputs; bit-identical placements (`argmin`'s first-index-of-min matches the Python reference's strict-less-than y-then-x tie-break). A Python reference (`_scan_radial_python`, `_find_best_polygon_*_python`) is preserved verbatim as the parity target and as the runtime fallback when numpy is unavailable (a source checkout without numpy — every shipped build has had numpy since 2026-10-06; try-import at the top of `svg_engine.py` sets `_HAS_NUMPY`). `tools/test_nesting_parity.py` (rectangle) and `tools/test_polygon_parity.py` (polygon) assert exact-match placements across all 9 edge biases, every polygon shape, and max-quantity fills.

**The linear scan is vectorized too (2026-09-20).** The cardinal biases (N/S/E/W) and "off" — the state the center button toggles to, so effectively *no bias* — use a row-by-row first-free-cell scan, not the radial one, and it was the last scan still running the pure-Python loop: O(cells × placed) per disc. Matt hit it with 120 felt pads on a sheet typed as 15.5 × 15.5 in: 94 s per nest on his ThinkPad, and the generate flow nested twice, so Windows logged `Application Hang` and he force-closed the app three times. `app.log` showed nothing because nothing raised — when a "crash" leaves no traceback, check `Get-WinEvent -LogName Application` for `Application Hang` / `AppHangB1` events before assuming the exception hook missed it. `_scan_linear_numpy` builds the occupancy mask with the shared `_build_occupancy_grid`, flips the axes into the reference's visit order (reversed scans are anchored at the far edge, so their grid only lines up with the forward grid when the free span is a whole number of mm — `_linear_axis_cells` reproduces the exact cells the loop visits), and takes the first free cell with `argmax`. `_scan_linear_python` is the verbatim closure, kept as the parity reference and numpy-less fallback. Same nest now takes 0.1 s. Guards live in `test_nesting_parity`: direct parity across all five linear biases (including obstacles on the first/last cell, a blocked row, and a fully covered sheet), end-to-end parity including the fail-to-place case, and a `< 5 s` regression bound on Matt's exact batch.

**Nesting Preview**: `NestingPreviewWindow` in ui_dialogs.py shows the nested layout before file generation. Works in standard mode (one material at a time) and scrap mode. The generate flow nests first via `nest_with_zones()`, shows the preview, then writes files via `generate_svg_from_placed()` / `generate_gcode_from_placed()` — no double-nesting. The fit check is the `fixed_placed == fixed_total` pair that same call returns; the three flows (SVG, G-code, Frame & Cut) used to call `can_all_pads_fit()` afterwards, which is a second full nest, and that doubled every nesting time until 2026-09-20. `can_all_pads_fit()` still exists for tests and one-shot callers — don't reintroduce it next to a `nest_with_zones()` call. Frame & Cut (machine integration, v2.62) reuses the same window before the head moves — it passes `proceed_label="Continue →"` (it streams to the laser rather than writing files, so "Save Files" would mislead) and a cancel there consumes nothing.

## SVG & G-code Rendering

**Shared Rendering Helpers**: SVG rendering is centralized in `_render_svg_discs()` and `_create_svg_drawing()` in svg_engine.py. Both `generate_svg()` and `generate_svg_from_placed()` call these. Similarly, `generate_gcode()` delegates to `generate_gcode_from_placed()` after nesting, so all G-code disc rendering logic lives in one place.

**Size-label placement modes** (`engraving_location[material] = {mode, value}`, per material, with `darted_leather` as its own key; Sizing Rules dialog radios **out / mid / int**, outer edge to centre, reordered from out / int / mid on 2026-10-28): `from_outside` puts the label's centre `value` mm inside the cut edge, or, on a darted leather disc with the **"Darted leather: measure 'out' from the dart valley"** box ticked (`settings["darted_out_from_valley"]`, in `SIZING_PRESET_KEYS`, off by default), `value` mm between the **dart valley** (the star's inner radius, `svg_engine.dart_valley_radius`, now the one place both engines get it from) and the **top of the number**, i.e. the label's centre sits `value + font_size / 2` inside the valley and 0 means touching. Matt, 2026-10-26: the valley deepens with pad size, so measured from the cut edge no single value kept the label just inside it and that placement had been a running nuisance; it is a checkbox rather than a silent redefinition so nobody's existing presets move, and his own preset (`presets/Matt mode.json`, 0.5 in every range) turns it on. It first measured to the label's middle like every other mode, so 0 put the number half into the darts; Matt asked for the near edge the same day, for this option only, because it was unreleased (changing `from_outside` from the cut edge or `from_inside` would move every saved preset's labels by half a font height). The half-height is the nominal text box (`font_size / 2`), so the burned digits sit a hair further in: 0.05 × font for the stroke font, ~0.01 for filled, more for LightBurn's own font in the SVG. **A dart tip always sits over the label**: `svg_engine.dart_wave_raw` peaks at `DART_TIP_ANGLE` (12 o'clock, Y-down) in the SVG path and the pad preview, and at its negation in the Y-up G-code, so the number gets a tip's room above it. Before, the wave peaked at 3 o'clock, which put a notch over the label on every size whose dart count is 2 mod 4 (10 and 12 under Matt mode); the cut is otherwise the same shape, turned half a dart. `test_engine_parity` pins the tip on both engines across sizes of both counts, plus the G-code star as the SVG star's mirror image; `test_pad_preview` pins the preview; `from_inside` puts it `value` mm outside the hole edge (outside the centre when the pad gets no hole); `centered` — labelled **mid** since 2026-10-26, previously "ctr" — puts it halfway between the hole edge and the cut edge, `(r + hole_r) / 2` from the centre, or halfway between the centre and the cut edge when the pad gets no hole (`hole_r = 0`); its mm value is ignored, and the dialog greys that row's entry out while mid is selected (`grey_value_when_mid`, a trace on the mode var, so preset loads and range switches follow; Matt, 2026-10-28). Mid measures from the cut edge on darted pads too (the dart tips), whether or not the valley box is ticked: that box only changes "out". The settings key stays `centered` so saved presets keep working. Matt asked for exactly that midpoint on 2026-10-26, not knowing "ctr" was nearly it: until then a no-hole pad used a phantom 1.75 mm hole radius, and the G-code engine placed int/mid labels from the *preset* hole size even on pads below `min_hole_size`, so small no-hole pads got different label positions in SVG and G-code. Both engines now resolve the disc's hole the same way (`should_have_center_hole` in SVG, `disc_hole_dia` in `_collect_disc_strokes`) before placing the label; `tools/test_engine_parity.py` pins the exact offsets for hole present / hole option None / pad below the hole size.

**SVG Output Modes (`compatibility_mode`)**: Options > Settings > Export Settings has an "Enable Inkscape/Compatibility Mode (unitless SVG)" toggle (setting key: `compatibility_mode`, default False). Both modes emit the same SVG root (`width="Xmm" height="Ymm" viewBox="0 0 X Y"`), so physical dimensions are identical either way — the difference is inside the document. Default mode declares `profile='tiny'` and writes every child attribute with explicit `mm` suffixes (e.g. `r="12.5mm"`, `stroke_width="0.1mm"`); compatibility mode omits the profile and writes bare numbers (`r=12.5`, `stroke_width=0.1`) that inherit the viewBox's 1-unit-per-mm mapping. The flag gates a branch per unit-suffixed element type in `_render_svg_discs()` (outline, hole, engraving text — the dart path is always unitless, which is fine) and `_render_svg_dies()` (plus die-specific elements). When adding new SVG element types to either renderer, remember to branch on `compatibility_mode` the same way or emit only the unitless form. Historical context: the flag exists for older tool chains that rejected per-attribute unit suffixes or SVG Tiny 1.2; modern Inkscape/LightBurn/Illustrator handle both forms fine.

**Coordinate Systems**: SVG uses Y=0 at top (Y increases downward), while G-code uses Y=0 at bottom (Y increases upward). The `gcode_engine.py` functions flip Y coordinates (`sheet_height_mm - cy`) to ensure G-code output matches the SVG preview.

## G-code Engine Details

`gcode_engine.py` contains two font systems: `STROKE_FONT` (single-stroke outlines for "line" engraving mode) and `FILLED_FONT` (Roboto glyph outlines for "filled" raster mode). Both fonts contain digits, period, hyphen, space, and 12 letters (D E S I G N B Y P H L O) — the letters cover the Phil Noy credit text engraved on tooling parts. Stroke letters are hand-designed single-stroke approximations matching the digit style; filled letters are extracted from `tools/Roboto-Regular.ttf` via `tools/extract_font_outlines.py`. To regenerate the filled letters, edit `CHARS` in the extractor and re-run; paste the output into the `FILLED_FONT` and `FILLED_CHAR_WIDTHS` blocks in gcode_engine.py.

Filled engraving uses scan-line fill with even-odd rule to convert font outlines into horizontal raster lines, with optional overscan (extending lines beyond character edges so the laser reaches full speed). `generate_gcode_from_placed()` is the main entry point — it supports two cut grouping modes ("layer": all engravings → all holes → all cuts; "pad": complete each disc before moving to the next) and per-layer air assist control (M8 on / M9 off). The internal `_collect_disc_strokes()` helper extracts per-disc stroke data for both modes.

**Arc text helpers**: `get_text_strokes_arc()` and `get_filled_text_strokes_arc()` lay text out along an arc with rigid per-character rotation (each character is a rotation+translation, not a polar warp). The filled variant runs scan-line fill IN THE CHARACTER'S LOCAL FRAME and then transforms each scan segment to world coordinates via the basis vectors, so curved text fills solid like flat text instead of using horizontal scan lines that would misalign on rotated glyphs. Both helpers take `(text, font_size_mm, cx, cy, radius, center_angle_rad, side='top'|'bottom')` where 'top' sweeps CW with character tops radially outward and 'bottom' sweeps CCW with character tops radially inward (so text reads upright when viewed from outside the circle). The svg_engine die/holder renderers call the same helpers and emit polylines so the SVG preview matches the gcode output exactly.

## Polygon Shape Tool

Users can draw custom polygon shapes for irregular leather skins. Grid size: default 17×17 inches (1" squares) or 43×43 cm (1cm squares); auto-grows in `PolygonDrawWindow.__init__` to at least `ceil(max(laser_bed_x_max, laser_bed_y_max) / mm_per_unit)` so a user with a 500mm bed gets a 20-inch grid even if their stored `polygon_draw_grid_size_in` setting is smaller. The polygon nesting algorithm (`_nest_discs_polygon()`) uses ray-casting for point-in-polygon checks and distance-to-edge calculations for circle fitting. The rectangle algorithm remains the fast path when no custom shape is defined.

**Vertex placement**: free-floating (`_canvas_to_grid` returns floats), not snapped to integer grid intersections — 1-inch granularity is too coarse for accurate scrap tracing. Hand-drawn AND camera-captured polygons share this float convention; downstream nesting + machine-coord round-trip handle non-integer points natively.

**Live camera overlay** (v2.5+): `PolygonDrawWindow._render_overlay` warps the live camera feed (via `cv2.warpPerspective`) onto the polygon canvas at 1:1 grid scale, anchored at machine `(0, 0)` by default (canvas BL = bed origin). Users can trace their scrap by eye on top of the camera image, or click "Get from camera" for auto-detection via `CameraCaptureDialog`.

## Scrap Mode

Allows users to place pads across multiple irregular scrap pieces instead of requiring one large sheet. Key components:
- Session state in `self.scrap_session` tracks the scrap count, locked material, and (since 2026-09-20) a per-size `done` tally of pads already cut. `original_pads` / `remaining_pads` are refreshed from the box at every Generate, not frozen at session start (see **Live pad list** below)
- `try_nest_partial(pads, ...)` and `compute_remaining_pads()` in svg_engine.py handle partial placement
- `generate_svg_from_placed()` / `generate_gcode_from_placed()` generate output from pre-computed placements
- Progress popup window (`scrap_remaining_window`) shows three columns: Remaining (not yet placed), On this scrap (nested, waiting for the cut), Done (cut). See **Pending scrap** below
- Materials are locked (disabled) during active session to prevent switching
- Files named with `_scrap1`, `_scrap2` suffixes
- After each scrap with a polygon loaded, a dialog asks whether to unload, keep the shape, OR re-capture from camera (when calibrated)

**Live pad list (2026-09-20)**: the pad list box stays editable during a session and is re-read on every Generate / Frame & Cut. `_scrap_pads_for_this_scrap(pads)` merges duplicate lines, stores the merged list as `original_pads`, and returns `remaining_pads` = the list *now* minus the session's `done` tally per size, so a size added, raised, lowered or removed mid-session simply takes effect on the next scrap, and lowering below what's already cut clamps to zero. `_scrap_record_result(remaining)` credits a finished scrap to `done` as the drop from the pre-scrap list; all three commit sites (SVG, G-code, `_frame_cut_scrap_advance`) route through it, so it must run before anything overwrites `remaining_pads`. The Done column of the remaining-pads window reads `done` directly rather than original minus remaining, so it stays honest when a quantity is lowered below the cut count. Before this, the session copied the list at its start and ignored the box until the session ended; a user who added sizes to fill a half-empty last scrap got a scrap without them and no message. Deliberately *not* changed: a `max` line still fills the first scrap only (pre-existing, pinned by the test), and the session's `hole_dia` is still fixed at session start. Tests: `tools/test_scrap_live_list.py`.

**Pending scrap (2026-10-26)**: until this date the window knew only Remaining and Done, and both moved at one point, the commit after a completed cut or a written file. From the preview opening until the laser stopped it still read "0 / 60 pads complete" with every pad in Remaining, which reads as pads being dropped: Matt hit it in the shop on a leather scrap whose nest placed the five 52s and the small sizes and skipped 5x50, 10x39 and 10x36 (correctly: after the 65 mm discs took the wide parts, the arms were too narrow for a 49-63 mm disc once the 5 mm camera inset and 1 mm spacing came off). The session now keeps `pending` = `{size: count}` of what the current scrap's nest placed, set by `_scrap_set_pending(placed)` at the end of `_scrap_begin_partial`. The window subtracts it from Remaining, lists it in the middle column and heads itself "{n} on scrap #{k}, {done} / {total} cut"; the main-pane status says "{left} left, {n} on this scrap". `_scrap_record_result` (the one commit point) clears it as it credits `done`. `_scrap_abandon_pending` puts it back and is called from a `finally` in `_generate_gcode_scrap_mode`, `_generate_svg_scrap_mode` and `on_frame_and_cut`, so every way out that is not a commit (preview Adjust, folder prompt cancelled, jog or framing dialog cancelled, stopped or errored cut, exception) restores Remaining without each path having to remember to. Tests: `tools/test_scrap_pending.py` (bookkeeping with the real window, and the Generate button with the preview stubbed to Adjust then Save).

**No large-batch optimizer (removed 2026-09-20).** v2.5 shipped an opt-in "large-batch optimization" for scrap mode: with ≥ 75 pads remaining, a prompt offered a multistart nest (largest-first, smallest-first, three seeded shuffles) and kept the best. It first kept the result with the most *pads*, which systematically picked smallest-first and left the big discs for later — Matt measured 63% of a leather scrap used against 70% from the plain nest. Re-ranked by material used, largest-first was the winner on every real scrap tried, and 22 orderings moved usage by 0 / 0.3 / 1.3% on Matt's actual 120-pad list. The reason is geometric: the interstice between three touching ~60 mm leather discs is under 10 mm, and the smallest pad on that list is a 29 mm disc, so no ordering can use those gaps. Put a dozen 10.0 mm pads (18 mm leather discs) in the same list and plain largest-first drops all twelve into the gaps (70.5% → 73.6% / 76.0%), still with no reordering. So the lever is the sizes in the list, not the order, and the feature was removed rather than kept as a code path with a prompt that couldn't earn its keep. The ordering-override parameter on both nesters went with it. Don't reintroduce an ordering search without a measured win on a real list.

## Leather Locator Marks

Sizing Rules > **Lesser-used settings** > Leather Locator Marks (2026-10-06, a feature request from another tech; Matt doesn't use it himself). Engraved guides on leather pads showing where the felt sits, so a pad with **no center hole** can be centered by eye before pressing. Opt-in, pad-size range (inclusive, default 7.0–16.0 = the no-hole sizes under default sizing), leather only. Styles: four cardinal lines ending at the felt edge (default — equal gaps all round reads as centered, where a circle exactly at the felt edge just disappears under the felt), a circle the size of the felt disc, or both; optional dashes.

**The marks are on the flesh side, so the leather is cut flesh-side up.** The felt sits on the flesh side and the laser marks the face-up side; a mark on the grain side is either on the sealing surface or on the visible rim. With the leather flipped, the size number lands on the flesh side too, in the wrap zone, glued against the card and hidden. Whether a laser line reads well on fuzzy flesh side is for the requesting users to find out — it's in the tooltip and the user guide, not enforced.

**One geometry, three renderers.** `svg_engine.locator_mark_geometry(pad_size, outer_r, settings)` returns primitives relative to the disc center (`circles` radii + line `segments`), or None; `locator_circle_points` samples a circle (solid or dashed arcs). `_render_svg_discs`, `gcode_engine._collect_disc_strokes` and `PadPreviewWindow._draw_locator` all call them and only translate. Everything is symmetric about both axes, so the SVG↔G-code Y-flip is a no-op — still pinned by `test_svg_and_gcode_draw_the_same_marks`. Felt edge = `get_disc_diameter(pad, 'felt') / 2`, the same number as the felt disc that gets cut. Lines run from the felt edge outward and stop `LOCATOR_EDGE_MARGIN_MM` (1.0) inside the cut, or inside the dart valleys on a darted pad, so nothing runs off material; a line shorter than `LOCATOR_MIN_LINE_MM` (0.8) is dropped rather than left as a speck. Dashes are laid from the felt edge outward so the inner end — the one that locates — is always a full dash on `felt_r`. No kerf: they're engraved.

**Layers and power — Matt's call, 2026-10-06.** SVG: own layer color `leather_locator` (LightBurn 06 Cyan, in Layer Colors), so LightBurn users set their own power. G-code: own layer comment `C06` but the **leather engraving speed/power/passes/air** — there is no separate locator power in G-code yet. The marks go down right after the engraving layer and before any hole or cut, in both grouping modes, with no overscan, and the file carries a comment saying where the power came from. Matt wants separate power "eventually", only if users really ask — it means four new keys in `gcode_settings.leather` and `GCODE_PRESET_KEYS`, hence a backfill for every saved leather preset. Until then the UI note and user guide recommend SVG output for this feature.

**Lesser-used settings** is a collapsible at the bottom of the Sizing Rules dialog holding, in order, Labeled Zones, the locator marks, Adhesive Rings (beta, 2026-11-05) and Export Settings (zones and export moved there 2026-10-06, Matt's call: both are opt-in features most users never open). Collapsed by default; opens itself on dialog open when anything inside is non-default, so an active setting is never out of sight. Put future rarely-touched settings there rather than growing the main dialog.

**Preset schema**: five keys (`locator_marks_enabled/min_size/max_size/style/dashed`) in `SIZING_PRESET_KEYS`, backfilled by `normalize_sizing_preset` like the zone keys. Universal only — no per-range variant.

Tests: `tools/test_locator_marks.py` (16) — off/absent is byte-identical output, leather-only and inclusive range, line endpoints on plain and darted pads, the too-short drop, styles and dash anchoring, SVG↔G-code point parity, compatibility-mode unitless marks, G-code layer settings and ordering in both grouping modes, preset capture/backfill, layer color validity, and three GUI cases (self-skip without a display): collapsible default/auto-open and form round trip, Layer Colors row, pad preview draws the marks.

## Adhesive Rings (beta)

Sizing Rules > **Lesser-used settings** > **Adhesive Rings (beta)** (Matt's spec, 2026-11-05). A tech who wraps pads in thin silicone sheet in place of leather has to stick the wrap to the back of the card, and the clean way is a ring of double-sided tape per pad. So the Pad Maker gains an opt-in fifth material, `adhesive_ring` ("Adhesive rings"): a plain ring, no engraving settings, no center-hole option, no darts, cut from tape. Off by default, and while off the material is not on the tab at all (see CLAUDE.md "Adhesive Rings").

**One geometry, four consumers.** `svg_engine.adhesive_ring_geometry(pad_size, settings)` is the only place a ring is computed; the SVG renderer (`_render_svg_adhesive_rings`), the G-code engine (`_write_adhesive_ring_gcode`), the pad preview and the nesting preview all draw from it, and the nester reads its `footprint_r` through `get_disc_diameter`.
- *Outer (cut) diameter* = the card disc, `get_disc_diameter(pad, 'card', settings)`.
- *Ring width* = the back wrap the leather disc gets for that size, from the same call the leather disc uses (`leather_wrap_for_size`: base wrap, plus the dart `wrap_bonus` when the size has darts, times the wrap multiplier), plus `adhesive_ring_trim_mm`.
- *Inner diameter* = outer - 2 x width. **Pads of `ADHESIVE_RING_SOLID_MAX_PAD_MM` (9.5) and under are solid discs with no inner cut**, whatever the sizing rules make of the hole (Matt, 2026-11-05: "9.5 and under solid is good"; under his own preset those sizes would otherwise have had 3.3 to 5.7 mm holes). Above that size a hole under `ADHESIVE_RING_MIN_HOLE_MM` (2.0) is dropped too, a floor for unusual sizing rules. Both are constants with no UI. A trim can't thin the ring below `ADHESIVE_RING_MIN_WIDTH_MM` (0.5).

**Why the trim exists.** The wrap figure is nominal, tuned on real pads, not a measured overlap on the card back: the card's thickness and its inset from the pad edge come out of it, and stretch puts some back. Silicone sheet is not leather either. So the computed wrap is a starting point and the user trims it (mm, either sign, default 0). **The dialog calls this number "Wrap clearance"**; the stored key stays `adhesive_ring_trim_mm` with the same meaning and sign (mm of ring width per side), the same precedent as the `dart_` keys behind "Darts". It is how far the ring's inner edge reaches past the edge of the wrap. Matt, 2026-11-05: "I think of negative clearance as being inside and hidden, positive clearance as being extra ring material", and "I want negative numbers to be reducing the ring size (increasing ID) and positive numbers to be increasing ring size (shrinking ID)". The control is a spinbox, 0.1 steps, -5.0 to 5.0, typing allowed; a typed value outside the range is held to it at Apply. The names tried and dropped on the way were "Ring width trim", "Inner edge clearance" and "Ring inner diameter adjustment" (that last one in diameter terms); no rename, migration or conversion of the key was ever shipped. Tk reformats and clamps a variable when a spinbox is created on it (a stored 0.25 becomes 0.2 just by opening the dialog), so the dialog puts the stored value back after building the control. Don't "fix" the ring by changing the wrap formula; that moves every leather disc.

**The number.** Every ring carries its pad size (`zone_label_text`, the same text the other labels use) as **stroke-font** polylines, never filled, whatever any `engraving_mode` says: `gcode_engine.get_text_strokes` at height 1, re-centred on the strokes' own box (the font cell has side bearings), then scaled. One constant decides where it goes, `ADHESIVE_RING_LEGIBLE_FONT_MM` (2.5):
- *Inside*: if the hole takes the number at 2.5 mm or more with `ADHESIVE_RING_HOLE_CLEARANCE_MM` (1.0) to the inner cut all round, it is centred in the hole, on the waste plug, at the largest height that fits, capped at `ADHESIVE_RING_MAX_FONT_MM` (5.0).
- *Outside*: otherwise (small rings, and every solid disc) it goes at 2.5 mm on the scrap, centred under the ring, its top `ADHESIVE_RING_OUTSIDE_GAP_MM` (1.0) below the outer cut.
A wide label needs a bigger hole than a narrow one, so "12.5" can sit outside while "12" and "13" sit inside. Measured 2026-11-05 for 7.0 to 60 mm in half sizes, with the 9.5 rule in place: 7.0 to 9.5 are solid discs under any sizing rules, so their number is always outside; beyond that the number is outside up to 11.5 and on 12.5, 13.5 and 14.5 under the program defaults, and on 10.5, 11.5 and 12.5 under `presets/Matt mode.json`. Matt agreed the 2.5 mm legible size and the outside list on 2026-11-05 (the list he saw had 9.0 inside; his 9.5 rule, given in the same reply, is what moves it out).

The strokes are stored Y-down relative to the ring centre ("under" is +y) and `adhesive_ring_number_strokes(geom, cx, cy, y_up=)` places them: as they are for SVG and canvases, mirrored in y for G-code, where `cy` is the already-flipped centre. That is what keeps the number under the ring, upright and unmirrored in both outputs; `test_engine_parity` and `test_adhesive_ring` pin it with the "7" glyph.

**Why the number is on the cut layer.** The material has no engraving settings (Matt: a plain ring), so there is nothing to engrave it with. In the SVG the number shares the ring's one layer colour (`layer_colors['adhesive_ring_cut']`, LightBurn 07 Magenta) and is emitted as polylines rather than `<text>`, so LightBurn gets single lines. In the G-code it is traced at the ring's cut speed, power, passes and air (layer comment `C07`, with a line in the file saying so). Order per ring is number, inner circle, outer circle, so an inside number is traced while its plug is still attached: with "by layer" grouping that is all numbers, all inner cuts, all outer cuts; with "by pad" the three steps ring by ring. Kerf goes inward on the inner cut and outward on the outer; none on the number. Both cuts are linearized with `ADHESIVE_RING_CUT_SEGMENTS` (72): the inner cut is nearly as big as the outer, not a 3 mm center hole, and at the center-hole figure (36) a 51 mm pad's inner cut had 3.7 mm flats, 0.08 mm off a true circle (found by the independent test pass, 2026-11-05). The SVG is true circles either way. The number gets the full cut passes, and all of its passes come first, before any cut, the way engraving does (Matt, 2026-11-05).

**Footprint versus cut radius (the trap).** An outside number needs sheet area no neighbour may take and that is on material. That is done by handing the nester a larger disc, never by adding obstacles and never by touching the parity-pinned scan functions: `get_disc_diameter(pad, 'adhesive_ring', settings)` returns the **nesting footprint**, the circle centred on the ring that encloses the ring and its number's box (equal to the cut when the number is inside). The nester's usual 1 mm spacing then keeps every number clear of every other ring and inside the sheet or polygon. The consequence: **for this material the radius stored in `placed` is the footprint, not the cut**. Every renderer must take the cut radius from `adhesive_ring_geometry`; one that trusts `placed` cuts a circle up to twice the size (12.5 nests as 17.1 mm and cuts at 9.75 under the defaults). The nesting preview is passed `settings=` for the same reason and draws the real ring and number; without settings it falls back to footprint circles. The footprint is a full circle round a number that only sits on one side, so small rings cost more tape than their size suggests; rings nest as solid discs (no ring-inside-ring nesting in this version).

**What stands down.** Labeled Zones (`nest_with_zones` nests rings plainly; a zone's border and label are an engraving layer this material doesn't have, and `_prepare_generation` skips the zones/`max` refusal for a rings-only job), the label placement and auto-fit code, the locator marks, the center hole, and `check_for_oversized_engravings`.

**Settings.** `adhesive_ring_enabled` and `adhesive_ring_trim_mm` are in `DEFAULT_SETTINGS` and `SIZING_PRESET_KEYS` (backfilled by `normalize_sizing_preset`, so older presets still name themselves). `gcode_settings['adhesive_ring']` is cut-only (`config.GCODE_CUT_ONLY_MATERIALS` / `GCODE_CUT_ONLY_KEYS`): cut speed, power, passes, kerf, cut air. `GcodeSettingsWindow` builds one cut row and the kerf for it and branches on the same tuple when capturing, applying, saving and resetting. **The default laser values are a starting point, not tested values** (1500 mm/min, 45 %, 1 pass, air on, kerf 0.2 = the card default; Matt, 2026-11-05). Nobody has cut this with the app and no published figure fits, so they are a straight scale from the one diode data point found (a 20 W diode cutting 1.5-3 mm silicone sheet at 60-75 %, 200-300 mm/min) down to a 0.5 mm (0.020 in) sheet on a 40 W diode: about 0.72 J per mm of cut, 18 W at 25 mm/s. No margin on energy, deliberately (Matt: "we don't want margin on energy, that could roast it"): a cut that doesn't go through can be repeated, a roasted part can't. An earlier 1200 mm/min at 70 % proposal carried a threefold margin and was rejected for that reason. The G-code section's note and the user guide call the defaults a starting point and send the user to Tooling > Speed & Power Test; no text may say the value was tested. The existing Default-preset backfill in `main.py` gives current users an `adhesive_ring` Default. `laser_framing_power_by_material['adhesive_ring']` defaults to 10; the Framing Power dialog shows its row only while the feature is on and merges into the stored map so a hidden row keeps its value.

**Machine control.** Nothing special was needed: `on_frame_and_cut` takes any single checked material other than `exact_size`, `_get_material_dimensions` gives rings the sheet or the custom polygon (the paper-size option is card's alone), and the ring writer runs after the shared Y flip, so `flip_height_mm` (camera-captured polygons) applies. ## Engraving Auto-Fit

When engraved text (pad size number) would impinge on the disc edge, both engines prefer shifting the text toward the disc center over shrinking it. Only scales down as a last resort when text can't fit even when centered. SVG engine uses bounding-box corner checks; G-code engine uses actual stroke-point measurements. Both maintain a 0.5mm clearance margin. The 80% radius check (`font_size >= r * 0.8`) disables engraving entirely before auto-fit runs.

## Strobe Tuner

12-wheel chromatic stroboscopic tuner. Architecture:
- `tuner_engine.py`: Pure audio/math — FFT-based pitch detection, per-pitch-class phase tracking, per-ring (octave) magnitude extraction. `TunerEngine` manages the sounddevice input stream; `TunerResult` holds magnitudes, phase offsets, ring magnitudes, and cents errors for all 12 pitch classes. `ReferencePlayer` outputs reference tones. Magnitude normalization is gated: `max_mag` must exceed `threshold * 1.5` before normalizing to 0-1, otherwise all magnitudes are zeroed. This prevents sensitive mics from showing wheel activity on room noise.
- **Peak frequency comes from the Hann closed form, not a parabola (2026-10-02).** `audio_utils.hann_peak_freq` reads a peak's frequency from the ratio of its larger neighbour to the peak bin, `d = (2a − 1)/(a + 1)`, which is exact for a Hann main lobe. The old parabola through three *linear* magnitudes is the wrong shape for Hann and lands up to ~0.05 bin off — and a bin is 10.77 Hz here, ~160 c at 110 Hz — so an exactly in-tune A2 read 7.8 c flat (E2 11.8 c) and the strobe turned on a note that was dead on. Both call sites (per-ring `ring_freq`, best-octave `cents_errors`/`phase_offsets`) use it; magnitudes, threshold and drift arithmetic are untouched, and the GPU renderer only draws the phases Python hands it, so nothing in `tuner_renderer/` changes. The estimator first climbs to the lobe's top (≤ 2 bins, the main-lobe half-width): the 3-bin window round the reference bin misses the top when a high note is well off pitch (B5 26 c flat peaks at bin 90; the window is 91–93), and without the climb that read 2.6 c wrong. A 4× zero-padded FFT with a log-parabola is equally accurate (measured, same worst case to 0.0001 bin) but costs a second, bigger FFT every frame — 0.5→0.8 ms/frame on the tuner and a 4-minute WAV import 4.0→16.1 s — so it was rejected. Gated by the "Pitch reading accuracy" block in `test_tuner_engine` (A2–A5 at ±20 c within 0.15 c; an in-tune note's wheel and ring turn less than 0.15 c worth per 0.1 s; the B5 off-window case). **JustATuner carries the same tuner code** and has the same bug.
- `tuner_tab.py`: All tkinter UI — `StrobeWheel` class renders one disc (annular sector polygons with wedge mask), `TunerTabMixin` builds the tab with control panel: three labeled slider groups (DISP: SENS/BRIGHT/FPS | PITCH: A=/KEY | BIAS: NOTE per-wheel/OCT. per-ring), flat/pilot/sharp indicator, vintage backlit VU meter. The VU needle has damped movement (lerp toward target each frame). Sensitivity gain: the VU path uses a quadratic curve (`sens**2`) so the low end of the slider has fine control; the wheel-brightness path uses a linear curve — they intentionally share the slider but respond differently. Theme walker is bypassed via `_skip_theme` and `_dark_canvas` flags on all dark widgets.
- The tuner auto-starts/stops when switching tabs (`_tuner_start`/`_tuner_stop` called from `on_tab_changed` in main.py).
- numpy and sounddevice are imported separately (2026-10-06); `AUDIO_AVAILABLE` means both are present, and the analysis math works wherever numpy is — the Intel Mac build has numpy but no sounddevice. One combined `try` used to set `np = None` whenever sounddevice was missing.
- `TunerEngine.synthetic_hz` is a test/CI hook, never set in normal use: `start()` opens no stream and `analyze()` feeds a generated tone (`audio_utils.synthetic_tone`) into the ring buffer, so the whole tab runs on a machine with no microphone (`test_tuner_canvas`, the `--tour` screenshots).
- `_tuner_error_state` keeps the "Audio error" / stream-error message across canvas rebuilds: `_tuner_build_wheels_canvas` starts with `delete("all")`, which used to wipe the message on the next resize, so a user with no microphone saw dark wheels and no explanation (Mac tour, 2026-10-06).
- **macOS is canvas-only**: `_HAS_GPU_RENDERER` is forced False on darwin at the top of `tuner_tab.py` — Tk Aqua's `winfo_id()` returns a `MacDrawable` pointer, not an NSView, and handing it to wgpu segfaults natively in `objc_msgSend` (no Python fallback possible). The same gate lives in `build.py` (no `--hidden-import` on darwin) and CI (no Rust/maturin on macOS runners). The "install tuner_render" CPU-mode hint is suppressed on macOS. Full mechanism in CLAUDE.md "GPU Tuner Renderer".
- Transposition support: wheel labels and VU readout both apply the shift from TRANSPOSITION_SHIFTS, with octave correction when the shift wraps past C.
- **GPU/Canvas constant alignment**: these constants exist on both sides of the Python/Rust boundary and must stay in sync: `DIM_MULTIPLIER` (`tuner_tab.py` ↔ `tuner_renderer/src/shader.wgsl`), `BRIGHTNESS_GAMMA` (`tuner_tab.py` ↔ `tuner_renderer/src/renderer.rs`, applied in host code, not the shader), `MAGNITUDE_THRESHOLD` (`tuner_tab.py` ↔ `renderer.rs`), `CENTER_GAP_FRACTION`/`CENTER_GAP` (`tuner_tab.py` ↔ `shader.wgsl`), and `RING_SEGMENTS` (`tuner_tab.py` ↔ the `ring_segments()` switch in `shader.wgsl`). If you change any of them, update both sides. Known divergence: `RING_GAP_FRACTION` (Python, 0.05 off the ring's outer edge) vs `RING_GAP` (shader, 0.015 off each side) — the two renderers draw slightly different ring gaps; align these if anyone complains about the look differing between GPU and CPU mode.
- `ReferencePlayer` in tuner_engine.py can output reference tones, but no UI control currently calls it (the play button was removed with the "Experimental" section) — it's exercised only by `tools/test_tuner_engine.py`.

## Audio Stream Health

Both `tuner_engine.py` and `toner_engine.py` import `AudioRingBuffer` from `audio_utils.py` for stream health monitoring. The ring buffer tracks a write counter; if the analysis loop detects no new audio data for ~1 second, the engine automatically restarts the sounddevice stream. This recovers from silent callback death on Windows.

## Tooling Tab

Accordion-style UI with die insert and die holder SVG/G-code generation. Small dies ≤39.5mm (50mm OD), large ≥40mm (70mm OD). Die holders 85mm OD; user picks 5-layer (solid + magnet + 2× pin + ring) or 6-layer (solid + magnet + 3× pin + ring), with magnet hole 6.5mm, pin holes 3.5mm. Variant is Small / Large / Both, where Both = two complete independent holders (one of each size) nested onto the same sheet — the layers are cemented together permanently, so there's no convertible-holder concept. User defines sheet size (W × H + in/mm) like Die Inserts; engine raises `ValueError` if pieces don't fit. Helpers `_holder_pieces_for(variant, layer_count)`, `_pack_holder_grid(...)`, and `_min_holder_sheet(...)` live in `svg_engine.py` and are imported by `gcode_engine.py` so SVG and G-code stay aligned. Canvas widgets need explicit handling in the resonance theme walker.

**Section buttons.** Seven buttons, three to a row, each 22 characters wide, unless a label is longer in the current language: then that one button takes the width its own label asks for (`create_tooling_tab` reads the button's natural width before fixing it at 22). At a fixed 22, "Geschwindigkeits- und Leistungstest" and "Polsterpressen-Distanzplättchen" (German, seen on screen 2026-11-09) and "Prueba de velocidad y potencia" and "Espaciadores de prensa de zapatillas" (Spanish) were cut off at both ends. English is unchanged. Only the long buttons grow, not all seven: three buttons at the longest German label's width need about 630 px, more than the 640 px window (the width with few tabs shown) has inside its margins. Gated in a child process per language, at the window's own width and at 640 px.

**Die inserts nest from the bottom-left corner (2026-11-09).** `svg_engine.nest_edge_bias(material, settings)` is the one place a nest's edge bias is read, and both nesters call it: pads get the Pad Maker's Edge Bias, `die_ring` always gets `DIE_NEST_EDGE_BIAS` ("sw": bottom-left as drawn, the G-code origin and the corner the head is jogged to for Frame & Cut). Tooling passes the shared settings dict, so until then dies inherited whatever the Pad Maker was set to, and its default, "center", puts the first and largest ring in the middle of the sheet: seven dies (30 to 44) on a 130 x 130 mm sheet placed 1 where 4 fit, and a job of two 50 mm rings and one 70 mm ring was refused as not fitting when it fits. Deciding it where the bias is read means the SVG, the G-code, Frame & Cut, the fit check and Scrap Mode all nest one layout, and nothing writes to the shared settings: the Pad Maker's Edge Bias is untouched in memory and on disk. Die output under any Edge Bias equals what the old code wrote with Edge Bias set to "sw" (checked on 48 cases, 540 files, under five bias values). Pads, adhesive rings and every other nest are byte-identical; Die Holders (a grid pack) never read the bias. *Measured, sheets needed in Scrap Mode over 24 list-and-sheet cases:* 125 from the corner, 146 from the centre, and 117 to 118 with the plain row scans ("off", "s", "w"). So the corner is not the best start everywhere: the full set 7 to 60 on a 12 x 12 in sheet takes 6 sheets from the corner and 5 from the centre or by rows, because the corner scan places smallest first and leaves the 70 mm rings for the last sheets. The rule is the one constant.

**Die Organizer**: A fourth Tooling section. The two source SVGs (`tooling_assets/die_organizer_upper.svg` and `_lower.svg`, Matt's CAD output) are bundled as data assets. Generate SVG copies one byte-for-byte to the user's chosen path, as it always has. `build.py` bundles `tooling_assets/` via `--add-data`.

*G-code and Frame & Cut (2026-11-09).* The section used to be SVG only, on the reasoning that LightBurn handles kerf, layers and material profiles better than we would and the organizer is a one-and-done part. That stopped being the right call once the aim became that nobody needs LightBurn. Matt: "building a gcode path for what needs it sounds like the right call." The section now has a material choice (basswood first, acrylic, cork; `tooling_settings.organizer_material`, stored as the key), a sheet size, Generate G-code and Frame & Cut, and its text offers G-code first and LightBurn as the other way.
- *The reader* (`svg_engine.read_die_organizer_drawing`) is no more than the drawings need, and **fails loudly on anything else** (`OrganizerDrawingError`): `rect` (with or without `rx`), `circle` and `ellipse`, each a direct child of `<svg>`, each placed by `translate(x,y)` or by a `matrix(...)` that is a pure rotation plus a move. A path, group, line, scale, skew, mirror, unit suffix, a missing viewBox, or a drawing without exactly one rectangle that is the whole plate raises, so a replacement drawing is never half read and mis-cut. The upper plate is 112 rects, 4 circles and 1 ellipse; **three of them are turned with a `matrix()`** (the oval and two 60.6 x 15.5 rectangles, about 89 and 90.4 degrees), which is why the reader takes a rotation and not just translate. The lower is the plate and 4 holes. To change the design, drop in a replacement SVG; if it uses anything else the G-code button says so.
- *Toolpaths* (`die_organizer_toolpaths`, `organizer_shape_path`): every element is a cut. Each path is the shape's exact parallel curve: openings half a kerf inward, the plate's own edge half a kerf outward, so slots, holes and plate come out at drawn size. A rectangle keeps its corner centres and changes its radius (a square slot stays square going inward); a circle changes radius and is built quarter by quarter so its four extreme points are on the path; the oval is moved along its normals, since a grown ellipse is not an ellipse. Corners are true arcs linearized to `TOOLPATH_ARC_TOLERANCE_MM` (0.002 mm of sag). A slot or hole too small for the kerf raises.
- *G-code* (`gcode_engine.generate_die_organizer_gcode`): all openings first in the drawing's order (layer C01), the edge last (C02), so the plate stays in the sheet until its slots are done. Cut speed, power, passes, air and kerf come from the chosen material; a material with no cut speed or power is refused. The plate sits `ORGANIZER_MARGIN_MM` (2) in from the sheet's bottom-left corner, which is the origin: drawing y becomes margin + 330 - y. The smallest sheet is 234 x 334 mm, upright as drawn (no auto-rotation); a smaller one is refused by the tab in the user's language before the save dialog, and by the engine as a backstop.
- Tests: `tools/test_die_organizer_gcode.py` (15). The key one reads the SVG **with regexes written in the test**, works out where each element's bounding box must land after kerf and the Y flip (turned rectangles and the oval included), and requires one closed cut per element there. Also inner before outer, the 230 x 330 + kerf box, true-arc corners, the oval being a parallel curve and not a scaled one (with a control that a scaled oval fails), the reader's fourteen refusals, cut settings, and the real section.

**Pad Press Spacers**: bundled 3D-printable STL files (`pad_press_spacers/*.stl`) copied byte-for-byte to the user's chosen path via `ToolingTabMixin._save_pad_spacer_stl`. Three sets: half-step (3.0/3.5/4.0/4.5 mm × 4 each, 16 total), quarter-step (3.25/3.75/4.25 mm × 4 each, 12 total), and an organizer rack with 7 compartments. No engine code — they're static assets bundled via `build.py --add-data`.

**Tonehole Crescent (2026-10-14)**: a crescent glued into the *mouthpiece* side of a tonehole covers part of its open area and flattens that note. Matt's case: a Selmer Super tenor whose bell is genuinely too short, so B and Bb need help. He notes crescents are rarely needed and sometimes overused, so the section's copy stays factual rather than promotional. Inputs: tonehole ID, **% of open area to cover** (area, not diameter: it's the acoustic quantity, and the readout shows the widest point in mm for checking with calipers), and an inner-edge curve slider. Outputs: SVG (one cut path made of two true arcs, no kerf compensation since the SVG does not know the material), a binary STL extruded to a print thickness, and since 2026-11-09 G-code cut from a chosen material with its kerf compensated (below). All geometry lives in `svg_engine.py` (`tonehole_crescent_geometry` and friends) and is shared by the preview canvas, the SVG and the STL.
- *Geometry*: the outer edge is the tonehole circle; the inner edge is an arc of a second circle slid in from the far side, solved by bisection on the circle–circle overlap area until the uncovered lens is `(1 − p)` of the tonehole. Mouthpiece side is −y in SVG/preview coordinates and +y in the STL.
- *The slider* (0–100, stored as `tooling_settings.crescent_curve`) sets inner-edge curvature relative to the tonehole's. **75 = the classic crescent** (inner radius = tonehole radius, `CRESCENT_CURVE_STANDARD`), 0 = curvature 0.2 (nearly a flat D). Rounder than standard is measured as a *fraction of the way* toward curvature `1/√(1−p)` and stops halfway, because that's where the inner circle becomes as small as the opening it leaves and the horns close into a ring. That limit moves with the percentage, so a fixed curvature range would be impossible at the small percentages that are the common case (at 10% the whole rounder-than-standard window is under 5% of curvature). Matt asked for "between A and C, a bit more on each side" and approved the prototype grid on 2026-10-14.
- *SVG precision*: the path prints 8 decimals, not the usual 4. On a small tonehole at a low percentage the horns sit within 1e-4 mm of a diameter apart, where the arc centre a reader rebuilds from the endpoints moves ~250× as far as they do; 4 decimals collapsed both arcs into the same semicircle (caught by the test grid at 8 mm / 0.5%).
- *STL*: the cap is a strip between the two edges matched point for point (degenerate triangle at each horn dropped), plus a wall quad per outline segment. Watertight and wound outward; header must not start with `solid`.
- *Several at once*: a list (`tooling_settings.crescent_list`, entries `{tonehole_d, percent, curve, qty}`). Add to list takes the fields plus a quantity; **Generate makes the list when it has entries and the crescent in the fields only when it's empty**, and a hint line under the list says which, because the fields keep showing whatever was typed last. `layout_tonehole_crescents` shelf-packs the parts' bounding boxes in list order (rows about as wide as the layout is tall; copies stay adjacent). The SVG and STL generators both take the entry list. **With more than one entry the SVG engraves each part's 1-based list number centred under it, on the scrap**, because a B and a Bb crescent a couple of mm apart look alike once cut and a part a few mm wide has no room for a number (the Labeled Zones reasoning). Copies of a single entry aren't numbered, and the STL never is, since a print has no engrave layer. Saved entries go through `_clean_crescent_entry` on load, so a hand-edited or stale list drops bad rows instead of failing the tab. Matt asked for the list on 2026-10-14, choosing it over "copies of one" and "percentage test set", which it covers.
- *G-code and Frame & Cut (2026-11-09)*: the section has a material choice (`_CRESCENT_MATERIALS`, cork first and the default; `tooling_settings.crescent_material`), Generate G-code and Frame & Cut. Same list-or-fields rule, same layout and numbering rule as the SVG (`generate_tonehole_crescent_gcode` calls `layout_tonehole_crescents`). The SVG still has no kerf compensation because it does not know the material; **the G-code does and compensates exactly**. `tonehole_crescent_toolpath(geom, kerf)` is the outline's parallel curve: outer circle radius plus kerf/2, inner circle radius minus kerf/2 (same centres), and each horn wrapped by an arc of radius kerf/2 centred on the horn's tip. The tip is then exactly half a kerf from the path on both sides, so the part comes out at the designed outline, horns included. With kerf 0 the path is the outline (cork ships with kerf 0, which reproduces the crescent Matt cut). **The two offset circles are not run on to where they cross** (a mitre), which was the first plan: the part would be the same, but on a thin crescent the edges meet at a shallow angle and the crossing is far away, 6.44 mm past the horn on a 43 mm tonehole at 2 % with a 0.2 kerf (2.55 at 5 %, 1.27 at 10 %, 0.63 at 20 %), through the number engraved under the part and into its neighbour. The wrap never leaves the design by more than kerf/2, so the SVG's layout needs no change. Refusals (`CrescentKerfError`, turned into a translated message by the tab): a kerf outside 0 to `CRESCENT_MAX_KERF_MM` (1.0), or a horn gap narrower than the kerf, which the beam would bridge. The horns are never closer than 0.66 x the tonehole diameter (75 %, roundest edge), so that second refusal needs a tonehole under 1.5 mm: a guard nobody will meet. **A thin crescent is never refused for being thin**: compensation only moves the path away from the part. Numbers are engraved first (layer C03) with the material's engraving settings, then one closed cut per crescent (C02); a material with no engraving settings gets no numbers (see "Cork"). Y is flipped with the layout's height, so the mouthpiece side is up in the SVG and up (+Y) on the bed. Tests: `tools/test_tonehole_crescent_gcode.py` (15): over 175 crescents x three kerfs, every path point is half a kerf from the design outline (measured against the two design arcs in the test, not with the app's offset code), the path's area is the design's plus perimeter x kerf/2 plus pi (kerf/2)^2, and every design point including the two tips is half a kerf inside it; kerf 0 is the outline; parity with the SVG's own arcs after the Y flip; the list and numbering rule; cork as shipped; the real section.
- Tests: `tools/test_tonehole_crescent.py` (area exact on a 224-case grid, monotonic slider, horns never close, SVG arc flags checked with an independent SVG-spec arc converter that exercises both large-arc values on both arcs, STL watertight with volume = area × thickness, list layout without overlaps and with each number under its own part, one STL shell per part, UI preview/validation/persistence/list), plus SVG, STL and a numbered list SVG through the real buttons in `test_tooling_e2e`.

**Framing power (`config.get_framing_power_s(material, settings)`)**: per-material Grbl S value for the framing pass, edited via Options > Machine > Framing Power. Framing is a positioning preview — bright enough to follow by eye, dim enough not to mark — and the right value is material-dependent: S10 (1%) reads fine on card but is invisible on dark leather, which is what prompted this. `laser_framing_power_by_material` holds the seven `GCODE_PRESET_MATERIALS` (adhesive rings and cork included; the rings' row in the dialog shows only while that feature is on); `laser_framing_power_s` remains the fallback for materials with no entry (`exact_size`) and for pre-existing configs. Defaults are all 10, unchanged from before the setting existed — shipping a higher default would silently alter every user's framing brightness. `FRAMING_POWER_S_MAX` (30 = 3%) is the ceiling — 3% covers the whole useful span, since even dark leather only needs a little more than card, and anything approaching engraving power marks the piece being lined up. It is enforced in `get_framing_power_s()` (clamped on **read**, not only in the dialog), so a config written under the earlier 15% ceiling can't keep framing at a marking power for a user who never reopens the dialog. The dialog shows one decimal always (`1.0`, not `1`) because the useful range is narrow and tenths are where the tuning lives — S values are integers, so 0.1% is exactly the available precision. Camera Calibration frames at basswood's value (the card material).

**Framing must always use M4, never M3** — non-negotiable, and it gets easier to break now that the power is user-adjustable. M4 scales the beam with feed rate so it drops to zero whenever the head decelerates or parks at a vertex, which is exactly what happens during a continuous framing loop while the user jogs or thinks. M3 would hold the full S value through every stall and scorch the material, and a higher S makes that worse. `tools/test_framing_power.py` asserts M4-and-not-M3 across the whole power range for both `generate_polygon_framing_gcode` and `generate_framing_gcode`.

The laser check comes before the job is prepared, as for pads, so nothing is asked or written when there is no laser. **The machine half reads the job's own values, never the Pad Maker's state**: for a Tooling job the framing polygon, the Try Auto Locate target and the flip override are None and the origin is `G92 X0 Y0`, whatever shape is loaded on the Pad Maker (`_frame_cut_anchor` is not asked). A scrap outline left loaded on the Pad Maker would otherwise shift a die cut by its anchor and frame the wrong shape; gated. A pad job that was not nested on the loaded shape (card on "Fit card to paper") is treated the same way: `on_shape` in `on_frame_and_cut` is the one switch for both.

*Why the machine half was not moved into its own method.* That was the plan. Three existing suites read `on_frame_and_cut`'s **source** for the pad flow's guarantees: `test_lid_confirm` (the jog dialog, `remind_lid_on_advance=True` and "Start Frame" are in this method), `test_frame_cut_alignment` (`flip_height_mm=flip_height_mm`, the outline-first flip source, `_keep_last_cut_gcode(`) and `test_framing_power` (`get_framing_power_s(material`). They were to stay green untouched, and moving the jog dialog out makes the first one false. So the routine stayed where the gates look and gained the job argument instead: one branch at the top (pad job or Tooling job), one for the origin, one after the cut. If it is ever split, those four source checks move with it.

*The stream is the file.* Each Generate G-code handler and its Frame & Cut twin share their validation and their generator call (`_validate_die_job`, `_die_scrap_begin`, `_validate_holder_job`, `_organizer_gcode_job` + `_write_organizer_gcode`, `_kerf_gcode_job` + `_write_kerf_gcode`, `_prepare_feeds_speeds_pieces` + `_write_feeds_speeds_gcode`, `_crescent_entries` + `_write_crescent_gcode`), so they refuse the same input in the same words and produce the same G-code. Frame & Cut runs the generator into a temp file, reads it back and deletes it (`ToolingTabMixin._gcode_text_from`), the way the Pad Maker does. Nothing is written to the user's folders except the Speed & Power legend. The refactor of the Generate handlers was checked against the committed code: 48 clicks, every prompt, file name and file content hash identical (the Done boxes differ only by the line described under "The G-code file line").

*Material.* Framing power and the cut dialog's title use acrylic for dies and holders (they always cut from `gcode_settings['acrylic']`) and the selected material for the Die Organizer, the Kerf Test, the Speed & Power Test and the Tonehole Crescent. Framing is the bounding box of the job's G-code (`extract_gcode_bbox`, which includes the return to X0 Y0, so the box starts at the jogged corner), at `get_framing_power_s(material)`, M4 as always.

*Material names in a translated app (bug found here, fixed).* The Kerf and Speed & Power dropdowns list translated names, and the settings key was the shown name lower-cased. That is only right in English: in German "Filz" looked up `gcode_settings['filz']`, found nothing, and the kerf test with "Use existing G-code settings" ticked ran at the hard-coded fallback, 180 mm/min at 100 %, instead of the user's felt settings. It had shipped for as long as those dropdowns have been translated, for file export too. `ToolingTabMixin._tooling_material_key` now maps the shown name back (translated first, then English, then the old lower-casing), `_tooling_material_label` goes the other way, and every Tooling material dropdown uses them. The suggested file names still come from the shown name, so they did not change in any language.

*Speed & Power legend.* The legend is the only record of which disc was cut at which settings. Frame & Cut asks where to save it (default `<name>_<material>_legend.txt`) after the preview and before the laser is touched, writes it with the same `_write_feeds_speeds_legend` (which takes an optional `legend_path` so the name the user typed is the name written), and a cancelled prompt cancels the run. `SpeedPowerTestPreview` takes a `proceed_label`, and Frame & Cut passes "Continue →" because nothing is saved.

*Die Scrap Mode.* One sheet per click. `_die_scrap_begin(folder_title)` is the front half shared by Generate SVG, Generate G-code and Frame & Cut (start or continue the session, nest what fits), and it counts nothing. The file exports count the sheet when the file is written, as before. Frame & Cut counts it in the job's `after_cut`, and only when the cut ended as "complete": cancelled at the jog step, framing stopped, cut stopped or errored, or no connection all leave the session exactly as it was and the same dies are offered again. A session that Frame & Cut starts has no folder (it writes nothing); a file export joining it asks for the folder then, once. The Pad Maker's rule, see `_frame_cut_scrap_advance`.

*Gating: one rule for both tabs.* See the Machine menu paragraph above. The first version of this work gated the Tooling buttons more loosely than the Pad Maker's (no calibration) and left the Pad Maker's alone; the same day Matt removed the calibration requirement from the Pad Maker too. The toggle itself is still restart-required, as the app says; the buttons follow detection and calibration live because those call `_refresh_machine_ui_state`.

*Small things decided.* The "Live camera preview" tick applies to a Tooling run on the same condition as a Pad Maker run: only while a calibration exists. After a finished kerf cut the measuring steps show, as after Generate. Tooling runs are **not** in Job History: that log is a pad list that can be loaded back into the Pad Maker's form. They do get `last_frame_cut.gcode` and one `app.log` line, `frame&cut tooling <tool> (<material>) scrap <n>: <k> pieces, ...`. The button is as wide as the Generate buttons and never narrower than its label (20 characters in German).

*Still no G-code:* on the Pad Maker the Exact Size material (SVG only, it has no laser settings). The Pad Press Spacers are 3D prints. Every other output can be cut by this app.

*Five older bugs, found during this work and fixed before 3.0 (2026-11-09).* All five were in v2.9. Matt: "Yes, fix all five". Gated together in `tools/test_release_3_0.py` (20 of its 29 checks; run against the code as it was, 14 of the 20 fail and the other 6 are controls that must pass on both; each fix was also broken on purpose, 20 single breaks, every one caught by the check meant for it). Four more of its checks gate the message-box guard (see CLAUDE.md "No suite may open a native message box") and five the lid question's buttons.
- **Card on "Fit card to paper" with a shape still loaded: Frame & Cut cut off the sheet.** `_get_material_dimensions` nests that job on the paper and ignores the shape (`mat_polygon` is None), and the file export was always right. The machine half still framed the shape, took the G92 from the shape's anchor and flipped the cut with the shape's height: with a 160 x 122 mm shape loaded the cut landed at y -48 to 20 where the same job with no shape lands at y 103 to 171. Now `on_shape = mat_polygon is not None` decides it once in `on_frame_and_cut`: a job that was not nested on the loaded shape takes nothing from it (no framing polygon, no flip override, `G92 X0 Y0`, no Auto Locate target), the rule Tooling jobs already followed (`on_shape = False` there). Such a run streams exactly what it streams with no shape loaded, and the cut is the exported file. No message is shown: the export ignores the shape silently and this matches it. A machine position only ever exists together with its camera shape (every unload clears both), so "a position but no shape" is not a state the app reaches, and it gets no target either.
- **Cancelling at the jog step never disconnected the sender.** The `try` whose `finally` calls `sender.disconnect()` started at the framing loop, after the jog dialog, so a cancelled jog (or an exception in `$X` or while the jog dialog was built) left the port open until the object was collected, and a quick second Frame & Cut could fail to open it. The `try` now starts right after a successful `connect()`: everything done with the port open is inside it, for pad and Tooling jobs alike. What is streamed, and in what order, is unchanged.
- **The no-laser return left the sleep lock held.** It sat after `sleep_lock.prevent_sleep()` and before the `try` whose `finally` releases the lock. The laser check now comes first; nothing may return between taking the lock and that `try`.

- **Tooling's section buttons cut off long labels**: see "Section buttons" under Tooling Tab.

**Cork, and "engraving not set" (2026-11-09)**: Matt: "tonehole crescents are usually cork. we do not have that as a material yet". `cork` is a full G-code material (every key in `GCODE_PRESET_KEYS`; the seventh entry in `GCODE_PRESET_MATERIALS`, so the first-launch backfill gives every user a `cork` Default preset) and a **Tooling material only** (`config.TOOLING_GCODE_MATERIALS` = acrylic, basswood, cork): it is in the Tooling settings dialog, the Kerf Test and Speed & Power Test lists, Framing Power and the Tonehole Crescent's material choice (its default), and not on the Pad Maker or in the Pad Maker's G-code Settings.
- *The cut default is a tested value*: 1000 mm/min at 30 %, one pass, air on, on 3/32 in (2.4 mm) sheet cork on a 40 W Falcon. It is what Matt cut a 43 mm, 20 % crescent with on 2026-10-14 (his file `crescent_43mm_20pct.gcode`, LightBurn output, one layer `Cut @ 1000 mm/min, 30% power`, M4, M8), in his words "it was perfect for 3/32 cork". About 0.30 J per mm of cut per mm of thickness. Two derived proposals came first (1600 mm/min at 50 % for an assumed 1.6 mm sheet, then 1050 mm/min at 50 % for 2.4 mm, scaled from the 3 mm basswood default at half the density); the second would have been about 55 % hotter than what actually worked.
- *The kerf is not measured.* 0.0 reproduces that crescent: its path encloses 290.45 mm2 and 20 % of a 43 mm tonehole is 290.44 mm2, so it was cut on the design line. No text may call the kerf tested; the dialog note and the guide point at Tooling > Kerf Test.
- *The engraving is not set, on purpose.* Matt: "leave the engraving setting for cork at 0/0. don't want a guess in there." **A speed or a power of 0 means "not set"** (`config.engraving_is_set`), for any material. No generator may write an `F0` move (Grbl rejects a zero feed) or trace an engraving at `S0`, so the three Tooling generators that engrave with the chosen material leave the engraving out and still write every cut: the crescent's list numbers, the Kerf Test's title and sizes, the Speed & Power Test's disc IDs. **Never silently**: `ToolingTabMixin._engraving_not_set_notice` gives one plain line, which goes in the Done box for a file and is asked (OK / Cancel, `_confirm_engraving_skipped`) before a Frame & Cut run; for a crescent list it says the parts will not be numbered and where to set it. The Speed & Power Test pre-fills its Engraving fields from the material, so with cork they read 0 and 0 (the power used to be floored to 1 %; not for a material with none). **0 there is accepted, not refused**: the test runs, the IDs are left off, and the notice says so. Refusing would only push the user to type a guess, the thing Matt did not want; negative or over 100 % is still a typo and refused. The pad engines and the die and holder generators are untouched (their engraving output is byte-identical: the 48-case hash and the 48-click export record both match the committed code).
