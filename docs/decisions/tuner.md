# Strobe tuner and GPU renderer: decisions and history

This file holds the why and the history behind the rules in the CLAUDE files, and the full detail they summarise: what was tried, measured, rejected and decided, with dates and the user's own words. The paragraphs were moved here verbatim from the CLAUDE files on 2026-11-10 (HEAD 01071f5); each section names where it came from. Add new decisions to the matching section, dated.

## GPU Tuner Renderer (Rust/wgpu)

*Moved from CLAUDE.md, section "CLAUDE.md > Building Executables > GPU Tuner Renderer (Rust/wgpu)" (2026-11-10).*

**Three renderer traps, found 2026-10-06** by an outside port of this crate into a Qt app on a 250 %-scaled laptop (Intel UHD, DX12), each verified here on the same GPU before fixing:

- **`Limits::downlevel_defaults()` caps textures at 2048 px.** A 1400 px tuner frame at 250 % is 3500 device px and `Surface::configure` panics ("maximum extent for either dimension is 2048") — in `Renderer::new` and again in `resize()` whenever the window grows past 2048. 150 % on a wide window is enough to hit it. Now `required_limits` is `downlevel_defaults().using_resolution(adapter.limits())` and `clamp_surface()` clamps width/height to `device.limits().max_texture_dimension_2d` in both places, so an oversize window stretches instead of panicking. Measured: 3500×1500 constructs and resizes.

- **A Rust panic reaches Python as `pyo3_runtime.PanicException`, a `BaseException`.** `except Exception` lets it through into Tk's callback. `tuner_tab.py` now catches `BaseException` (re-raising `KeyboardInterrupt`/`SystemExit`) at every call that can touch the surface — init, `resize`, `render` — and routes every failure through one `_tuner_gpu_fallback(reason)`: unpack the GPU frame, pack a canvas in its slot, show a CPU-mode notice that says *unavailable* (not *uninstalled*), log the reason. A single bad `render()` is a dropped frame; `GPU_RENDER_FAIL_LIMIT` (30, ~0.5 s) consecutive ones switch to the canvas. **Never retry the GPU on the same frame**: a failed `configure` leaves the surface dead. `_last_line()` trims the multi-line panic text for the log.

- **Fifo blocked `render()` for a full vsync on the UI thread.** Measured 16.66 ms/frame on Intel UHD/DX12 at 1400×800 — every tuner frame stalled Tk for 16 ms. The surface now takes `PresentMode::Mailbox` where `surface_caps.present_modes` offers it (it does on DX12), else Fifo: 0.45 ms/frame, same vsync-aligned output, no tearing. `present_mode()` reports which one is in use.

Also: **a software adapter counted as GPU mode.** If wgpu only finds Windows' Basic Render Driver or llvmpipe, `Renderer::new` succeeds and the CPU-mode hint never shows. `adapter_info()` exposes `(name, backend, device_type)`; the tab treats `device_type == "Cpu"` as no GPU and falls back. Logged at INFO on every GPU start, so `app.log` names the adapter and present mode. Gates: section 9 of `tools/test_gpu_tuner.py` (big-surface construct/resize, adapter_info/present_mode, and the render-failure fallback with a fake `BaseException`; GUI cases self-skip without a display or GPU). **JustATuner's `renderer.rs` is byte-identical to the pre-fix file and needs the same three changes** — do it there when the tuner's final home is settled, not twice. If the import fails for any reason the tuner falls back to canvas rendering on Windows/Linux — the app still runs, just slower. See the `_skip_theme` / `_dark_canvas` flag notes in the Strobe Tuner architecture section for integration details, and the GPU/Canvas constant alignment warning (`DIM_MULTIPLIER`, `BRIGHTNESS_GAMMA`) for what has to stay in sync between the Python path and the shader.

### macOS is canvas-only — never load `tuner_render` on darwin

**macOS is canvas-only — never load `tuner_render` on darwin.** Tk Aqua draws all widgets into a single NSView per toplevel, and `winfo_id()` returns a pointer to Tk's internal `MacDrawable` struct, not an NSView ("the value has no meaning outside Tk" — Tk docs). `tuner_renderer/src/platform.rs` would wrap that handle as an NSView, so wgpu's Metal backend segfaults in `objc_msgSend` during surface creation — a native crash the Python init-failure `except` in `tuner_tab.py` can never catch. Three layers enforce the gate: `tuner_tab.py` skips the `tuner_render` import on darwin, `build.py` skips the `--hidden-import` on darwin, and CI skips the Rust/maturin steps on macOS runners. Even a real NSView wouldn't fix it — a CAMetalLayer on the shared per-window view would paint over the entire UI (and would still need Retina scale handling), so macOS GPU rendering is off the table by design. **History**: the macOS Apple Silicon zips for v1.95 through v2.6 shipped with the renderer bundled — on those builds, opening the Tuner tab crashes the app outright.

## Strobe Tuner

*Moved from CLAUDE-engines.md, section "Engines: Pad Generation, G-code, Tuner, Tooling > Strobe Tuner" (2026-11-10).*

- **Peak frequency comes from the Hann closed form, not a parabola (2026-10-02).** `audio_utils.hann_peak_freq` reads a peak's frequency from the ratio of its larger neighbour to the peak bin, `d = (2a − 1)/(a + 1)`, which is exact for a Hann main lobe. The old parabola through three *linear* magnitudes is the wrong shape for Hann and lands up to ~0.05 bin off — and a bin is 10.77 Hz here, ~160 c at 110 Hz — so an exactly in-tune A2 read 7.8 c flat (E2 11.8 c) and the strobe turned on a note that was dead on. Both call sites (per-ring `ring_freq`, best-octave `cents_errors`/`phase_offsets`) use it; magnitudes, threshold and drift arithmetic are untouched, and the GPU renderer only draws the phases Python hands it, so nothing in `tuner_renderer/` changes. The estimator first climbs to the lobe's top (≤ 2 bins, the main-lobe half-width): the 3-bin window round the reference bin misses the top when a high note is well off pitch (B5 26 c flat peaks at bin 90; the window is 91–93), and without the climb that read 2.6 c wrong. A 4× zero-padded FFT with a log-parabola is equally accurate (measured, same worst case to 0.0001 bin) but costs a second, bigger FFT every frame — 0.5→0.8 ms/frame on the tuner and a 4-minute WAV import 4.0→16.1 s — so it was rejected. Gated by the "Pitch reading accuracy" block in `test_tuner_engine` (A2–A5 at ±20 c within 0.15 c; an in-tune note's wheel and ring turn less than 0.15 c worth per 0.1 s; the B5 off-window case). **JustATuner carries the same tuner code** and has the same bug.

- numpy and sounddevice are imported separately (2026-10-06); `AUDIO_AVAILABLE` means both are present, and the analysis math works wherever numpy is — the Intel Mac build has numpy but no sounddevice. One combined `try` used to set `np = None` whenever sounddevice was missing.

- `TunerEngine.synthetic_hz` is a test/CI hook, never set in normal use: `start()` opens no stream and `analyze()` feeds a generated tone (`audio_utils.synthetic_tone`) into the ring buffer, so the whole tab runs on a machine with no microphone (`test_tuner_canvas`, the `--tour` screenshots).

- `_tuner_error_state` keeps the "Audio error" / stream-error message across canvas rebuilds: `_tuner_build_wheels_canvas` starts with `delete("all")`, which used to wipe the message on the next resize, so a user with no microphone saw dark wheels and no explanation (Mac tour, 2026-10-06).

- **macOS is canvas-only**: `_HAS_GPU_RENDERER` is forced False on darwin at the top of `tuner_tab.py` — Tk Aqua's `winfo_id()` returns a `MacDrawable` pointer, not an NSView, and handing it to wgpu segfaults natively in `objc_msgSend` (no Python fallback possible). The same gate lives in `build.py` (no `--hidden-import` on darwin) and CI (no Rust/maturin on macOS runners). The "install tuner_render" CPU-mode hint is suppressed on macOS. Full mechanism in CLAUDE.md "GPU Tuner Renderer".

## The bottom row drifted the wrong way (2026-11-12)

Matt, on the installed beta: "the wheels on the tuner on the bottom row are moving in the wrong direction". True, and since the tuner shipped. Both renderers turn every disc the same way for a sharp note. The top row (the five accidentals) is seen through a wedge that opens upward, where that turn carries the stripes right; the bottom row (the seven naturals) through a wedge that opens downward, onto the bottom of the disc, where the same turn carries them left. So "drifting right: sharp" (the User Guide's words) held for five wheels of twelve.

Fix: `tuner_tab.window_phases(pitch_class, phases)` negates the phases of the bottom row's wheels (`BOTTOM_ROW_PITCH_CLASSES`, pinned to the layout's own `is_up`) before either renderer gets them: the GPU path's `ring_phases` and the canvas path's `phase` and `ring_phase_offsets`. Python only, one place; the shader's `angle - phase` and the Rust side are untouched, so no wheel rebuild is needed and the two renderers cannot disagree. Rejected: a sign per wheel in the shader (a second copy of the rule across the Python/Rust line, and a rebuilt wheel, for the same picture).

Gate: `test_tuner_canvas`, "the bottom row's discs are turned the other way". What no suite can see is the picture: Matt's eyes on a sharp and a flat natural. JustATuner carries the same tuner and has the same fault; not touched from here.

## Three faults ported from JustATuner (2026-11-25)

JustATuner (which carries this tuner) found four faults on 2026-11-25 and sent them here to port. Each was measured here first. Three were real here and are fixed; the fourth was not ported, see below.

**The canvas turned backwards.** The shader draws `angle - phase` with its angle clockwise from the top, so a rising phase turns the GPU disc clockwise; `StrobeWheel.update` drew `base + phase` in the canvas's counter-clockwise angles, the opposite turn (JustATuner measured it from screen pixels: +3 deg of phase, GPU +3.1 deg clockwise, canvas -3.1). The 2026-11-12 bottom-row fix negated the bottom row before both renderers, which made the GPU right and left the canvas wrong in all twelve windows: measured here from the canvas items' own coordinates, a sharp note's stripes travelled left in every window on the old code. The canvas is what every Mac draws, and what Windows and Linux fall back to. Nobody here owns a Mac, so nobody had watched it. Now `base_start - ring_phase`. The earlier gate's comment said the two renderers counted alike; that was the mistake, and the new gates read the drawn picture instead.

**The 60 setting ran at 32 fps.** `_tuner_animate` ended with `after(16)` after the frame's work, and Windows rounds every Tk timer up to its 15.6 ms tick. Measured here on the GPU path (Intel UHD, DX12, Mailbox), old code: 31.9 fps at 60, 64.1 at 90, 64.1 at 120. New: 60.0, 90.4, 119.3. JustATuner found that the 1 ms tick alone gave 40 fps and that both the clock pacing and the tick are needed, and that arming a short `after()` inside the frame let the next frame start before Tk had drawn the last on the canvas path. At this window size the canvas path keeps Tk busy about 32 ms a frame and runs at about 31 fps whatever the setting; the gate prints that rather than judging it. The Analyzer's loop (`toner_tab._toner_animate`) had the same `after(interval)`: 21.2 fps at its 30 setting and 32 at 60, measured. Matt: "fix the analyzer frame loop too". `FramePacer` and `fine_timer` moved to `frame_pacing.py` and both loops use them: the Analyzer now runs 30.0 at 30 and 60.1 at 60 (Tk busy about 14 ms a frame on this machine, so 60 is close to its limit here). Gated in `test_toner_live`.

**Room noise steered the inner rings.** A ring followed its own pitch whenever anything at its bins cleared the threshold, the whole spectrum's median, and a room's low end is many times that. On the gate's rumbling room (low end 30x the median) under an A4 5 c sharp, the old code turned the rings A1 to A3 with their wheel in 0 % of frames, sent them left in about half (48 to 68 frames of 118 each) and read them -20 to +18 c. The rule and its thresholds are JustATuner's, set there from 106,650 lit ring-frames of a real room; new code: 100 % with the wheel, none left, every ring +5.0 c, and octave partials 4 c and 9 c sharp still read +4.00 and +9.00 on their own rings.

**Not ported: the two-neighbour Hann estimator.** JustATuner changed `hann_peak_freq` from d = (2a - 1)/(a + 1) on the larger neighbour to d = 2(R - L)/(L + 2P + R), on the grounds that a note decaying in 20 ms read 0.105 bin off with the old form and 0.000 with the new. Measured here over every offset within a bin rather than only the bin centre, the two forms have the same worst error on a decaying note (tuner window, 20 ms decay: 0.105 against 0.107 bin; 100 ms: 0.006 against 0.007; toner window, 50 ms: 0.200 against 0.191). The difference is where the error falls: the old form's is largest at a bin centre and changes sign there (a note crossing it jumps about 0.2 bin), the new form's is continuous and largest near half a bin. JustATuner's gate only tests offsets within 0.01 bin of the centre. Through the whole engine on harmonic tones the decay errors were as large either way (A2, 50 ms decay: +1.98 c old, -1.52 c new). And the Analyzer, which shares the function, got worse on vibrato: +/-15 c vibrato read through the file path, alto 0.09 c mean (0.70 worst) with the old form against 0.73 c mean (2.08 worst) with the new, tenor 0.07 / 0.30 against 0.56 / 1.80, baritone 0.05 / 0.17 against 0.40 / 1.44; `test_pitch_octaves` failed its alto and tenor vibrato bounds. Clean, drifting and noisy tones were the same to 0.01 c. The tuner's vibrato readings were the same within 0.1 c. Sax notes are held, not plucked. Matt, on these figures, 2026-11-25: "Keep the old one". Don't port the two-neighbour form here without a measured gain on held notes and the Analyzer's vibrato bounds still met.
