# Tone analyzer: decisions and history

This file holds the why and the history behind the rules in the CLAUDE files, and the full detail they summarise: what was tried, measured, rejected and decided, with dates and the user's own words. The paragraphs were moved here verbatim from the CLAUDE files on 2026-11-10 (HEAD 01071f5); each section names where it came from. Add new decisions to the matching section, dated.

## Tone Analyzer (Toner)

*Moved from CLAUDE-toner.md, section "Tone Analyzer (Toner)" (2026-11-10).*

- Live descriptor gauges (Pure↔Complex, Thin↔Warm) were removed 2026-04-06. Mic position alone shifted complexity 10-20% across same-horn takes, mouthpiece dominates the signal (~25% systematic offset between mpcs), and the 51-preset corpus is too thin and too varied for absolute single-preset readouts to be meaningful. Brightness/darkness/resonance/fullness were removed earlier (2026-03-27) for similar reasons. The descriptor functions still live in `toner_engine.py` and feed the Analyze tool, where deltas cancel the mic/setup confounders. The right side of the live tab now shows just the intonation gauge and note display.

## Pitch reading (2026-10-02)

*Moved from CLAUDE-toner.md, section "Tone Analyzer (Toner) > Pitch reading (2026-10-02)" (2026-11-10).*

### Frequencies come from `audio_utils.hann_peak_freq`, levels don't

**Frequencies come from `audio_utils.hann_peak_freq`, levels don't.** `_detect_fundamental` and `_extract_harmonics` read each peak's frequency with the Hann closed form (mechanism and the rejected zero-padded alternative under "Strobe Tuner" in CLAUDE-engines.md). The old linear parabola put `fundamental_freq` up to ~4 c off (median 0.44, p95 1.9) and `harmonic_cents` up to ~5 c. `peak_mag` and its parabolic amplitude correction are **deliberately unchanged**, so `harmonics_db` — and every descriptor, none of which reads pitch — stays comparable with every capture already stored. Measured on 20-partial tones (H20 up to 9.9 kHz): every partial's level identical to the old code, every descriptor identical. A more accurate f0 does move the ±3-bin search window at high harmonic numbers, so a *noise-level* reading where a tone has no partial can change; that's noise either way. Captures stored before this carry the old pitch error in `fundamental_freq`/`harmonic_cents`; nothing in the Analyze tool reads them for a descriptor.

### Sub-harmonic verification counts only multiples coprime to the divisor

**Sub-harmonic verification counts only multiples coprime to the divisor.** The check "is the strongest peak harmonic *d* of a lower fundamental?" used to count every multiple in `[2, 3, 4]` / `[2..6]`, including `mult == divisor` (the strongest peak itself) and multiples of it (`/2` ×4 is the strongest's own H2; `/4` ×2 and ×6 are the `/2` candidate's H1 and H3). Those are present whether or not the candidate is real, so any noise bump at half a note passed as its fundamental — 138 octave-low frames of 14,070 in a sweep of every soprano/alto/tenor/bari note. Now only `gcd(mult, divisor) == 1` counts, and the requirement drops by one because the candidate's own peak is already checked for noise and prominence; for `/3` and `/5` that is exactly the old effective rule. Same sweep: 10 octave-low, 0 high. **Don't "simplify" it to skipping only `mult == divisor`** — that was proposed in an outside review of the ported code, and measured: with self excluded, `/2` needs both H3 and H4, so a tone with H2 a little over H1 and no H4 reads an octave HIGH — 2,199 of the same 14,070 frames, and Test 13's warm tone (H1, H2, H3 only) read 880 for 440. Also: the peak search round a sub-harmonic can reach below `MIN_FUNDAMENTAL_HZ`; such a peak is skipped. Gated by Tests 20–21 in `test_toner_engine` (a 233.08 Hz tone within 0.05 c and its harmonics within 1 dB; a hand-built spectrum per octave mechanism; H2-over-H1 tones read the right octave; a 2,144-frame sweep with no octave error either way and every frame within 0.5 c).

**Cost**: none worth measuring — the estimator reads the spectrum already computed. A 4-minute WAV through `analyze_audio_file`: best of three 3.85 s before, 4.26 s after on a noisy machine.

## Recording Quality

*Moved from CLAUDE-toner.md, section "Tone Analyzer (Toner) > Recording Quality" (2026-11-10).*

`compute_rolloff_rate()` measures harmonic rolloff (dB/harmonic). Live warning if rolloff exceeds the threshold returned by `get_rolloff_threshold(mic_type, sax_type)` (suppressible per-preset via "Don't show again" checkbox). Stored per session and in fingerprints. Comparison tool warns on mismatch. The threshold function takes both mic class and sax type because both matter: ribbon mics naturally read higher than dynamics, which read higher than condensers (HF rolloff in the mic itself); and higher-pitched horns naturally read higher than lower-pitched horns (their H12 reaches further into the mic's HF rolloff region). Current values: ribbon 3.5, dynamic 2.8 (alto+dynamic bumped to 3.5 after Foster's Conn 6M data showed alto reads ~1 dB/H higher than bari with the same RE20), condenser uses the base `ROLLOFF_WARN_THRESHOLD` constant. Both call sites in `toner_tab.py` pass sax_type — the live capture handler from `engine.sax_type`, the Analyze tool from `fp['_preset']['horn_type']`. Real-world rolloff readings observed: Matt AT2020 condenser 1.1-1.3 dB/H, Tyler Neumann TLM 1.8-3.1, Edinger U67 1.65-2.04, Mario AT2035 alto 1.99 / soprano 4.00, Foster RE20 dynamic bari 1.5-2.3 / alto 2.99-3.49, Grant MXL RI44 ribbon tenor 2.16-2.46.

## Analyze Tool

*Moved from CLAUDE-toner.md, section "Tone Analyzer (Toner) > Analyze Tool" (2026-11-10).*

Renamed from Compare. Handles single preset view, two-preset delta analysis with difference chart, and multi-preset spread analysis. Accessible via File > Analyze... or File > Presets > Analyze. Analysis descriptors (complexity, warmth, even/odd, rolloff shape, evenness) are user-configurable in Options > Settings > Analysis tab. Back button on analysis/group report windows returns to the selection picker. Clickable legend labels and chart lines show preset detail (player, mpc, mic, etc.). **Character Map**: 2D quad-chart scatter plot of every selected preset on warmth x complexity axes (Y axis was originally "H4-H5 mean" but switched to complexity 2026-04-06 because warmth and H4-H5 share a denominator and were not independent within tenors); click a dot, legend entry, or chart line and the matching items highlight together in the same color across legend, harmonic chart, and quad map. **Bars chart toggle**: switch the harmonic comparison chart between line view and side-by-side bars view. **Maximize / fullscreen mode**: the Analyze window is non-modal (intentionally NOT a transient toplevel, since transients lose the maximize button on Windows), resizes freely, and has a Maximize button that toggles between zoomed and normal window state (with a macOS Aqua fallback that uses a screen-filling geometry since Aqua doesn't support `state('zoomed')`). The whole window scrolls vertically since comparison data can exceed any viewport. Same pattern is applied to the Group Report dialog. **Cross-sax-type warning**: mixing alto + tenor + bari + soprano in one comparison is allowed but pops a warning, since lower-pitched horns intrinsically read warmer/brighter regardless of mouthpiece.

## Tone Preset Data Model

*Moved from CLAUDE-toner.md, section "Tone Analyzer (Toner) > Tone Preset Data Model" (2026-11-10).*

### Read-side capture filter

**Read-side capture filter** (`_capture_is_plausible()`): Before averaging, `compute_fingerprint` drops captures that fail two checks. (1) **Range filter**: the labeled note must fall inside `SAX_NOTE_RANGES[sax_type]`, which uses tight bounds — lower bound = written low Bb for most types, extended to low A only on bari (common spec) and alto (rare); upper bound = high F# written (no altissimo margin, because altissimo is a harmonic partial of a lower fingering, not a true closed-tube fundamental, so its harmonic structure isn't useful for tone analysis). (2) **Plausibility filter**: no value in `harmonics_db` may be NaN, ±inf (checked with `math.isfinite` — JSON round-trips `-Infinity` happily and one poisons every average), or > +20 dB above the labeled fundamental — that's a clear sub-octave detection error where the real fundamental landed in an upper-harmonic bin. Real low-register alto H2 tops out near +10 dB legitimately, so +20 dB is the hard sentinel. The filter is read-only — raw on-disk captures are NOT modified, so any descriptor formula or filter improvement applies retroactively to historical data on the next load. Was added 2026-04-07 after a library audit found 37 of 58 presets had at least one out-of-range capture; the worst case (Selmer VI alto GP) had 105 of 164 captures bogus.

## Toner Calibration

*Moved from CLAUDE-toner.md, section "Tone Analyzer (Toner) > Toner Calibration" (2026-11-10).*

### Descriptor calibration status

**Descriptor calibration status**: Two descriptors survived data-driven validation: complexity (spectral flatness) and warmth (H2 strength). Brightness/darkness were removed because the labels conflicted with player vocabulary (data showed Yamahas read "dark" but players call them "bright"). Resonance was removed because it read 100% on all 39 presets — no differentiation. Fullness was removed because it depended on brightness/darkness. Key constants live in toner_engine.py: `RICHNESS_RAW_MIN`, `RICHNESS_RAW_RANGE`, `WARMTH_DB_FLOOR`, `WARMTH_DB_RANGE`. Development history in `.claude/projects/*/memory/descriptors.md`. `tools/profile_report.py` generates a detailed single-preset report.

## The Analyzer, round 1: characterization, the capture port, the intonation module (2026-11-10)

Matt: "I wonder if we can incorporate that into the harmonic analyzer and just change that to the analyzer. we can forefront the intonation bit, and the harmonic fingerprints etc can be something people CAN use but do not need to." For 3.0. His decisions, as relayed: the tab is "Analyzer" and opens on the intonation chart; the harmonics side stays behind a switch and is labelled "experimental"; the Analyzer tab is viewable by default and the one-time terms gate the switch, not the tab; both capture modes with an easy toggle, default free ("that is what I personally like"); an intonation run requires sax make, model and size, mouthpiece and player (serial and the other fields optional, plus notes; mic type and model stay required for the harmonics side only); the chart shows each note low to high (a preference, default low on the left), overlays runs picked from the library, exports as image or PDF; the look is the comparison figure Matt sent (a colour and a marker per run, a legend above in columns, a title, x the written notes turned 90 degrees, y cents with a grid every 10, a solid zero line, the register change dashed); the y axis is cents AS PLAYED and nothing else ("just as played is what everyone will want to see. the other two options do not make sense to me"). Round 1 (this entry) built the engine and data with no visible change; round 2 builds the tab.

**Characterization first.** The toner was the thinnest-covered part of the app, so before anything changed, two suites pinned it as it was: `test_toner_live` grew a second half that feeds the tab's capture state machine fabricated frames on a seeded library (the mic backfill, the preset label, free and calibration capture rules, the session saved once per date, the exit flush, the library read back), and `test_toner_data` (45 checks, headless, 1.8 s) pinned storage and its migrations (in subprocesses), the fingerprint and descriptor arithmetic with golden numbers, and the file analyzer on generated WAVs. Both passed on c436232 as it was. Facts recorded on the way, left as they are: sessions are keyed by their date to the second, so two sessions started within one second collide; a session with no capture is never written; `save_tone_presets` leaves `<file>.tmp` behind when the target is a directory or the dump fails partway; `analyze_audio_file`'s progress total is one short and its callback fires only every 200 windows (a file under 200 windows never calls it, none reports completion); the same note across a silence gap joins into one capture only if no release window misreads (D4 joins, A3 splits); `compute_group_fingerprint`'s empty result has a different shape from a full one; `note_name_to_midi` reads no flats and no two-digit octaves; `compute_fingerprint` drops `harmonic_cents`; `percentile_rank` ranks ties low.

**The capture rules.** Three rules were named; two were missing here and were added, one was already here:
- *Whole-window frames only.* Free mode skipped three attack frames and kept everything to the note's end; calibration kept everything after the first 0.1 s; the file analyzer skipped three frames. A frame reads the last 0.37 s of sound, so the frames at either end held the onset or the release. Now `whole_window` keeps a frame only when its whole window lies inside the note, in all three paths (`toner_engine.whole_window`, `WINDOW_S`). Measured on a generated A3 held 1.5 s: the file analyzer read it at -1.09 cents before (the release averaged in) and reads it at 0.00 after; a 40-frame free note gives a 16-frame capture (was 37); a note must be held about 1.1 s to be kept at all (was 0.43 s); a 5 s calibration note gives 141 frames (was 149). Stored captures are raw data and untouched; `compute_fingerprint` recomputes from them, so every fingerprint golden in `test_toner_data` is the same before and after. What changes for users: new captures average fewer frames than the ones they already have, so a capture from before 2026-11-10 is not frame-for-frame comparable with one made after; short notes in free mode are no longer kept (it is recorded in `_toner_too_short` for round 2's status line, since round 1 adds no string).
- *Audio-time clocks.* The capture machine ran on `time.time()`. Now `TonerEngine.audio_time_s` counts the samples the input hands over (the callback's frames; 1024 per `analyze()` on the synthetic source) and the tab reads it through `_toner_clock()`. On a microphone nothing changes; a WAV fed faster than real time counts the same seconds, which is what lets the suites drive the machine without waiting.
- *A calibration capture stored under the note asked for, with `detected_as`:* this app already did that (`note` the asked note's concert name, `written_note`, `detected_as` in display pitch), so nothing moved; the characterization pins it, including the case where the detector disagrees.
Not ported, not asked: `level_dbfs` on captures and `wav_start_s`/`wav_end_s` on calibration captures (the re-read of a recording under the asked names); listed for a later round.

**The intonation module** (`intonation.py`): a capture is a `Take` (cents of its fundamental against equal temperament at the reference pitch, which the captures do not record, so the caller's is used and the run says which), takes of one written note a `NoteReading` whose cents are the median of its takes (one misfiled take cannot drag it), with the takes' spread (max - min) and lowest and highest for the chart's bars; written names by `SAX_TRANSPOSITIONS` in this app's spelling (sharps); registers by the written note as the horn is played (to C#5 the low register, D5 up the octave key; D6 up the palm keys as a band for a summary); the fingerprint's plausibility filter applies and the leavings are counted. `note_spreads`, `overlay` (the union of the runs' notes low to high, one register per note, one line of points per run) and `register_changes` are the chart's data; `offset_and_shape` (the mean, "the player and the cork", each note less it, "the horn", per register) and `low_register_offset` (the median of the low register) are kept because they cost nothing, and nothing shows them. Its test cases cover (the median of takes, the spread, tenor G#2 as written A#3 low and C4 as D5 upper, the dropped out-of-range and impossible-harmonic captures, the reference pitch at 442 and 440, the offset arithmetic, the no-prediction case).

**Not done in round 1, by the brief:** the tab, the chart, the switch, the export, the strings and their catalogs, the settings for the chart preference. The data-model and export proposals, the migration of `visible_tabs` / `toner_unlocked`, and the list of every string that says Toner are in the round-1 report for the parent session to confirm.

## The Analyzer, round 2: the tab (2026-11-10)

Round 1's engine and data got their tab the same day: the Toner tab became the Analyzer, opening on the intonation chart, with the harmonic analyzer behind a HARMONICS switch and marked experimental. Matt's answers to round 1's questions: the ~1.1 s minimum for a free note is fine, "have the frames or whatever it shows turn green when its long enough to use"; required for a run are "name, make, model, size, player, mouthpiece. no mic details for intonation but required for harmonics sounds good"; export "png and pdf sounds good". A wrapped import file is unwrapped and a newer format version refused.

**The top area is one of two frames**, swapped by `_toner_show_harmonics` with `pack(before=the first packed child)`, so the capture bar and the control strip keep their places under either. Nothing else of the harmonics view moved: the spectrum, the gauge, the Analyze tool and the ghost overlay are as they were, and the spectrum is simply not rendered while its frame is hidden. The guided-capture prompt (the large note name) lives on the spectrum canvas, which nobody sees while the switch is off, so `_toner_update_cal_prompt` draws it on the chart canvas as well; the chart redraw deletes only its own tag and raises the prompt over it.

**The switch is off at every start.** Persisting it was considered and not done: not asked for, and a user who turned the harmonics on once would otherwise never see the chart first again. The terms dialog moved from a nested function in main's Feature Set to `toner_tab._toner_show_harmonics_terms` (same text with "experimental" for "beta" and the Analyzer for the Toner; mic fields "for harmonic captures"), triggered by the switch's trace through `after_idle`, since a modal dialog from inside a Scale's own variable trace would open while the slider is still being dragged. A decline moves the slider back (`_toner_harmonics_int.set(0)`), whose own trace puts the variable to off; an accept stores `toner_unlocked` and saves at once. Feature Set lost its terms branch and its "Experimental / In Progress" tab list; the heading stays for the Machine menu tick and shows only when that tick does.

**The free readout counts kept frames, not frames.** The readout shows how many frames a capture would keep if the note ended now (`whole_window` over the frames so far, with "now" as the end), so the number reaches `FREE_MIN_FRAMES` at exactly the frame where a release would be kept, and that is when it turns green (the IN TUNE lamp's #00CC00; pinned at the 34th frame, the shortest note kept). A note let go before that is named in the progress line ("E5 too short to keep", in display pitch) until the next note is kept.

**The chart's runs**: Compare... picks presets with captures and, for a preset with two or more sessions with captures, single sessions; up to seven (the palette), refused beyond rather than cycling colours, since two runs in one colour and marker cannot be told apart. With nothing picked the chart is the loaded preset with the session being captured merged in by date, exactly as the save merges it, so the chart during a run shows what the file will hold. The title is the preset's name for one run and nothing for a comparison (the legend names the runs). Export is one dialog with PNG and PDF types, told apart by the extension of the name typed; the PNG at twice the chart's size.

**The window was too narrow for the strip all along.** Measured with the app's own start-up size: the window opens at 655 px in English (640 before this round), the Toner's control strip asked 829 px, and pack, packing the right column last, left the Capture button unmapped: off the page. The Toner's terms said "Run it in full screen", which is why nobody reported it. Now the tab shows by default, so `_fit_window_to_tabs`, which already widened the window for the Tooling tab's buttons, counts the Analyzer's strip too: the window opens at about 933 px in English and 1063 in German (the strip asks 909 and 1039: the HARMONICS switch added 77, "guided" a few). This is the one change in this round that reaches users who never open the tab, and it is flagged for Matt; the alternative, a two-row strip, is a layout he has not asked for. Gated in `test_analyzer_tab` (the Capture button on the page, in English and in a German child).

**Required fields**: horn type (the combo, always set), make, model, player, mouthpiece; the mic fields only while the switch is on, in the form and at the "Mic Type Required" stop before a session starts. The seeded test preset without a mic captures an intonation run and is refused a harmonic one.

**The migration writes nothing at startup.** Its first version saved the flag the moment it ran; the full run's `test_adhesive_ring_upgrade` failed twice on that (an untouched pre-feature folder had its settings rewritten by a plain build and by `--selftest`), which is the standing rule that building the app is side-effect free. Now the migration changes the dict only and the flag reaches the disk with the next regular save (exit, Feature Set, a dialog's OK). A crash before any save re-runs it, to the same result.

**Suites**: `test_analyzer_tab` (guarded; 14 checks: the migration from each starting state once only, the tab as built on a never-unlocked profile, Feature Set, the switch and the terms stood in both ways, required fields both ways, a free run and a guided run through the synthetic source (the guided one with the countdown and recording constants shortened), the readout frame by frame, Compare, Export PNG and PDF, the Settings tick flipping the axis, the tour's stop, a German child for fit); `test_toner_live` turns the switch on for its spectrum checks; `test_user_guide`, `test_release_1_9` (Toner defaults to True) and `test_release_2_86` ("Analyzer" not offered on the Intel Mac) re-pinned. Against the round-1 tree the new suite fails at import (no `intonation_chart`, no `migrate_analyzer_tab`); planted breaks (the readout never green, the migration skipped, the mic always required, the strip left out of the fit rule, accepted terms not saved, the chart not redrawn after a capture) each fail their check and nothing else; the table is in the round-2 report.

**Still open from round 1** (not in this round, for Matt): `save_tone_presets` leaves `<file>.tmp` behind when the target is a directory or the dump fails; `analyze_audio_file`'s progress total is one short and its callback fires only every 200 windows; `level_dbfs` and the WAV stretches on captures.
