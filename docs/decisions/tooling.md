# Tooling tab: decisions and history

This file holds the why and the history behind the rules in the CLAUDE files, and the full detail they summarise: what was tried, measured, rejected and decided, with dates and the user's own words. The paragraphs were moved here verbatim from the CLAUDE files on 2026-11-10 (HEAD 01071f5); each section names where it came from. Add new decisions to the matching section, dated.

## Tooling Tab

*Moved from CLAUDE-engines.md, section "Engines: Pad Generation, G-code, Tuner, Tooling > Tooling Tab" (2026-11-10).*

Accordion-style UI with die insert and die holder SVG/G-code generation. Small dies ≤39.5mm (50mm OD), large ≥40mm (70mm OD). Die holders 85mm OD; user picks 5-layer (solid + magnet + 2× pin + ring) or 6-layer (solid + magnet + 3× pin + ring), with magnet hole 6.5mm, pin holes 3.5mm. Variant is Small / Large / Both, where Both = two complete independent holders (one of each size) nested onto the same sheet — the layers are cemented together permanently, so there's no convertible-holder concept. User defines sheet size (W × H + in/mm) like Die Inserts; engine raises `ValueError` if pieces don't fit. Helpers `_holder_pieces_for(variant, layer_count)`, `_pack_holder_grid(...)`, and `_min_holder_sheet(...)` live in `svg_engine.py` and are imported by `gcode_engine.py` so SVG and G-code stay aligned. Canvas widgets need explicit handling in the resonance theme walker.

### Section buttons

**Section buttons.** Seven buttons, three to a row, all one width: 22 characters where 22 characters hold every label, else as many as the longest label asks for (`create_tooling_tab` reads each button's natural requested width, which Tk computes when the button is configured on every port, then raises the character width until a probe asks for at least the widest). **"One width" is a property of the layout, not of seven requests (2026-11-09, round 3):** the seven sit in one grid whose three columns share a `uniform` group, each button `sticky="ew"`, row 3's single button in column 0 of the same group, so every button is stretched to the widest cell whatever a port asks for any one of them; the character width is the cells' minimum. Why: packed into three row frames, each button was as wide as its own request, and CI's two Macs (`2ee3267`) gave the seven two different widths in every language — en [194, 234], es [221, 261], de [260, 270] on Apple Silicon — with no section open, a gap that depended on the labels; nobody here has a Mac to see why. The gate (`test_release_3_0`, `section_button_checks`) asserts the layout in the grid's own terms too — each button's column in the `tooling-sections` uniform group, each button `sticky` east and west, read from Tk in the child — because on Windows the pixels come out the same with or without them and only Aqua would show the difference; and it carries the evidence in its failure message (each button's text, relief, characters, requested and actual width, row and column, whether a section was open) and measures a third time with a section open, printing what the port asks for the sunken button against the raised ones on every run. Proved on Windows with the Aqua case planted (one button given `relief="sunken", padx=25` at the same character width): the grid layout passes, all seven stretched to the planted request and the window fit to it; the old row-frame layout fails in every language with that button named in the evidence. *Open question, left as it is on purpose:* on Aqua a classic `tk.Button` is drawn natively only in its default look; the active section's `relief="sunken"` is probably drawn as Tk's generic bevel there, differently padded. If it asks for more than the raised ones, the uniform columns all grow by that much when a section is opened; the open-section line in the CI log will say. Not changed without asking. At a fixed 22, "Geschwindigkeits- und Leistungstest" and "Polsterpressen-Distanzplättchen" (German, seen on screen 2026-11-09), "Prueba de velocidad y potencia" and "Espaciadores de prensa de zapatillas" (Spanish) were cut off at both ends, and so was English "Pad Press Spacers" with Linux's wider font (CI, the same day). **The window is never narrower than the Tooling tab's content**: `_fit_window_to_tabs` takes the larger of the tab row's need and `tooling_tab_frame.winfo_reqwidth()` plus the notebook's chrome. In Aqua a 22-character button is about 228 px, so three to a row need about 720 px, and a Mac or Linux window with fewer tabs shown stayed at the 640 px it starts at and squeezed the buttons, in English, in v2.9 (with all seven tabs the tab row happened to widen it enough); Windows never showed it because 22 characters fit 640 there. Only the Tooling tab is counted, not the notebook's whole request: the library and audio tabs ask for 850 px and more on every platform and are built to live in less, and on Windows the window would otherwise jump from 640 to 853 px for everyone. **The chrome is measured, not assumed (round 4, same day).** The room between the window's width and a page's (the pack padx round the notebook, its border and inset) was the constant `TOOLING_CONTENT_MARGIN_PX` = 24; on Windows it is 14 px, on Aqua more, and the Apple Silicon picture of `c671b33` (CI run 42719069476, every gate green) showed the result: the window 15 px wider than the released build's and the third column of buttons still running past the page's right edge, clipped there, because the uniform grid had made every cell as wide as Aqua's widest request and the constant undershot the chrome. `_notebook_page_chrome_px()` reads `root.winfo_width() - <the mapped page>.winfo_width()` (the inset is the same for every page, so the Pad Maker at startup serves) **once and keeps it**: right after a `geometry()` call the window's width is already the new one while the page is still laid out for the old, so a fresh reading there is meaningless (found on Windows with Aqua's chrome planted: the first version read 640 − 653, fell back to the constant and left the planted page 100 px short); the padding and border never change while the app runs, so one credible reading (0 < chrome ≤ `PAGE_CHROME_MAX_PX`) is the chrome. The constant is only the fallback before that. Gated per language in a child process, with the default tabs and with the fewest Feature Set allows, in terms of the rule and not pixel counts: one width, no label narrower than its button, the window at least the content's width, and — what let the clipping through — every button's right edge inside the Tooling PAGE's own visible area (`winfo_rootx` + `winfo_width` against the page's), the page at least as wide as the selector grid asks (`buttons_on_the_page`, on all three measurements). Proved on Windows with Aqua's chrome planted (`notebook.pack(padx=60)`): the measured fit passes, the constant fit fails in every language, naming the page's visible area.

### Die inserts nest in rows from the bottom-left corner (2026-11-09)

**Die inserts nest in rows from the bottom-left corner (2026-11-09).** `svg_engine.nest_edge_bias(material, settings)` is the one place a nest's edge bias is read, and both nesters call it: pads get the Pad Maker's Edge Bias, `die_ring` always gets `DIE_NEST_EDGE_BIAS`, "s": the bottom row left to right, then the next row up, largest first. The first ring lands 1 mm from the left edge and 1 mm from the bottom, the G-code origin and the corner the head is jogged to for Frame & Cut. Tooling passes the shared settings dict, so until then dies inherited whatever the Pad Maker was set to, and its default, "center", puts the first and largest ring in the middle of the sheet: seven dies (30 to 44) on a 130 x 130 mm sheet placed 1 and took three sheets (by rows: 3 then 4), and a job of two 50 mm rings and one 70 mm ring was refused as not fitting when it fits. Deciding it where the bias is read means the SVG, the G-code, Frame & Cut, the fit check and Scrap Mode all nest one layout, and nothing writes to the shared settings: the Pad Maker's Edge Bias is untouched in memory and on disk. Die output under any Edge Bias equals what the old code wrote with Edge Bias set to "s" (checked on 48 cases, 512 files, under five bias values). Pads, adhesive rings and every other nest are byte-identical; Die Holders (a grid pack) never read the bias. *Why rows and not the corner scan ("sw"), which also starts in that corner.* Measured on the released engine, sheets needed in Scrap Mode: over 24 list-and-sheet cases 146 from the centre, 125 from the corner scan, 117 to 118 by rows ("off", "s", "w"); over 30 cases, independently, 187 / 152 / 144 ("s"). The corner scan places smallest first, so a mixed list leaves its 70 mm rings for the last sheets: the full set 7 to 60 on a 12 x 12 in sheet is 6 sheets from the corner and 5 by rows (first sheet 30 small rings against 18 rings of which 16 large). Rows are not better everywhere: nine 50 mm rings on 160 x 160 mm are 9 from the corner (a square grid) and 8 by rows (the second row nestles between the first and the third no longer fits). "s" was chosen over "w" (141 sheets) because "s" starts exactly in the corner; "w" leaves 1.8 mm at the bottom. The rule is the one constant.

### Labeled Zones never reach dies (2026-11-09)

**Labeled Zones never reach dies (2026-11-09).** `svg_engine.ZONE_FREE_MATERIALS` (adhesive rings, `die_ring`) nest plainly in `nest_with_zones` whatever `zone_labels_enabled` says. Zones is a Pad Maker setting and the die generators nest plainly, but the die *fit check* (`can_all_pads_fit`) came through `nest_with_zones` with the shared settings: with zones on for pads it grouped the 7 to 12.5 mm die sizes (50 mm rings) and refused jobs that fit (nine dies 7 to 11 on 160 x 190 mm: refused, where the nest places all nine). Gated in `test_release_3_0`, engine and buttons: every die path gives exactly what it gives with zones off. *Which Pad Maker settings can still move a Tooling output, measured key by key (2026-11-09):* `compatibility_mode` (the unit style of every Tooling SVG), `gcode_return_speed` (every G-code footer), `filled_overscan_enabled` / `filled_overscan_mm` (filled engraving in die and crescent G-code), the pad materials' `gcode_settings` when a Tooling test is run on that material, and the `die_*` entries of `layer_colors`. All by design: one export style, one return move, one overscan, one colour table. Nothing else: not `edge_bias`, not the zones, not units, sheet sizes, sizing rules, darts, engraving placement or hole settings. Spacing is the nesters' 1 mm default argument, not a setting.

### G-code and Frame & Cut (2026-11-09)

*G-code and Frame & Cut (2026-11-09).* The section used to be SVG only, on the reasoning that LightBurn handles kerf, layers and material profiles better than we would and the organizer is a one-and-done part. That stopped being the right call once the aim became that nobody needs LightBurn. Matt: "building a gcode path for what needs it sounds like the right call." The section now has a material choice (basswood first, acrylic, cork; `tooling_settings.organizer_material`, stored as the key), a sheet size, Generate G-code and Frame & Cut, and its text offers G-code first and LightBurn as the other way.

- *The reader* (`svg_engine.read_die_organizer_drawing`) is no more than the drawings need, and **fails loudly on anything else** (`OrganizerDrawingError`): `rect` (with or without `rx`), `circle` and `ellipse`, each a direct child of `<svg>`, each placed by `translate(x,y)` or by a `matrix(...)` that is a pure rotation plus a move. A path, group, line, scale, skew, mirror, unit suffix, a missing viewBox, or a drawing without exactly one rectangle that is the whole plate raises, so a replacement drawing is never half read and mis-cut. The upper plate is 112 rects, 4 circles and 1 ellipse; **three of them are turned with a `matrix()`** (the oval and two 60.6 x 15.5 rectangles, about 89 and 90.4 degrees), which is why the reader takes a rotation and not just translate. The lower is the plate and 4 holes. To change the design, drop in a replacement SVG; if it uses anything else the G-code button says so.

- *Toolpaths* (`die_organizer_toolpaths`, `organizer_shape_path`): every element is a cut. Each path is the shape's exact parallel curve: openings half a kerf inward, the plate's own edge half a kerf outward, so slots, holes and plate come out at drawn size. A rectangle keeps its corner centres and changes its radius (a square slot stays square going inward); a circle changes radius and is built quarter by quarter so its four extreme points are on the path; the oval is moved along its normals, since a grown ellipse is not an ellipse. Corners are true arcs linearized to `TOOLPATH_ARC_TOLERANCE_MM` (0.002 mm of sag). A slot or hole too small for the kerf raises.

- *G-code* (`gcode_engine.generate_die_organizer_gcode`): all openings first in the drawing's order (layer C01), the edge last (C02), so the plate stays in the sheet until its slots are done. Cut speed, power, passes, air and kerf come from the chosen material; a material with no cut speed or power is refused. The plate sits `ORGANIZER_MARGIN_MM` (2) in from the sheet's bottom-left corner, which is the origin: drawing y becomes margin + 330 - y. The smallest sheet is 234 x 334 mm, upright as drawn (no auto-rotation); a smaller one is refused by the tab in the user's language before the save dialog, and by the engine as a backstop.

- *Kerf refusals are typed and translated (2026-11-09).* `svg_engine.OrganizerKerfError` (an `OrganizerDrawingError`) carries the kerf and the opening it bridges (`opening`: "54 x 3.175" for a slot or an oval, "6.5" for a hole, None for a negative kerf); `ToolingTabMixin._organizer_kerf_message` turns it into the user's language, the way the crescent's kerf refusals have one, for Generate G-code and Frame & Cut alike. Before, the engine's English reached the user. The tab's own sheet check refuses a sheet too small in either direction before the save dialog; the engine's check is the backstop.

- Tests: `tools/test_die_organizer_gcode.py` (15). The key one reads the SVG **with regexes written in the test**, works out where each element's bounding box must land after kerf and the Y flip (turned rectangles and the oval included), and requires one closed cut per element there. Also inner before outer, the 230 x 330 + kerf box, true-arc corners, the oval being a parallel curve and not a scaled one (with a control that a scaled oval fails), the reader's fourteen refusals, cut settings, and the real section.

### Pad Press Spacers

**Pad Press Spacers**: bundled 3D-printable STL files (`pad_press_spacers/*.stl`) copied byte-for-byte to the user's chosen path via `ToolingTabMixin._save_pad_spacer_stl`. ### Tonehole Crescent (2026-10-14)

**Tonehole Crescent (2026-10-14)**: a crescent glued into the *mouthpiece* side of a tonehole covers part of its open area and flattens that note. Matt's case: a Selmer Super tenor whose bell is genuinely too short, so B and Bb need help. He notes crescents are rarely needed and sometimes overused, so the section's copy stays factual rather than promotional. Inputs: tonehole ID, **% of open area to cover** (area, not diameter: it's the acoustic quantity, and the readout shows the widest point in mm for checking with calipers), and an inner-edge curve slider. Outputs: SVG (one cut path made of two true arcs, no kerf compensation since the SVG does not know the material), a binary STL extruded to a print thickness, and since 2026-11-09 G-code cut from a chosen material with its kerf compensated (below). All geometry lives in `svg_engine.py` (`tonehole_crescent_geometry` and friends) and is shared by the preview canvas, the SVG and the STL.

- *Geometry*: the outer edge is the tonehole circle; the inner edge is an arc of a second circle slid in from the far side, solved by bisection on the circle–circle overlap area until the uncovered lens is `(1 − p)` of the tonehole. Mouthpiece side is −y in SVG/preview coordinates and +y in the STL.

- *The slider* (0–100, stored as `tooling_settings.crescent_curve`) sets inner-edge curvature relative to the tonehole's. **75 = the classic crescent** (inner radius = tonehole radius, `CRESCENT_CURVE_STANDARD`), 0 = curvature 0.2 (nearly a flat D). Rounder than standard is measured as a *fraction of the way* toward curvature `1/√(1−p)` and stops halfway, because that's where the inner circle becomes as small as the opening it leaves and the horns close into a ring. That limit moves with the percentage, so a fixed curvature range would be impossible at the small percentages that are the common case (at 10% the whole rounder-than-standard window is under 5% of curvature). Matt asked for "between A and C, a bit more on each side" and approved the prototype grid on 2026-10-14.

- *SVG precision*: the path prints 8 decimals, not the usual 4. On a small tonehole at a low percentage the horns sit within 1e-4 mm of a diameter apart, where the arc centre a reader rebuilds from the endpoints moves ~250× as far as they do; 4 decimals collapsed both arcs into the same semicircle (caught by the test grid at 8 mm / 0.5%).

- *STL*: the cap is a strip between the two edges matched point for point (degenerate triangle at each horn dropped), plus a wall quad per outline segment. Watertight and wound outward; header must not start with `solid`.

- *Several at once*: a list (`tooling_settings.crescent_list`, entries `{tonehole_d, percent, curve, qty}`). Add to list takes the fields plus a quantity; **Generate makes the list when it has entries and the crescent in the fields only when it's empty**, and a hint line under the list says which, because the fields keep showing whatever was typed last. `layout_tonehole_crescents` shelf-packs the parts' bounding boxes in list order (rows about as wide as the layout is tall; copies stay adjacent). The SVG and STL generators both take the entry list. **With more than one entry the SVG engraves each part's 1-based list number centred under it, on the scrap**, because a B and a Bb crescent a couple of mm apart look alike once cut and a part a few mm wide has no room for a number (the Labeled Zones reasoning). Copies of a single entry aren't numbered, and the STL never is, since a print has no engrave layer. Saved entries go through `_clean_crescent_entry` on load, so a hand-edited or stale list drops bad rows instead of failing the tab. Matt asked for the list on 2026-10-14, choosing it over "copies of one" and "percentage test set", which it covers.

- *G-code and Frame & Cut (2026-11-09)*: the section has a material choice (`_CRESCENT_MATERIALS`, cork first and the default; `tooling_settings.crescent_material`), Generate G-code and Frame & Cut. Same list-or-fields rule, same layout and numbering rule as the SVG (`generate_tonehole_crescent_gcode` calls `layout_tonehole_crescents`). The SVG still has no kerf compensation because it does not know the material; **the G-code does and compensates exactly**. `tonehole_crescent_toolpath(geom, kerf)` is the outline's parallel curve: outer circle radius plus kerf/2, inner circle radius minus kerf/2 (same centres), and each horn wrapped by an arc of radius kerf/2 centred on the horn's tip. The tip is then exactly half a kerf from the path on both sides, so the part comes out at the designed outline, horns included. With kerf 0 the path is the outline (cork ships with kerf 0, which reproduces the crescent Matt cut). **The two offset circles are not run on to where they cross** (a mitre), which was the first plan: the part would be the same, but on a thin crescent the edges meet at a shallow angle and the crossing is far away, 6.44 mm past the horn on a 43 mm tonehole at 2 % with a 0.2 kerf (2.55 at 5 %, 1.27 at 10 %, 0.63 at 20 %), through the number engraved under the part and into its neighbour. The wrap never leaves the design by more than kerf/2, so the SVG's layout needs no change. Refusals (`CrescentKerfError`, turned into a translated message by the tab): a kerf outside 0 to `CRESCENT_MAX_KERF_MM` (1.0), or a horn gap narrower than the kerf, which the beam would bridge. The horns are never closer than 0.66 x the tonehole diameter (75 %, roundest edge), so that second refusal needs a tonehole under 1.5 mm: a guard nobody will meet. **A thin crescent is never refused for being thin**: compensation only moves the path away from the part. Numbers are engraved first (layer C03) with the material's engraving settings, then one closed cut per crescent (C02); a material with no engraving settings gets no numbers (see "Cork"). Y is flipped with the layout's height, so the mouthpiece side is up in the SVG and up (+Y) on the bed. Tests: `tools/test_tonehole_crescent_gcode.py` (15): over 175 crescents x three kerfs, every path point is half a kerf from the design outline (measured against the two design arcs in the test, not with the app's offset code), the path's area is the design's plus perimeter x kerf/2 plus pi (kerf/2)^2, and every design point including the two tips is half a kerf inside it; kerf 0 is the outline; parity with the SVG's own arcs after the Y flip; the list and numbering rule; cork as shipped; the real section.

- Tests: `tools/test_tonehole_crescent.py` (area exact on a 224-case grid, monotonic slider, horns never close, SVG arc flags checked with an independent SVG-spec arc converter that exercises both large-arc values on both arcs, STL watertight with volume = area × thickness, list layout without overlaps and with each number under its own part, one STL shell per part, UI preview/validation/persistence/list), plus SVG, STL and a numbered list SVG through the real buttons in `test_tooling_e2e`.

### Speed & Power Test (v2.40+, beta)

**Speed & Power Test (v2.40+, beta)**: laser-settings calibration tool. Generates a sheet of small test discs at user-defined sweeps of speed / power / passes / air-assist; each disc gets a 2-digit ID and a `legend.txt` mapping IDs to parameters. Engine entry point `generate_feeds_speeds_test_gcode` in `gcode_engine.py`. Matrix expansion via `build_feeds_speeds_matrix` and grid packing via `_grid_pack_discs` (both in `svg_engine.py`), wired through `ToolingTabMixin._prepare_feeds_speeds_pieces`. Preview window `SpeedPowerTestPreview` in `ui_dialogs.py` shows the layout (color-coded by air state when "Also test with air off" is on) before the file dialog; toggleable via the "Preview before saving" checkbox. G-code only — per-disc parameters can't survive an SVG round-trip, so the SVG path was deliberately not added. Engraving feed/power are exposed as editable fields so the labels stay legible when the cut settings are still unknown (the whole point of the tool).

### Inner diameter / washer mode (v2.62)

*Inner diameter / washer mode (v2.62)*: an optional "Hole diameter" field (0 = solid disc, the default and historical behavior) turns each test piece into a washer/ring for shim stock (e.g. flute padding shims). When set, `generate_feeds_speeds_test_gcode` cuts the inner hole FIRST (so the part stays anchored to the sheet while the hole is cut) then the outer perimeter, both in the same per-disc `C{id}` layer at that disc's speed/power/passes. Because the center is now cut away, the ID label moves into the lower ring: the shared pure helper `feeds_speeds_label_geometry(diameter, inner_diameter)` in `svg_engine.py` returns `(label_dy_mm, font_size_mm)` — `dy=0`/historical font for a solid disc, mid-annulus offset + ring-width-auto-fit font (floored at `FEEDS_SPEEDS_LABEL_MIN_FONT_MM`) for a washer. Both the G-code engraving and the `SpeedPowerTestPreview` canvas call this helper so the drawn label matches the cut. `feeds_speeds_ring_fits_label` backs a non-blocking UI warning when the ring is too thin to engrave a legible ID. Validation refuses a hole ≥ the disc diameter.

### Sheet size is a soft target, not a hard cap

*Sheet size is a soft target, not a hard cap*: if the matrix doesn't fit the entered sheet, `_prepare_feeds_speeds_pieces` grows the sheet (each axis only as far as needed via `_min_feeds_speeds_sheet`) and proceeds instead of erroring — the layout preview shows the enlarged sheet before the file dialog, so nothing happens blind. The live fit indicator reads "→ sheet will grow to fit" rather than a hard failure.

Tests in `tools/test_feeds_speeds_tester.py` cover the label geometry, the holed-cut G-code (inner-before-outer, ring label drop), and the sheet auto-grow path.

### Material

*Material.* Framing power and the cut dialog's title use acrylic for dies and holders (they always cut from `gcode_settings['acrylic']`) and the selected material for the Die Organizer, the Kerf Test, the Speed & Power Test and the Tonehole Crescent. Framing is the bounding box of the job's G-code (`extract_gcode_bbox`, which includes the return to X0 Y0, so the box starts at the jogged corner), at `get_framing_power_s(material)`, M4 as always.

### Material names in a translated app (bug found here, fixed)

*Material names in a translated app (bug found here, fixed).* The Kerf and Speed & Power dropdowns list translated names, and the settings key was the shown name lower-cased. That is only right in English: in German "Filz" looked up `gcode_settings['filz']`, found nothing, and the kerf test with "Use existing G-code settings" ticked ran at the hard-coded fallback, 180 mm/min at 100 %, instead of the user's felt settings. It had shipped for as long as those dropdowns have been translated, for file export too. `ToolingTabMixin._tooling_material_key` now maps the shown name back (translated first, then English, then the old lower-casing), `_tooling_material_label` goes the other way, and every Tooling material dropdown uses them. The suggested file names still come from the shown name, so they did not change in any language.

### Speed & Power legend

*Speed & Power legend.* The legend is the only record of which disc was cut at which settings. Frame & Cut asks where to save it (default `<name>_<material>_legend.txt`) after the preview and before the laser is touched, writes it with the same `_write_feeds_speeds_legend` (which takes an optional `legend_path` so the name the user typed is the name written), and a cancelled prompt cancels the run. `SpeedPowerTestPreview` takes a `proceed_label`, and Frame & Cut passes "Continue →" because nothing is saved. The export's legend is headed with the G-code file it belongs to; a Frame & Cut run has no file, so its header says "sent to the laser with Frame & Cut" and the date and time (until 2026-11-09 it named the legend file itself).

### Die Scrap Mode

*Die Scrap Mode.* One sheet per click. `_die_scrap_begin(folder_title)` is the front half shared by Generate SVG, Generate G-code and Frame & Cut (start or continue the session, nest what fits), and it counts nothing. The file exports count the sheet when the file is written, as before. Frame & Cut counts it in the job's `after_cut`, and only when the cut ended as "complete": cancelled at the jog step, framing stopped, cut stopped or errored, or no connection all leave the session exactly as it was and the same dies are offered again. A session that Frame & Cut starts has no folder (it writes nothing); a file export joining it asks for the folder then, once. The Pad Maker's rule, see `_frame_cut_scrap_advance`. The first click starts the session and opens its window before the jog step; cancelling there leaves both, with nothing cut and every die still offered, as the Pad Maker's own scrap session does after a cancelled first run (left so on purpose, 2026-11-09; pinned).

*Still no G-code:* on the Pad Maker the Exact Size material (SVG only, it has no laser settings). The Pad Press Spacers are 3D prints. Every other output can be cut by this app.

### Cork, and "engraving not set" (2026-11-09)

**Cork, and "engraving not set" (2026-11-09)**: Matt: "tonehole crescents are usually cork. we do not have that as a material yet". `cork` is a full G-code material (every key in `GCODE_PRESET_KEYS`; the seventh entry in `GCODE_PRESET_MATERIALS`, so the first-launch backfill gives every user a `cork` Default preset) and a **Tooling material only** (`config.TOOLING_GCODE_MATERIALS` = acrylic, basswood, cork): it is in the Tooling settings dialog, the Kerf Test and Speed & Power Test lists, Framing Power and the Tonehole Crescent's material choice (its default), and not on the Pad Maker or in the Pad Maker's G-code Settings.

- *The cut default is a tested value*: 1000 mm/min at 30 %, one pass, air on, on 3/32 in (2.4 mm) sheet cork on a 40 W Falcon. It is what Matt cut a 43 mm, 20 % crescent with on 2026-10-14 (his file `crescent_43mm_20pct.gcode`, LightBurn output, one layer `Cut @ 1000 mm/min, 30% power`, M4, M8), in his words "it was perfect for 3/32 cork". About 0.30 J per mm of cut per mm of thickness. Two derived proposals came first (1600 mm/min at 50 % for an assumed 1.6 mm sheet, then 1050 mm/min at 50 % for 2.4 mm, scaled from the 3 mm basswood default at half the density); the second would have been about 55 % hotter than what actually worked.

- *The kerf is not measured.* 0.0 reproduces that crescent: its path encloses 290.45 mm2 and 20 % of a 43 mm tonehole is 290.44 mm2, so it was cut on the design line. No text may call the kerf tested; the dialog note and the guide point at Tooling > Kerf Test.

- *The engraving is not set, on purpose.* Matt: "leave the engraving setting for cork at 0/0. don't want a guess in there." **A speed or a power of 0 means "not set"** (`config.engraving_is_set`), for any material. No generator may write an `F0` move (Grbl rejects a zero feed) or trace an engraving at `S0`, so the three Tooling generators that engrave with the chosen material leave the engraving out and still write every cut: the crescent's list numbers, the Kerf Test's title and sizes, the Speed & Power Test's disc IDs. **Never silently**: `ToolingTabMixin._engraving_not_set_notice` gives one plain line, which goes in the Done box for a file and is asked (OK / Cancel, `_confirm_engraving_skipped`) before a Frame & Cut run; for a crescent list it says the parts will not be numbered and where to set it. The Speed & Power Test pre-fills its Engraving fields from the material, so with cork they read 0 and 0 (the power used to be floored to 1 %; not for a material with none). **0 there is accepted, not refused**: the test runs, the IDs are left off, and the notice says so. Refusing would only push the user to type a guess, the thing Matt did not want; negative or over 100 % is still a typo and refused. The pad engines and the die and holder generators are untouched (their engraving output is byte-identical: the 48-case hash and the 48-click export record both match the committed code).

- Tests: `tools/test_cork_material.py` (12): the defaults; a settings folder saved before this change gains cork and loses nothing, and a v2.9 folder gains adhesive rings and cork (in a child process, since a profile is fixed per process); where cork is and is not offered; the settings dialog taking 0/0; the Kerf and Speed & Power tests with cork (cuts all there, no engraving layer, no F0, the notice, real values bringing it back, Frame & Cut asking first and Cancel running nothing); other materials untouched.

### The G-code file line (2026-11-09)

**The G-code file line (2026-11-09)**: every message box shown after G-code is written to a file ends with one line, "Send this file to the laser as it is. For LightBurn, use Generate SVG." A user had imported die insert G-code into LightBurn, which drops the speeds and powers the file carries, and was confused by the result. Matt: "is there a dialog when the user generates gcode? maybe we can put something in there (this is not for lightburn)", and "short message for gcode is best". The sentence is written once, in `ui_dialogs.gcode_file_note()`, and translated once per catalog. It is on the Pad Maker's three G-code success wordings and its two scrap-mode G-code boxes (the continue dialog takes a fourth **positional** flag, because several suites stand in for it with a `lambda *args`), and on Tooling's Die Inserts (standard and both scrap boxes), Die Holders, Die Organizer, Kerf Test, Speed & Power Test and Tonehole Crescent boxes. Never on an SVG or STL box, and never on Frame & Cut, which writes no file. The why is in the user guide ("G-code or SVG?"), not in the box. **The Kerf Test's G-code export gained a Done box for this**: it used to show only its measuring steps, which stop appearing once "Don't show this again" is ticked, and then the export said nothing at all. Tests: `tools/test_gcode_file_note.py` (7) clicks every Generate button that ends in a box and requires the line on every G-code one and on no other.
