# Testing and CI: decisions and history

This file holds the why and the history behind the rules in the CLAUDE files, and the full detail they summarise: what was tried, measured, rejected and decided, with dates and the user's own words. The paragraphs were moved here verbatim from the CLAUDE files on 2026-11-10 (HEAD 01071f5); each section names where it came from. Add new decisions to the matching section, dated.

## Testing

*Moved from CLAUDE.md, section "CLAUDE.md > Running the Application > Testing" (2026-11-10).*

### SVG↔G-code parity

**SVG↔G-code parity**: `test_engine_parity` pins the contract that the SVG/preview output and the G-code output describe the same physical object (dart wave shape, engraving label placement, engine purity). The two engines render independently and have drifted before — when touching shared geometry (wave math, placement formulas, Y-flip), run this suite and extend it for any new shared shape.

### What CI runs (since 2026-10-06)

**What CI runs (since 2026-10-06).** Three jobs on every push to `beta` or `main`: `lint` (ruff), `test` (every suite via `run_tests.py` on **Windows, macOS Apple Silicon, macOS Intel and Linux** — Windows and macOS runners have a display so the GUI suites run for real; Linux runs under `xvfb-run`; full `requirements.txt` is installed so the OpenCV and pyserial suites run instead of self-skipping), and `build`, which `needs: [lint, test]` — nothing is built or attached to a release unless every test job passed (added 2026-10-06 after the first release cut showed the test job ran *beside* the build, not before it). Before this, CI ran no tests at all, and the macOS code paths (`IS_MACOS` theming, `::tk::mac::Quit`, canvas-only tuner, the no-numpy Intel build) had never been executed anywhere — nobody on the project owns a Mac. The macOS test job is the only place they run. The repo is public, so Actions minutes are free; that is why the test job runs on every push rather than only on `main`.

### Dependencies are locked (since v2.86)

**Dependencies are locked (since v2.86).** Every CI install is `pip install --require-hashes -r locks/<set>.txt`: `full.txt` (universal: Windows, macOS, Linux; `requirements.txt` + `requirements-dev.txt`), `intel-mac-test.txt`, `intel-mac-build.txt` (the Intel build bundles exactly svgwrite + numpy) and `lint.txt` (ruff, uv). All are produced by `python tools/update_locks.py` (uv, resolved for CI's Python 3.11, a hash per file); edit `requirements*.txt` or `locks/*.in` and re-run it. The lint job re-resolves and fails on any diff, so the locks can't drift from the requirements. A new version reaches a build only through a commit that changes a lock: `.github/workflows/lock-refresh.yml` runs `--upgrade` on the 1st of each month, pushes `deps/lock-refresh-YYYY-MM`, starts Build Releases on it and opens a PR into `beta` (the PR needs Settings > Actions > "Allow GitHub Actions to create and approve pull requests"; without it the job summary links the one-click compare page). **Why:** `requirements.txt` sets floors only, and until v2.86 every build took whatever was newest that day. OpenCV 5.0 reached PyPI on 2026-07-02 and went into every build after it with no commit saying so; v2.7 through v2.85 shipped it, and the calibration dialog, written against OpenCV 4's array shapes, was broken in all of them (see Portability notes). The first locks were resolved with `--exclude-newer 2026-10-14T18:17:05Z` and checked job by job against v2.85's install log: identical for Python 3.11. `full.txt` also carries a numpy line for Python >= 3.12 (numpy 2.5 dropped 3.11) — CI never uses it. The app logs the versions it is actually running at startup (`config.log_runtime_versions`), so a user's `app.log` answers "which OpenCV is in this build" without the CI logs, which expire.

### The Intel Mac is tested as it ships

**The Intel Mac is tested as it ships.** The `test` matrix includes `macos-15-intel` with `svgwrite numpy pillow babel` installed — numpy but no sounddevice, exactly the Intel build's dependency set — running `run_tests.py --allow-missing sounddevice`, which counts a suite that dies on one of those imports as skipped (reported, not hidden). Everything else runs for real on x86 macOS Tk. Until 2026-10-06 that build had no numpy, and the first Intel run measured the pure-Python nest at **774 s (`test_zone_labels`), 293 s and 260 s (the two scrap suites)** — the wait an Intel user was living with on a big fill; Matt's answer was to ship numpy in the Intel build ("include numpy for them"), after which `test_zone_labels` took 7.7 s there. The `_HAS_NUMPY` fallback now runs only in the parity suites' reference implementations and in source checkouts without numpy; no shipped build lacks it. The audio-tab suites (`test_tuner_canvas`, `test_toner_live`) self-skip when `AUDIO_AVAILABLE` is False, because that build has no audio stack. **Since 2026-10-15 the Intel build doesn't offer what it can't run** (Matt: "let's just not support the features on an intel mac that it cannot use. they are getting rare"): `main.audio_supported()` is False on a Mac without sounddevice, so the Tuner and Toner tabs are hidden and left out of Feature Set (the tour skips them — selecting a hidden ttk tab would show it); `main.machine_supported()` is False without pyserial, so the Machine menu toggle isn't offered and an old setting that enabled it is ignored. Windows/Linux keep their "not available" audio panels, because there it's a missing library the user can install. Gated in `test_release_2_86`.

### What the new coverage found on its first runs (2026-10-06 evening)

**What the new coverage found on its first runs (2026-10-06 evening):** the no-mic tuner stop showed dark wheels and *no message* — `_tuner_build_wheels_canvas` starts with `canvas.delete("all")`, which wiped the "Audio error" text on the next resize, so a user with no (or a denied) microphone saw a dead tuner with no explanation; the toner's `_toner_build_spectrum_bars` did the same. Both tabs now keep an `_*_error_state` and redraw it after a rebuild; gated in `test_tuner_canvas` (pass 0) and `test_toner_live`. The German tour showed the pad preview's material names and legend hard-coded in English (`PadPreviewWindow.LABELS`, now `_()`-wrapped). And the "dark" Mac tour came back light: `defaults write -g AppleInterfaceStyle Dark` does not change a running login session, so the tour now forces its windows dark through Tk (`::tk::unsupported::MacWindowStyle appearance … darkaqua`, `--appearance dark`) and writes the *measured* mean brightness into `tour-done.txt`, so the artifact says which mode it really is. One Linux build job failed at "Set up job" with no log — runner infrastructure, not code; a re-run is the fix for that one. Second-round findings from the same pictures: the Mac runner *has* a silent input device, so the "tuner-no-mic" stop shows a running tuner with the pilot lit rather than the error overlay — the no-mic error itself is gated in `test_tuner_canvas` pass 0, the stop stays as "what you see before you play"; with the per-window appearance switch the main window renders dark but dialogs stay light (each Toplevel has its own appearance), so the CI dark step also tries the session-wide `osascript` appearance switch — check `tour-done.txt`'s measured brightness and the dialog shots to see which took; and the library dropdowns' "All Libraries" was untranslated because the code compares against the literal — every use is now `_("All Libraries")`, which keeps the comparisons consistent at runtime, and a stored English sentinel from an older config simply falls back to the all-libraries default.

### Mac blind spots that remain (2026-10-06), none reachable from a runner

**Mac blind spots that remain (2026-10-06), none reachable from a runner:** the microphone/camera *permission prompt* itself (the synthetic tone bypasses the mic; the signature/plist guards cover the mechanism that broke before); Retina scaling (runners are 1× displays); native file dialogs (every test stubs them, the tour never opens one); Gatekeeper's first-launch path (CI runs the binary directly, no quarantine attribute). A report in any of those areas has no automated coverage behind it.

### Windows and Linux coverage added 2026-10-06, same evening

**Windows and Linux coverage added 2026-10-06, same evening:** the Windows build job **installs the Inno Setup installer silently, runs the installed copy's `--selftest`, checks the Start Menu shortcut, uninstalls silently, and asserts the user's `%APPDATA%` config folder survived** — nothing had ever run the installer before. Both GPU-building jobs (Windows, Linux) run `test_gpu_tuner` and `test_tuner_canvas` with the freshly built wheel: runners have only a software adapter (Windows) or no Vulkan (Linux), so what that exercises is the *fallback* — `test_tuner_canvas` accepts either a live GPU renderer or the designed drop to canvas with the CPU-mode notice. The Windows build job also runs the screenshot tour **in German** (longest language) as `win-tour-de`, so clipped translated labels can be seen. **Blind spots that remain, none reachable from a runner:** display scaling above 100 % (Matt's machines run 125–250 %; runners are 100 %); SD-card eject (removable drive); Falcon serial and camera hardware (mock and synthetic only); Wayland sessions (runners are X11); real audio devices on any platform.

### Frozen-build probe

**Frozen-build probe.** `SaxShopCompanion --selftest` (`_selftest()` in main.py) constructs the whole app in a withdrawn root — every tab, every import — and exits 0 or 1 without saving anything or showing a dialog (the excepthook is replaced for the run). The `build` job runs it against the PyInstaller output on each platform right after building: the one check that runs the *shipped bundle* rather than the source tree, so a missing hidden import, a bad `--add-data` path, or a module bundled on the wrong platform (the macOS GPU renderer class of failure) fails the build instead of a user's first launch. The .exe is a windowed app, so the Windows step waits on it with `Start-Process -Wait` and reads `ExitCode`.

### Eyes on the Mac

**Eyes on the Mac.** The macOS build jobs launch the built .app for real, `screencapture` the runner's screen after 12 s, and upload it as the `mac-screenshot-*` artifact — two pictures: the Pad Maker, and a second launch with `--tour tuner`, which opens the Tuner tab on a **synthetic 440 Hz tone** instead of the microphone (`TunerEngine.synthetic_hz`; `start()` opens no stream and `analyze()` feeds the tone into the ring buffer itself), so the canvas strobe and VU readout can be seen running on real macOS Tk. `tools/test_tuner_canvas.py` is the automated form of the same thing: it forces canvas mode, drives the tab with the synthetic tone through the real `_tuner_animate` loop, and requires the A wheel lit and the others dark, the readout to say A within 1 cent, and no error overlay; where the GPU wheel is built it runs the GPU path too and requires zero render failures. On the macOS CI runner that suite is the tuner's only end-to-end check. The toner has the same pair: a third Mac launch with `--tour toner` (Bb3 with six harmonics via `TonerEngine.synthetic_hz`) screenshots the analyzer, and `tools/test_toner_live.py` drives the Toner tab the same way and requires the note and frequency readouts, the fundamental within 0.5 c, and at least five harmonics. The toner is hidden behind the beta terms, so both use **`SAXSHOP_CONFIG_DIR`** — an environment override of the config folder (`config.get_config_dir()`), read before `config` is imported — to hand the app a prepared profile with the toner unlocked; `open` on macOS drops the environment, so the CI step runs the bundle's executable directly for that launch. `SAXSHOP_CONFIG_DIR` is also how any test should isolate itself from the user's real settings. The tab tests drive frames with a real `mainloop` and a quit timer, never a `root.update()` loop: the canvas tuner's frame outlasts its 16 ms interval on a large window, so `update()` keeps servicing the already-due reschedule and never returns (found 2026-10-06, 25 s stall in `canvas.coords`). Their `check()` helper fails on a returned `False` as well as on an exception — the first draft only caught exceptions, and two checks passed against an engine that had no synthetic source at all. `continue-on-error`, so it never fails a build — it is a picture for Matt to look at, the only way the Mac UI gets seen. A first-run dialog or a theme problem shows up there.

### End-to-end through the real buttons (2026-10-06)

**End-to-end through the real buttons (2026-10-06).** `test_pad_maker_e2e` types a pad list into the live form, picks all four materials with zones and locator marks on, clicks Generate SVG and Generate G-code with only the folder dialog and message boxes stubbed, and checks the *output*: one file per material (G-code skips `exact_size` by design — it has no laser settings), every SVG parses with the sheet size on its root, the leather SVG and G-code carry the locator layer (engraved before any cut), every G-code move lies on the sheet and ends with the laser off, and the job history recorded both runs. `test_tooling_e2e` drives every Tooling handler the same way (dies, holders in all three variants including the too-small-sheet refusal, organizer and spacer copies byte-identical to the bundled assets, kerf tests, speed & power with its `<name>_legend.txt`). `test_library_tabs_e2e` saves, reloads and deletes a key-height set and a screw spec, on disk too, and checks the serial lookup label against `lookup_serial_year`. `test_mac_paths` pins the macOS-specific paths (quit command, system colours, GPU never on darwin, config folder) and runs the whole `--tour all` as a dialog-construction gate with screenshots off. All four use `SAXSHOP_CONFIG_DIR` and never touch the user's data. The first run of these found the three gettext-shadowing bugs above and the Aqua tab-label clipping (`_fit_window_to_tabs`) and, from the first Mac tour screenshots, the Sizing Rules dialog clipping its preset bar at a fixed 500 px (`OptionsWindow._fit_dialog_width` now widens to the content; gated in `test_mac_paths`).

**The screenshot tour.** `SaxShopCompanion --tour all --shots DIR` walks every tab and dialog (20 stops: Pad Maker, Sizing Rules with the lesser-used section open and the pad preview up, Layer Colors, G-code Settings, nesting preview, polygon draw, Job History, Feature Set, User Guide, About, the Welcome window, the Quick Start Guide (both added 2026-11-09, so they are in the Mac pictures), the four library/tooling tabs, Key Layout, the tuner with no microphone (the audio-error overlay a user with a denied mic sees), then tuner and toner on synthetic tones), screenshots each cropped to the app's own windows, writes `tour-done.txt` (with any step errors), and exits. **Portability notes**:

- `test_descriptor_validity` hardcodes a local WAV corpus path (`C:\sax shop companion\recordings`) and only runs on Matt's workstation; `run_tests.py` skips it when the corpus is absent. `test_goodson_import` reads the website checkout at `C:/code/stohrermusic/...` and self-skips elsewhere.

- `test_tuner_engine`'s reference-player start tests and `test_wav_recording`'s "Music or Documents exists" check self-skip on a machine with no audio output device / a bare home folder (CI runners). `play()` returning False there is the fallback working.

- **The first CI test run (2026-10-06) caught a shipped bug:** CI installs `opencv-python` 5.0, which returns ChArUco ids as a flat `(N,)` array where 4.x returned `(N, 1)`; `calibrate_from_frames` indexed `i[0]` on a scalar and raised `IndexError`. The Windows installer built that day bundled OpenCV 5, so camera calibration in the shipped build would have crashed at the save step. Fixed by flattening the ids (`np.asarray(ids).reshape(-1)`); `requirements.txt` keeps `>=4.7`. Nobody had run `test_camera_capture` with OpenCV installed before — on the dev machine it had always self-skipped. Its calibration fixture was also degenerate (eight fronto-parallel translations of one card cannot determine a focal length; OpenCV 5 diverged to fx ≈ 9 × 10¹⁷) and is now ten synthetic pinhole views with a known K, which the test requires `calibrate_from_frames` to recover (fx within 2 %, principal point within 3 px; measured 800.2 of 800, rms 0.04 px).

- **The same OpenCV 5 change broke the calibration dialog itself, and that fix missed it (found 2026-10-15 from a user's report).** OpenCV 5 also returns ChArUco *corners* as `(N, 2)` where 4.x gave `(N, 1, 2)`; the live overlay indexed `pt[0][0]`, an `IndexError` on every frame the board WAS found in, and `_refresh_loop` swallowed it with `except Exception: pass`. So the preview froze on the last frame the board wasn't found in, Capture never enabled, the status said "Move the card into view", and Reconnect left the preview black (blanked, then every new frame raised before drawing). Nothing reached `app.log`. Shipped broken v2.7–v2.85 (every build after OpenCV 5 reached PyPI); invisible to Matt because his calibration was made under 4.x. Any code reading ChArUco output point by point goes through `camera_capture.corner_points` (and ids through `reshape(-1)`); contour outputs (`findContours`, `approxPolyDP`) keep `(N, 1, 2)` in 5.0 — measured. The loop now logs the first failure with its traceback and counts the rest. Gated by `test_calibration_dialog`, which drives the real dialog with a fake camera serving a rendered card — nothing had ever run that loop.

- `test_smoke_ui` constructs the full `PadSVGGeneratorApp` in a withdrawn Tk root — requires a display, so works on Windows/macOS and GitHub Actions Windows runners. The Linux CI job runs it under `xvfb-run`; it self-skips with a "no display" message only on a truly headless box.

- `test_zone_labels` is headless for everything except its three `preview_*` cases, which build a real `NestingPreviewWindow` and inspect its canvas. Those self-skip without a display; the other 44 always run. Note the window calls `wait_window()` in `__init__`, so the canvas inspection must be scheduled on the parent via `after()` *before* constructing it — see `_probe_preview`.

### Tests never touch the real settings folder (2026-11-05)

**Tests never touch the real settings folder (2026-11-05).** Every suite that can reach the config folder sets `SAXSHOP_CONFIG_DIR` to a temp folder at module level, **before any project module is imported** (config's file paths are module constants, fixed at import), and `tools/run_tests.py` gives each suite its own temp `SAXSHOP_CONFIG_DIR` when the environment has none (`suite_env`). `tools/test_config_isolation.py` gates both: an AST scan of every `tools/test_*.py` (a suite that imports `main`, `ui_dialogs` or a tab module, or names one of config's file paths, writers or migrating loaders, must set the override first), the runner's `suite_env`, and a subprocess proof that the app built under an override leaves the OS folder byte for byte alone. When you add a suite that builds the app, a dialog or a tab, set the override first; the gate says so if you forget. **Why:** startup backfills a Default G-code preset for any material missing from `gcode_presets.json` and saves at once (keep that: it is how an existing user gets a new material's preset). For years that wrote nothing for an existing user, so the suites that built the app without the override were harmless by accident. The day the adhesive ring material was added, six of them (`test_smoke_ui`, `test_job_history`, `test_frame_cut_scrap`, `test_scrap_live_list`, `test_scrap_pending`, `test_card_paper_size`) began writing that material's Default, with that morning's placeholder values, into the developer's real `gcode_presets.json`; it happened on Matt's machine before an independent test pass caught it the same day. The hunt also found `test_v161_compat` overwriting the real `app_settings.json` with old-version fixtures and restoring it from memory at the end: the same content afterwards, but a run killed half way would have left a v1.61 fixture as the user's settings. 25 suites were isolated. Proof, with `APPDATA` pointed at a scratch copy of a real folder and every file's content, size and mtime compared before and after: an old un-isolated suite changes the copy (the control); all 68 suites run directly, with no runner and no override, leave it identical; so does a full `run_tests.py`. On Windows a subprocess with `APPDATA` redirected also needs `PYTHONUSERBASE` set to the real user base, or user-site packages (svgwrite) stop importing.

### Writing a check (2026-10-15)

**Writing a check (2026-10-15):** the suites' `check(name, fn)` fails only on an exception or a literal `False`. A check written `lambda: a == b or a` returns `a` when the comparison fails, which is truthy, so it passes — three of the first calibration-dialog gates did exactly that and passed against the old code. Assert inside the function (or return a real bool), and run every new gate against the old code before trusting it. For a modal dialog whose worker threads call `after()`, construct it from inside `root.mainloop()`, not from top-level test code ("main thread is not in main loop"); `test_calibration_dialog.run_dialog` does this.

### No suite may open a native message box (2026-11-09)

**No suite may open a native message box (2026-11-09).** `tools/box_guard.py`. A suite that drives handlers or dialogs does `import box_guard` and `box_guard.install()` at module level, before anything else can run, and its `check()` calls `box_guard.settle()` after the check's own function (and prints `box_guard.reset()` after a failure, which says what was pending). `install()` replaces all eight `tkinter.messagebox` functions (`showinfo`, `showwarning`, `showerror`, `askokcancel`, `askyesno`, `askyesnocancel`, `askquestion`, `askretrycancel`), the `_show` underneath them, the native file dialogs, `simpledialog`'s prompts, and at the bottom `tkinter.commondialog.Dialog.show`, which every native box and file dialog ends in, so none can open by any route. A suite may put its own recording stand-ins on top afterwards. The `show*` stand-ins just record. A **question** must be named by the check that causes it, `guard.expect("Engraving Not Set", answer=True)`: one nobody expected is answered no (or cancel) and makes that check fail, and so does an expectation that was never used. Never write `messagebox.askyesno = lambda *a, **k: True` in a suite again: it answers a question nobody meant to ask and forgets it. **Why:** `test_tooling_e2e` stood in for `askyesno` but not `askokcancel`. An independent mutation pass planted a bug that made the Tonehole Crescent's Frame & Cut ask "Engraving Not Set"; the real box came up on Matt's screen and waited for his click, and the suite then PASSED (17.9 s instead of 2.8 s). On a CI runner the same regression would have hung until the job timed out instead of failing with a message. With the same bug planted the suite now fails in 3 s, naming the question, and nothing reaches the native layer. Every suite that builds a window carries the guard: 36 of the 81 (the other 45 are headless, read source, or run the app only in a child process). The list is `GUARDED_SUITES` in `tools/test_release_3_0.py`, which gates the guard and the suites' use of it (installed before the first top-level `def`, settled in the check helper, no `.ask* = lambda`). A new suite that builds the app, a dialog or a tab installs it. Those gates look before they call: a check of the guard asserts that a function IS the guard's stand-in and only then calls it. The first version called first, and when the guard was broken on purpose to test the gates, two real dialogs (a Yes/No box and a Save dialog) sat on Matt's screen for seven minutes each until the run timed out. Run a deliberately broken tree only with something under the native layer.

### No suite may open a real serial port either (2026-11-10)

**No suite may open a real serial port either (2026-11-10).** `test_falcon_sender`'s smoke section used to call the real `list_serial_ports()` and `auto_detect_falcon()`: every serial port on the test machine was opened, and a device that did not answer `?` was soft-reset (Matt's Falcon is plugged into the machine the suites run on). It now stands in for pyserial's port enumeration and for the probe, and checks the code's own work (the port dicts, the detection order). `test_laser_watch` runs that whole suite in a child with `serial.Serial` and `comports()` replaced by classes that raise, and requires it to pass: a real open or enumeration anywhere in it fails there. **Three gates from the pre-3.0 housekeeping, same day:** `test_exception_handling` (an AST scan: no bare `except:` in a root module, and every silent `except Exception: pass` is in its allow-list by file and function with its exact count; the 208 swallowed handlers were audited, 47 now log, see CLAUDE-architecture.md "Error Logging"), `test_tls_context` (the web data imports' SSL context verifies and has certificate authorities, never returns `CERT_NONE`, and a certificate failure reaches the user as the Connection Error box), and `--selftest` calling `config.assert_tls_ready()` so the shipped bundle on every platform, the Intel Mac included, is checked to carry certifi's CA bundle. **The bug round that followed (2026-11-10, the faults the audit listed):** `test_audit_fixes` gates each fix on the code as it is, every check failing on the frozen tree a10c8dd8 (the bed-bounds check refusing when the head's position cannot be read; Reset Falcon one box, the homed flag cleared only by a reset that went out; the calibration jog's port closed in a `finally`; the run dialog's Start Frame unlocked only by a jog the sender wrote and Pause/Resume following the byte, with `FalconSender.jog/send_realtime/pause/resume` returning the answer and a stand-in's `None` still counting as sent; the two camera refresh loops logging once, counting and going on; `parse_pad_list` rejecting inf/nan; the tone library kept as `.corrupt.bak` and bad bytes not a crash; a stored non-numeric pitch). **`run_tests.py` changed the same day:** each suite is named on its own line before it starts (`..   name`), the per-suite timeout is 300 s (`SSC_SUITE_TIMEOUT_S` overrides; the slowest suite takes about 135 s), a timed-out suite is killed with every process it started (its own process group; `subprocess.run(timeout=)` killed only the child and then waited for ever on a pipe a grandchild held, which is how a Linux job sat 33 minutes on 2026-11-10), and its output goes to a file so the lines it printed before hanging are shown at once; and every suite's interpreter arms `faulthandler` (a `sitecustomize` the runner puts first on `PYTHONPATH`, with `SSC_FAULTHANDLER_S` = 15 s before the timeout), so a hung suite's output ends with every thread's stack and the next hang says where it sat. The three hangs of 2026-11-10 (the tuner engine suite on Apple Silicon, the calibration dialog suite and an unnamed first suite on Linux, all intermittent, all green on re-run) share one thing: each imports `sounddevice`, directly or through main, which runs `Pa_Initialize()` at import and `Pa_Terminate()` from an `atexit` hook; every thread the app starts is a daemon thread, so no Python thread can hold the exit. Nothing is concluded until a dump shows it. `test_tuner_engine` runs every call that touches the audio device under a 20 s bound and leaves with `os._exit` if one hung (it hit the 900 s timeout on a macOS runner the same day). The look for other unbounded device calls found one, in the app: `toner_engine.check_mic_quality`, which `_toner_start` calls on the Toner tab's first start before any stream is opened (so the toner suite and the CI tour reach it even on the synthetic tone), now answers within `MIC_CHECK_BOUND_S` (5 s) whatever PortAudio does. The two tab suites stub `engine.start` for their no-mic cases, `test_wav_recording` never opens a stream, `test_config` mocks sounddevice, and every thread a suite starts is joined with a timeout.

### Swallowed exceptions, audited (2026-11-10, pre-3.0 housekeeping)

**Swallowed exceptions, audited (2026-11-10, pre-3.0 housekeeping).** Every `except ...: pass` in the root modules (208) was put in a class. 161 are deliberate and stay silent: widget teardown, a Tk call on a window that may be gone, a cosmetic call, an optional import, closing a port or releasing a camera that may already be closed; where the type was obviously narrower it is now named (`tk.TclError`, `OSError`; `(tk.TclError, ValueError)` round `after_cancel`, which raises `ValueError` on a None id). 47 now log one line through the module's logger and change nothing else (the handler still swallows and continues): the laser dialog's Stop, Pause, Resume and jog failures, the `on_finished` / `on_status` / `on_progress` callbacks in `falcon_sender` (throttled through `_log_throttled` where they repeat), every settings write in the camera dialogs, the keep-awake lock, the live camera preview failing to open, the camera overlay's per-frame loop (once-then-count: the first failure with its traceback, a count when the overlay stops). None hid a bug of the OpenCV 5 kind; the one that led straight to `CERT_NONE` went with the unverified SSL fallback. The 60 silent handlers that catch `Exception` are listed by file and function in `tools/test_exception_handling.py`, which fails on any new one, on a count that grows, and on any bare `except:`; to keep a new deliberate one, add it there with its reason. A handler that repeats on a timer logs once and counts, never per tick.

## The Spanish strip "off the page" on Linux and Aqua: a check reading layout before any event ran (2026-11-11)

After round 6 CI was green on Windows and the Intel Mac and failed one check of `test_analyzer_tab` on Linux and Apple Silicon, in Spanish only: "Capture off the page at [1217, 720]" with the app's measured need 1006. ## The suites run on a private desktop (2026-11-11)

Matt: "any chance the tests could be done minimized? I can't use my pc for a while when they are running". Every suite builds Tk windows, and a Tk window cannot be kept from showing or from taking focus on the desktop it is created on; minimizing them would still flash and steal focus at each build. So the suites are moved to a Windows desktop of their own: `tools/run_tests.py` re-runs itself through `tools/hidden_desktop.py` (`CreateDesktopW`, then `CreateProcessW` with `lpDesktop` set, inside a job object that kills the whole tree when the runner goes), and every process it starts inherits that desktop. The display is the same, so the suites read the same screen size (1536 x 864 here, measured on and off the private desktop under both interpreters); the keyboard focus inside the desktop is theirs alone, so the checks that look at focus (`test_user_guide`, `test_welcome`, `test_frame_cut_steps`) behave as before; `run_tests_as_ci.py` inherits it; `--visible` keeps the suites on the user's desktop; macOS, Linux and CI (`GITHUB_ACTIONS` set) are untouched. The runner's first line says which.

**Why ctypes.** Python's `subprocess.STARTUPINFO` accepts an `lpDesktop` attribute and `_winapi` ignores it: a child started that way lands on the user's desktop all the same (measured: the child's thread desktop reads "Default"). The first prototype relied on that attribute and believed it worked because the suites passed; they passed in the open.

**What was checked on the private desktop.** The 300 s kill (`SSC_SUITE_TIMEOUT_S`, here 15) still takes the whole process group: a planted suite that hangs in its mainloop after starting a child that sleeps ten minutes is reported as a TIMEOUT and both pids are gone afterwards. A planted suite that opens a NATIVE message box with no guard and no stand-in hangs unseen there, is killed at the timeout and fails the run (exit code 1 through the re-run); with the audit backstop on PYTHONPATH (`tools/box_guard.py` for the suites, a developer's `sitecustomize` for broken trees) the same box is answered and logged instead. The runner's own faulthandler `sitecustomize` hands over to the next one on the path, so the backstop reaches the suites under `run_tests.py`. A native box on a hidden desktop is worse than one on the user's, since nobody can see it: the standing rules about `box_guard` and the backstop matter more now, not less. Full runs under Python 3.11.18 (CI's lock) and 3.14.3 on the private desktop: in report-analyzer-12.md.

## A check that raced the runner's clock (2026-11-12)

`test_analyzer_tab`'s "coming back within the restore's check" failed once on the Apple Silicon runner, on a commit that changed one line of guide text. It left the tab, ran a 30 ms slice and asserted that the restore's 100 ms check had not run; on a loaded runner the slice took longer than the 100 ms. The fault was the check's own precondition. It now holds the restore's check back for its own duration (a stand-in for `root.after` that lengthens only that one timer to 1.5 s) and waits past it afterwards. Proven both ways: with `_cancel_width_restore` made to do nothing the check fails; planting out only the `after_cancel` inside it does not, because closing the record is what stops the old check, and that is fine. The rule this adds to "never a fixed wait": a check that needs to act *before* a timer of the app's fires holds that timer, it does not try to be quick.
