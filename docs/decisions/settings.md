# Settings: the schema, validation at the door, and the key gate

The CLAUDE files hold the rules (CLAUDE-architecture.md, "Settings Persistence Pattern" and "Settings Loading Hardening"). This file holds the why and the history.

## Typed settings (2026-11-10, structural step 4, the last)

Matt's second of two structural picks (the first: split `on_frame_and_cut`, machine-integration.md). The problem as the parent session put it: 103 top-level settings (28 bool, 24 float, 21 str, 12 dict, 9 int, 5 None, 4 list) read as string keys from a plain dict in some 750 places (`settings["x"]` 337, `settings.get("x"` 413); a typo is a silent default; a wrong type from a hand-edited or old file travels until something breaks far from the cause. Not done, on purpose: rewriting those call sites into attribute access (a settings class). The dict stays the runtime object and every preset, test and module that passes it around is untouched. What was added: a schema in one place, validation at load, and a gate on the keys.

**The schema** is `settings_schema.py`, its own module rather than a section of config.py: config.py is 1,400 lines and the schema is 400 lines of declarations; the gate and the dialogs can import it without config's side effects; config imports it lazily inside `load_settings` (settings_schema imports nothing from config, and its material and preset-key tuples are checked against config's by the gate). One `Field` per key: a kind (bool, int, float, str, list, dict), an enumeration or a range, None allowed or not, a regex for colours, the element Field and fixed length for lists, the key schema and the Field for unknown keys for dicts. 104 top-level fields, 382 in all with the nested blocks (gcode_settings' seven material blocks from the G-code preset keys, the tuner, toner and tooling blocks, the Speed & Power Test's remembered form, engraving_location, layer_colors, key_layout, visible_tabs and the rest). An int is accepted where a float is declared; a bool is never a number (`True` is not 1); NaN and infinity are never numbers.

**Where the ranges came from, and the rule not to invent one.** Enumerations: the dialogs' radios and comboboxes and the code's tuples (units in/cm/mm, the four Universal/Per Size Range switches, the placement radios out/mid/int, the hole options, the d-pad's ten biases including `off`, letter/a4, layer/pad, line/filled, the Tooling label locations, languages, locator styles, transpositions, the tuner's fps switch 60/90/120 and waveforms pure/rich, the toner's switches 30/60, spectrum/bars, linear/db, the eight sax types, 5- or 6-layer holders, the two Tooling material lists). Ranges: the sliders' ends (sensitivity 0..100, BRIGHT 10..150, NOTE and OCT. 0..100, the crescent curve 0..100, the detection bias -80..80, the capture threshold 0..100, the dart shape 0..1 which the v2 migration clamps too), the Inset dialog's "a number 0-50", the G-code dialog's `max(1, ...)` on passes, and what Grbl and the engines assume (speeds and powers non-negative, 0 meaning "not set"; the scan-line spacing above 0; kerf non-negative, its spinbox's top of 1.0 not declared because typing is not clamped). Everything else is a type only, with a comment saying nothing bounds it: the sizing numbers, the zone and locator sizes, feeds, the bed, the grid sizes, the fonts, the reference pitch (the tuner's slider runs 420..460 but a file may hold any pitch), framing power (`get_framing_power_s` clamps on read to `FRAMING_POWER_S_MAX`; declaring the cap here would have turned a value the clamp handles into a reset to the default). The Speed & Power Test's `material` is the combobox's translated display label, so it is text, not an enumeration. Layer colours accept the 3- and the 6-digit hex forms, which Tk and SVG both take, although the chooser writes six.

**Validation** runs in `load_settings` after the merge, the null rejection, the non-dict skip, the LightBurn colour replacement and the dart-shape migration, all of which stay as they were. A bad value goes back to the default at its path and is logged once on `ssc.settings` with the key, the value (repr, 80 chars) and the file. A nested value is replaced alone, never its block; a key a block carries that the schema does not know (one from a newer version, kept by the two-level merge) is left alone; a list is checked as a whole (its type, its elements' type), not the fields inside each range rule. A fault in the check itself is caught, logged, and the merged values are used; it cannot archive the user's file as corrupt. Proven to change nothing for a valid file by loading five profiles with the old config.py (8b451c2) and the new one in fresh subprocesses and comparing deep-equal (`scratchpad/s4/prove.py`): the defaults (an empty profile), the v1.0 and v1.61 configs `test_v161_compat` uses, the v2.9-era profile `test_adhesive_ring_upgrade` writes (defaults without the adhesive-ring keys, Matt mode applied, a user's own values), and a copy of Matt's real settings (read only). All five identical, zero corrections logged, apart from the six keys below, which every profile now gains with their defaults. One thing the proof corrected during the work, not after it: the first draft declared the Speed & Power Test's `passes_value`, `passes_start` and `passes_end` as ints; Matt's file holds 1.0 and 3.0, because the tab stores every value, start and end as `float()` (and only the stops as `int()`). The schema was changed to say so; without the real file that would have reset three of his values to the defaults on the next start.

**The gate** (`tools/test_settings_schema.py`) is an AST scan of the 28 app modules for every string-literal key read from or written to a settings dict: `settings["k"]`, `.get("k"`, `.setdefault`, `.pop`, `"k" in settings`, writes, on `settings`, `self.settings`, `self._settings`, `app.settings`, `DEFAULT_SETTINGS`, and the local names assigned from any of those (a function-scoped alias table), top level and one level down through the known sub-dicts (a literal material under `gcode_settings` reaches that material's block; a dynamic key reaches the block the children share). 775 literal accesses are checked. What it cannot see, counted and named in its output: 191 accesses of schema keys on dicts it cannot tell are the settings, a sizing preset `source` or `preset` in the Sizing Rules dialog (37 and 10), a range rule `r` (10), a `sizing` result (10), the dialogs' `vars` (10), a material block passed under its own name. A typo in those is not caught; a typo in the other 775 is. An honest partial gate, as the brief asked.

**The first run's hits: six, all real, one class.** Keys the app writes and reads back but never declared in `DEFAULT_SETTINGS`, so `load_settings`' merge dropped them on every start, which CLAUDE-architecture.md's "Settings Persistence Pattern" forbids and nothing checked: `show_live_camera` (the Pad Maker's "Live camera preview" tick, saved by `_save_checkbox` since v2.5: ticked, restart, unticked) and, in `tooling_settings`, `organizer_material`, `organizer_sheet_width`, `organizer_sheet_height`, `organizer_sheet_units` and `crescent_material` (written by the Tooling tab since 2026-11-09, every restart forgot the Die Organizer's material and sheet and the Crescent's material). Fixed by declaring them: `show_live_camera: False`; the organizer's material `basswood` and the crescent's `cork` (each list's first entry, which was already the fallback for a missing key); the sheet width, height and units `""`, meaning "not set, size it from the app's units" as before, with the two reads in tooling_tab.py changed from `.get(key, fallback)` to `.get(key) or fallback` so the empty default does not blank the entries. One check pins all six: a profile holding them comes back with them (before the fix every one came back as never set). No typo, no false positive: the scan's allow-list is empty.

**Dead keys**, found by counting references and left in place (removing a key is not this step's call): `gcode_output_enabled`, `sd_card_path`, `falcon_serial_port_override`, `laser_seed_feed` are declared and never read or written anywhere; `toner_settings.gauge_bias` outlived the descriptor gauges (removed 2026-04-06). `laser_framing_feed` is read by Frame & Cut and the calibration dialog and written by no dialog: a hand-editable constant, kept.

**Presets: not validated on load, by choice.** The schema can check a sizing preset (its keys are settings keys) and a G-code preset (a material block); tried on Matt's sizing and G-code presets, the v2.9 fixture's and the bundled Matt mode, it corrects nothing. But the only shared point sizing presets pass through on their way to the form is `normalize_sizing_preset`, which the dialog also calls on every form change to name the active preset, so a log line there would repeat; doing it right means a validate-and-log pass at the two `load_presets` call sites in main.py plus a third after an import, three more call sites than "a few lines". Listed as not done. The pieces are there (`validate_settings` takes any dict, any defaults and any key schema) for a later step.

**Rejected.** A settings dataclass with attribute access (hundreds of call sites, every preset and test, for a typo check the gate gives without touching them). Declaring ranges from "reasonable" values (a limit nobody enforces today would reset a working file). Validating a list's elements field by field (a bad field inside one range rule would have thrown away the user's whole list of rules; the rules are a dialog's own data and the dialog builds them). Logging through the root logger (it is on WARNING and the line names the file; `ssc.settings` keeps it findable).

## JSON files are read as UTF-8 first (2026-11-13)

Every JSON read was `open(path, 'r')`, which on Windows is the system encoding (cp1252 on Matt's machine). The app's own files are written with `json.dump`'s default, plain ASCII, so the app never met the fault with its own files. A file written as UTF-8 by another program, or edited by hand and saved, did: measured, a key height set named "Selmer Série II" was imported as "Selmer SÃ©rie II" and a Japanese name as noise, with no error. Found by reading a sibling program whose key heights files are meant to go both ways and are written as UTF-8.

`config.read_json(path)` reads the bytes, decodes UTF-8 (a byte order mark allowed, which until now failed to parse), and only when the bytes are not UTF-8 decodes them in the system encoding, strictly, as before. So every file that read before reads the same, and the two cases that were wrong or failed now read. All nine JSON reads go through it: settings, the preset libraries, Job History, the tone presets, and the imports of pad presets, key height sets, screw specs, tone presets and sizing presets. The writes are unchanged (ASCII). Rejected: `encoding="utf-8"` on each `open`, which would turn a hand-edited cp1252 settings file with an accent in a path into a "corrupt" file put aside and replaced by defaults.

Gate: `test_config`, "JSON files read as UTF-8 first, the system encoding after" (failed on the old code with the garbled names).
