# Machine integration: decisions and history

This file holds the why and the history behind the rules in the CLAUDE files, and the full detail they summarise: what was tried, measured, rejected and decided, with dates and the user's own words. The paragraphs were moved here verbatim from the CLAUDE files on 2026-11-10 (HEAD 01071f5); each section names where it came from. Add new decisions to the matching section, dated.

## Direct machine control everywhere (the 3.0 work, 2026-11-09)

*Moved from CLAUDE.md, section "CLAUDE.md > Direct machine control everywhere (the 3.0 work, 2026-11-09)" (2026-11-10).*

Matt: "let's add direct machine control for tooling. we can truly say then after that that you do not *need* lightburn". This is one body of work, meant to become version 3.0 (no version bump or release notes until Matt asks for release prep). Detail is in CLAUDE-engines.md ("Tooling: Frame & Cut", "Die Organizer", "Tonehole Crescent", "Cork") and CLAUDE-architecture.md (gating, the Welcome window). In short:

- **Frame & Cut on Tooling.** Every Tooling tool that writes G-code has a Frame & Cut button beside Generate G-code that sends the same job straight to the laser: Die Inserts (and its Scrap Mode), Die Holders, Die Organizer, Kerf Test, Speed & Power Test, Tonehole Crescent. It is the Pad Maker's sequence run by the Pad Maker's routine, `main.on_frame_and_cut(tooling_job=...)`.

- **G-code for the two tools that had none.** Matt: "building a gcode path for what needs it sounds like the right call." The Die Organizer's bundled drawings are read and cut (openings first, the edge last, kerf both ways); the Tonehole Crescent is cut half a kerf outside its outline so it comes out at size. Both sections gained a material choice. Only the Pad Maker's Exact Size material is still SVG only.

- **Cork** is a laser material (Matt: "tonehole crescents are usually cork. we do not have that as a material yet"): Tooling only, the crescent's default. Its cut default is Matt's own tested value; its engraving ships at 0 and 0, which means **not set** (`config.engraving_is_set`): generators leave the engraving out, never write F0 or S0, and the tab says so.

- **One gating rule for Frame & Cut, both tabs.** Asked "Should Frame & Cut require a camera calibration?", Matt answered "No, on either tab". The button shows with machine integration on and a laser detected. The Machine menu's laser items need only the toggle. Everything that uses the camera still needs a calibration.

- **One line on every "G-code written" box**: "Send this file to the laser as it is. For LightBurn, use Generate SVG." (`ui_dialogs.gcode_file_note`, the only place the sentence is written). A user had imported die G-code into LightBurn, which drops the speeds and powers. Never on an SVG or STL box, never on Frame & Cut.

- **Welcome window, Quick Start Guide, User Guide search.** A Welcome window shows once per version on a real launch (`main.maybe_show_welcome`, called only from the `__main__` block) and from Help > Welcome; it links to the User Guide with the cursor in its new search box and to a one-page Quick Start Guide (Help > Quick Start Guide).

- **Five older bugs fixed on the way** (all in v2.9; Matt: "Yes, fix all five"). Frame & Cut for card on "Fit card to paper" with a shape still loaded cut off the sheet (a job that is not on the loaded shape now takes nothing from it). A cancelled jog left the serial port open. The no-laser exit left the sleep lock held. Die inserts nested with the Pad Maker's Edge Bias, from the middle of the sheet by default, and now always nest in rows from the bottom-left corner (`svg_engine.nest_edge_bias`; Labeled Zones never reach them either). Tooling's section buttons cut off long German and Spanish labels (and, with fewer tabs shown, a Mac or Linux window stayed too narrow for them: the window is now never narrower than the Tooling tab's content). Detail in CLAUDE-engines.md ("Five older bugs", "Die inserts nest from the bottom-left corner", "Section buttons"); gates in `tools/test_release_3_0.py`.

- **The laser and the camera may come later (2026-11-09).** Matt: "is there a way for the ssc to be ok with a user plugging in the laser when the ssc is already running? I feel like now it has to be plugged in first", and of the camera, "same deal?" — "Yes, both". A laser watch (`falcon_sender.LaserWatch`, run by `main._start_laser_watch` from the launch block only) lists the serial ports every 2 s and probes what has just appeared; Frame & Cut shows within seconds of the laser being plugged in and goes when its port vanishes; the probe asks `?` before it resets. A camera whose saved number cannot be opened falls back once through the rest of the resolver (`camera_capture.open_camera_or_fallback`, used by all four camera windows) — with a calibration on disk only to the Falcon-named camera, never silently (the window's status line says which camera it shows), and never against the app's own live preview, which is closed first — and the saved number is left alone. Tooling runs go into Job History (above). Detail in CLAUDE-engines.md ("The laser watch", "The camera's saved number").

Tests: `test_tooling_frame_cut` (49), `test_tonehole_crescent_gcode` (16), `test_die_organizer_gcode` (15), `test_cork_material` (13), `test_gcode_file_note` (7), `test_welcome` (9), `test_release_3_0` (41), `test_laser_watch` (21), `test_camera_fallback` (13), plus checks in `test_tooling_e2e` (every Generate button is one Job History row for its tool). Every gate was run against deliberately broken code (145 breaks, one at a time, each caught by the check meant for it); the gating checks were also run against the old gating code and fail there. The Pad Maker's Frame & Cut was recorded on a mock sender before any of this (28 clicks, 19,721 streamed lines) and is byte-identical afterwards with a calibration present; without one the streamed lines are still identical and only the camera extras are gone. Not covered by anything automated: a real laser.

## Tooling Tab

*Moved from CLAUDE-engines.md, section "Engines: Pad Generation, G-code, Tuner, Tooling > Tooling Tab" (2026-11-10).*

### Camera Calibration (v2.5)

**Camera Calibration (v2.5)**: integrated single-pass calibration that solves camera intrinsics + lens distortion + pixel-to-MACHINE-mm homography in one workflow. `CameraCalibrationDialog` (ui_dialogs.py) opens with a horizontal-split layout (preview left, controls right) showing two phases. Phase 1 (engrave): live camera + jog cluster + MPos display + Home Laser button + Frame (continuous-loop bbox tracer, follows jogs) + Engrave button. The engrave commits the calibration card at machine `(head_x − card_w/2, head_y − card_h/2)`; uses the basswood G-code preset's `filled_engraving_speed`/`power`/`passes`/`line_spacing` from `gcode_settings.basswood` (so users tune their machine's basswood feeds once and the card engrave matches). Bed-bounds safety check refuses to engrave/frame if the card would extend off the bed. Phase 2 (capture): live preview + multi-pose ChArUco captures with explicit reference / intrinsics substates — the user takes 1+ reference captures (card untouched at engraved position, pooled in `calibrate_from_frames` for the machine-mm homography) then clicks "Done with references" and moves the card for the remaining intrinsics captures. Retake-last + Reset-all recovery buttons let users iterate on bad detections without losing other captures. After save, calibration JSON has `homography_px_to_machine_mm` (replaces the old `homography_px_to_mm` which was board-frame). `pixels_to_mm` returns machine coords directly. `is_legacy_calibration` detects pre-v2.5 files; `load_calibration` returns None on those (forces recalibration).

*Calibration hardening (v2.86, from a user's report plus a bug hunt; all gated in `test_calibration_dialog`, each gate run against the old code):*

- **Diagnostics.** The dialog logs (logger `ssc.machine`, INFO reaches `app.log`) camera open/reconnect/switch with the first frame's size and brightness, a detection summary every `SUMMARY_INTERVAL_S` (5 s: frames, frames with markers, frames with the board, max corners, brightness range, detect ms, frame errors) instead of a line per frame, every capture/retake/reset/Done, calibrate inputs and result, engrave position and basswood settings. It saves the raw camera frame as `<config dir>/last_calibration_frame.png` (3 s after the camera goes live, then at most once a minute while the board isn't found for 10 s) — the exact image the detector saw, written via `imencode` because `cv2.imwrite` can't open a non-ASCII Windows path. A frame that raises is logged once with its traceback, then counted; the loop never swallows silently again.

- **Layout.** The right panel is packed BEFORE the preview: a Tk label showing no image reads width/height in *text characters*, so the old 640x480 preview asked for ~4500x7200 px when the camera failed and squeezed the panel to 1 px (no Cancel/Switch/Reconnect). `_fit_height` grows the window to the panel's controls (engrave phase overflowed 600 px). `CameraCaptureDialog` uses a blank 640x480 `PhotoImage` placeholder for the same reason (it asked for 7076x10779 px with a dead camera).

- **Status hold.** The preview writes its progress line only in capture phase and only once any other message has been up `STATUS_HOLD_S` (6 s) — it used to overwrite Homed / Framing done / Engrave complete / capture hints 10x a second.

- **Calibrate refuses inputs that save a wrong calibration** (`_calibration_inputs_ok`): no reference capture left (Retake past the references used to leave 'card moved' mode with zero references, and a moved frame became the reference: ~50 mm off on a simulated Falcon camera), 'Done with references' not clicked or fewer than `MIN_MOVED_CAPTURES` (5) moved captures (21–43 mm off with a fine-looking RMS), no engrave offset on file (offers manual entry; the (50, 50) default used to be applied silently). The RMS the dialog reports does not catch any of these.

- **Framing aborted with the window X** soft-resets mid-trace and loses position: `_framing_done` and `_engrave_homed` are cleared (Done ends gracefully and keeps them). Calibration framing and the card G-code start with `G92.1` — a G92 left by Frame & Cut would shift a card positioned from MPos. After every `FalconRunDialog` the dialog re-takes the input grab (Tk doesn't hand it back). Engrave new card re-enables Frame. Opening the camera is a no-op while one is open or opening (engrave->Next used to open a second handle and a second refresh loop); a handle that finishes opening after the dialog closed is released. Switch camera with captures discards them after asking. The MPos poll runs on a worker thread; buttons that open the serial port hold `_port_lock` (`@_holds_port`) and the poll skips a tick while it's held (it used to block the Tk thread ~0.3 s every 0.8 s).

- **Use time.** `camera_capture.calibration_size_mismatch` refuses a camera delivering a different frame size than the calibration was made at (scrap capture and the polygon overlay). `default_calibration_path` follows `SAXSHOP_CONFIG_DIR`.

- **A bed-bounds check that cannot be made does not pass (2026-11-10).** `_engrave_check_position_safe` used to return True when the connect or the status query failed, or no MPos came back, so the check was skipped silently and a head left at the home corner would have engraved off the bed. It now refuses with "Head Position Unknown" (the reason in the box), logs it, and closes the port in a `finally`; `_engrave_jog` closes its port in a `finally` too. Gated in `test_audit_fixes`.

- **Known, not fixed:** RMS isn't a quality signal and a card lying flat gives one plane orientation, so intrinsics can be loosely determined even with good captures (a design question, raised with Matt). The dialog's framing box is 8 mm off-centre from the engraving and 18 mm taller (cosmetic: frame encloses engraving; the solver uses the true geometry).

### Frame & Cut (v2.5)

**Frame & Cut (v2.5)**: Pad Maker > Frame & Cut button (the Tooling tab's four Frame & Cut buttons run the same routine since 2026-11-09, see "Tooling: Frame & Cut" below). Manual-only — there's no "Auto" mode anymore (the v3.0-dev auto-frame was stripped because head MPos drift made it unreliable). On click, a nesting preview of the layout shows first (the per-scrap subset in Scrap Mode, the whole batch in standard mode); **Adjust** backs out without consuming a scrap (v2.62). After the preview is confirmed:

1. `FalconRunDialog` opens in jog-only mode (empty G-code, `_is_jog_only_mode=True`) with the title "Position the head at your material's bottom-left corner…". Buttons: Home Laser (re-homes mid-dialog), jog cluster, **Try Auto Locate** (drives the head to the polygon's anchor vertex via `$J=G90G53 X… Y…` — machine coordinates, so a G92 left by the previous Frame & Cut can't shift it — when `_custom_polygon_lb_machine` is set and the laser has been homed this session), Cancel, Start Frame →.

2. Start Frame asks the **lid question** ("Is the lid closed?", Yes, Start Frame / No, Cancel) — framing energises the laser, so this is the boundary where an open lid alarms the machine. No keeps the jog dialog open. `on_frame_and_cut` builds the framing G-code with a `G92 X{lb_x} Y{lb_y}` prefix where `(lb_x, lb_y)` is the outline's anchor vertex (`svg_engine.polygon_anchor_vertex`: the vertex nearest the bbox bottom-left, Y-up) relative to the bbox, from `_frame_cut_anchor()`. Auto Locate's target and the polygon dialog's machine anchor use the same function: until v2.86 Auto Locate took the *leftmost* vertex, which on a scrap tilted 2° CCW is the top-left corner, ~150 mm from where the G92 assumed the head was. This makes work `(0, 0)` map to the polygon's bbox-BL even when the user jogs to a non-bbox-BL vertex (tilted scraps where the visible BL corner is not at bbox-min-Y).

3. `generate_polygon_framing_gcode(custom_polygon_outline)` emits the trace, ROTATED so polygon[0] is the vertex closest to `(0, 0)` (the BL after Y-flip). G-code starts with `G0 X0 Y0` — no head-jump at trace start regardless of user's click order. Closes with `M5` only (NO trailing `G0 X0 Y0`; that would land the head at bbox-BL between loop iterations, breaking the G92-with-LB-offset alignment).

4. Framing runs in `FalconRunDialog` loop mode (`loop=True`) at low power until user clicks "Looks Good — Cut!" — `_on_cut_clicked` sets `_cut_requested=True` (no second lid prompt; framing has been running, so the lid is shut), last pass completes naturally, dialog closes.

5. Cut runs with the SAME `G92 X{lb_x} Y{lb_y}` prefix as framing so both passes share work-origin.

### Lid question (`FalconRunDialog._remind_lid_closed`)

**Lid question (`FalconRunDialog._remind_lid_closed`)**: `LidClosedDialog`, a two-button Toplevel reading exactly "Is the lid closed?" with **Yes, Start Frame** and **No, Cancel** (tk's askyesno can't label its buttons), shown at **one** boundary — **Start Frame** (`_on_advance_clicked`, gated by the caller's `remind_lid_on_advance=True`). Yes returns True and the jog dialog closes so the caller proceeds; No (also the close box and Escape) returns False and `_on_advance_clicked` simply returns, leaving the jog dialog open with nothing consumed, so the user shuts the lid and clicks Start Frame again. No detection. `tools/test_lid_confirm.py` asserts there is exactly one call site, so a new one can't creep in. The two buttons are one width: 16 characters, or as many as the longer label needs in the current language (2026-11-09, Matt: "Yes, fix buttons"). At a fixed 16 the French "Oui, démarrer l'encadrement" was cut off, and for a few hours the French and Italian labels had been shortened to fit the button. Each language's Yes label names its own Start Frame button; both are gated per language in `tools/test_release_3_0.py`.

### Start Frame is the boundary, not the cut

**Start Frame is the boundary, not the cut.** Framing runs at low power, but *low power is still power* — Grbl enters Door state the moment the beam is asked for with the lid up, so the alarm lands at the framing pass. A prompt on the cut fires after the user has already eaten the alarm and needs a laser power cycle plus an app restart. The cut needs no prompt of its own: framing has been running by then, which proves the lid is shut.

This took two corrections. It originally fired at three boundaries (Start Frame, Cut, and Done during a framing-only loop), which just trains you to dismiss it. Matt cut it back to one on 2026-08-11 — but to the **cut**, on the reasoning that framing "isn't about to start burning." That reasoning conflated *marking the material* with *energising the laser*: it's the beam coming on that trips the door interlock, at whatever power. Matt hit it in the shop and corrected it on 2026-08-18 — v2.7 was pulled from release and re-cut with the reminder on Start Frame. The `confirm_lid_on_advance` constructor flag was removed on 08-11 and is back as `remind_lid_on_advance` (default False, opt-in), because the dialog can't know whether its caller's next step fires the laser. The message stays the bare question. The buttons changed once more on 2026-10-26: from 08-05 the popup was single-OK with nothing to decline (a yes/no gate "just gets clicked through"), but in the shop the lone button read as the app asserting the lid was closed rather than asking, so Matt asked for two real answers. The one-call-site rule and the one-boundary rule are unchanged.

The reminder replaced a per-boundary `_confirm_door_closed()`/`_is_door_open()` pair that branched on Grbl's reported door state (`Door` state or a `Pn:` `D` pin): live-hardware testing on 2026-08-05 found the Falcon2 Pro 40W (ESP32-S3 controller) never sends a `Pn:` field at all, lid open or closed, so detection was unverifiable across Falcon models and dead code on the one machine tested — plus it cost a synchronous status poll before the popup could even show. The aggressive mid-cut Stop path (soft-reset abort, not a laser-firing handoff) is untouched — it keeps its own "Stop the job?" confirm.

### Scrap-mode Frame & Cut (v2.6)

**Scrap-mode Frame & Cut (v2.6)**: when Scrap Mode is on, Frame & Cut runs one scrap per click — it routes through the shared `_scrap_begin_partial()` helper (same partial-nest + session bookkeeping as the file-export `_generate_gcode_scrap_mode` path) instead of a full nest, then `_frame_cut_scrap_advance()` bumps the scrap count, decrements remaining, and shows the continue/recapture dialog — but only after the cut streams to completion (`cut_dlg._final_reason == "complete"`), so a stopped or errored cut leaves the scrap re-cuttable. The G92/outline logic above is unchanged, so each re-captured scrap aligns on its own jogged origin. The session can start without a save folder (Frame & Cut streams, never writes files); if the user later switches to file-export Generate mid-session, `_scrap_begin_partial` prompts for a folder then. Covered by `tools/test_frame_cut_scrap.py`.

Both are normalized using the OUTLINE's `bbox-min-x` + `max-y` in `_set_custom_polygon_from_y_up(points_y_up_mm, outline_y_up_mm=None)`. Pad placements in custom_polygon's storage frame sit inside the inset bounds (e.g. (3, 3) to (97, 97) for a 100mm scrap with 3mm inset), so after the G92 zero-at-jog they land at the right machine positions — **provided the cut is Y-flipped with the outline's height**. `generate_gcode_from_placed` flips with the height of the polygon it's handed, and Frame & Cut hands it the inset polygon, whose max-y is `inset` short of the outline's; the framing pass flips the outline with the outline's height and both streams share one G92, so from v2.5 to v2.7 every camera-captured cut landed `inset` mm toward the machine front of where the frame showed it (5 mm on Matt's 5 mm inset: the front row of pads on the scrap's edge). Found 2026-09-20 while chasing a label report. `on_frame_and_cut` now passes `flip_height_mm=` (the outline's height) and `tools/test_frame_cut_alignment.py` pins the disc's machine position against the framed outline, including the negative control. Hand-drawn polygons have no separate outline and were never affected.

### The streamed cut is kept

**The streamed cut is kept.** The temp file the cut is generated into is deleted as soon as it's read, which left nothing to audit when a user reported labels outside their discs. `_keep_last_cut_gcode` now writes the exact lines sent to the Falcon to `<config dir>/last_frame_cut.gcode` (overwritten per cut) and logs one `frame&cut ...` line to app.log with the G92, flip height and polygon bbox. Check that file before assuming the engine: every label in 40 fuzzed leather scraps (622 discs) sat inside its disc, so a label "outside the pad" on part of a sheet points at step loss or material movement between the engraving pass and the cut, not at placement math. For leather on a loose scrap, `gcode_cut_grouping = "pad"` engraves each label right before its own cut and takes that window away. Plain hand-drawn polygons (no overlay → no inset path) get `custom_polygon_outline = None`; `on_frame_and_cut` falls back to `custom_polygon` in that case.

### Framing loop → cut handoff (fixed 2026-10-26)

**Framing loop → cut handoff (fixed 2026-10-26)**: between framing passes the dialog polls for Idle (`_wait_idle_then_restart`, then `_restart_stream` after a 150 ms settle) before streaming the next pass, and nothing is streaming during that wait. Clicking **Looks Good — Cut!** there used to wedge the run: both steps returned early on `_cut_requested`, no pass was running to fire `on_done`, and the dialog sat on "Cut requested — finishing current framing pass..." with the head stopped (Matt, v2.80, in the shop; still present in v2.86). Stop did nothing for the same reason: it soft-resets and waits for the sender's `on_done`, which never comes when nothing streams. Now a Cut (or graceful Done) seen during the wait still waits for Idle (a jog may be finishing, and the cut's first line would hit error:9) and then ends the loop with `_on_done("complete")`, the same handoff as the normal end-of-pass path; and Stop and Home go through `_stop_stream()`, which finishes the run as `stopped` itself when `sender.is_streaming()` was False. Homing never fires `on_done`, so it can't start a cut from the home position. Gated by `tools/test_framing_loop_handoff.py` (9 cases; the six that cover the bug fail on the old code).

### FalconRunDialog jog-only mode

**FalconRunDialog jog-only mode**: dialogs constructed with empty `gcode_lines` (e.g. the position-the-head step before framing) enter `_is_jog_only_mode = True` (the `_total == 0` check). Progress bar / line counter / elapsed timer are hidden (they'd just read 0 forever). State label initial value is "Position the head, then click {label}." instead of "Connecting...". X-out and explicit Cancel button → `_on_close_window` / `_on_cancel_jog_clicked` set `_final_reason = "cancelled"`; the post-stream "advance" button (e.g. Start Frame →) is rewired in `_on_done` to `_on_advance_clicked`, which destroys without clobbering `_final_reason` (left as "complete" from `_on_done`). `_on_stop_clicked`'s already-finished branch delegates to `_on_advance_clicked` rather than destroying directly, so the two paths can't drift. Three distinct close paths — Cancel, X, and Advance — must stay distinct or the caller's `if _final_reason != "complete"` check misfires. `tools/test_lid_confirm.py` covers the single lid-reminder call site, the paths that must NOT show it (advance *without* `remind_lid_on_advance`, finished-Stop, graceful framing Done, the cut, aggressive mid-cut Stop), and a full Frame & Cut run prompting exactly once on Start Frame. **The buttons follow the sender's answer (2026-11-10):** `FalconSender.jog`, `send_realtime`, `pause` and `resume` return True when the bytes were written and False when there was no port or the write failed; `_on_jog_clicked` unlocks Start Frame only on a jog that went out (a failed one used to unlock it), and Pause/Resume flip their buttons only when the byte went out (they used to flip either way, showing "paused" over a laser still cutting). A sender that answers `None` (the suites' stand-ins, an older sender) still counts as sent, so no fake sender had to change. Gated in `test_audit_fixes`; nothing streamed changed (the two recordings are identical).

### Framing power (`config.get_framing_power_s(material, settings)`)

**Framing power (`config.get_framing_power_s(material, settings)`)**: per-material Grbl S value for the framing pass, edited via Options > Machine > Framing Power. Framing is a positioning preview — bright enough to follow by eye, dim enough not to mark — and the right value is material-dependent: S10 (1%) reads fine on card but is invisible on dark leather, which is what prompted this. `laser_framing_power_by_material` holds the seven `GCODE_PRESET_MATERIALS` (adhesive rings and cork included; the rings' row in the dialog shows only while that feature is on); `laser_framing_power_s` remains the fallback for materials with no entry (`exact_size`) and for pre-existing configs. Defaults are all 10, unchanged from before the setting existed — shipping a higher default would silently alter every user's framing brightness. `FRAMING_POWER_S_MAX` (30 = 3%) is the ceiling — 3% covers the whole useful span, since even dark leather only needs a little more than card, and anything approaching engraving power marks the piece being lined up. It is enforced in `get_framing_power_s()` (clamped on **read**, not only in the dialog), so a config written under the earlier 15% ceiling can't keep framing at a marking power for a user who never reopens the dialog. The dialog shows one decimal always (`1.0`, not `1`) because the useful range is narrow and tenths are where the tuning lives — S values are integers, so 0.1% is exactly the available precision. Camera Calibration frames at basswood's value (the card material).

### Framing must always use M4, never M3

**Framing must always use M4, never M3** — non-negotiable, and it gets easier to break now that the power is user-adjustable. M4 scales the beam with feed rate so it drops to zero whenever the head decelerates or parks at a vertex, which is exactly what happens during a continuous framing loop while the user jogs or thinks. M3 would hold the full S value through every stall and scorch the material, and a higher S makes that worse. `tools/test_framing_power.py` asserts M4-and-not-M3 across the whole power range for both `generate_polygon_framing_gcode` and `generate_framing_gcode`.

### Machine menu (Pad Maker > Options > Machine)

Until that date everything except Camera Calibration greyed out until a calibration existed and the Frame & Cut button stayed hidden (commit `021d8df`, 2026-05-26, "Two-level machine gating"). ### The laser watch (2026-11-09)

**The laser watch (2026-11-09)**: Matt: "is there a way for the ssc to be ok with a user plugging in the laser when the ssc is already running? I feel like now it has to be plugged in first." ## The Tk-thread / worker deadlock (2026-11-10)

**How it was found.** CI run 42764761759 on b9a46ab (and then the run on 01071f5) hung `test_calibration_dialog` on ubuntu; the runner's new `faulthandler` dump, armed 15 s before the per-suite timeout, named it. The new worker thread, not yet running its target: `tkinter/__init__.py` `Variable.__del__` <- `threading.py` `_set_tstate_lock` <- `_bootstrap_inner`. The main thread: `threading.py` `Thread.start` waiting on the started event <- `ui_dialogs.py` `_open_camera_and_start` <- `CameraCalibrationDialog.__init__` (in `wait_window`) <- the suite's `construct`. The cyclic collector had run on the new thread during its bootstrap (the allocation in `_set_tstate_lock`), collected a dead tkinter Variable sitting in a reference cycle, and `Variable.__del__` called into Tcl. A Tcl call from any thread but the Tk thread is queued for the Tk thread and waited on; the Tk thread was inside `Thread.start()`, waiting for this very thread to report that it had started. Neither could move. Two earlier hangs in the same week (`test_tuner_engine` on Apple Silicon, an unnamed first suite on Linux, both intermittent, both green on re-run) fit the same mechanism; the sounddevice hypothesis written for them the day before was wrong for this one. It can freeze the real app at any thread start whenever a Variable sits in an uncollected cycle, which closed dialogs leave behind; more dialogs and more threads that week made it likelier.

**The fix: `threads.py`.** `start_worker(target, name, args, kwargs, daemon=True)` creates the thread and runs `Thread.start()` with the collector held off (`gc.disable()` across the call, counted so nested and concurrent holds compose and a collector that was already off stays off): `start()` returns only after the new thread has set its started event, after the bootstrap's allocations, so no collection can run on the new thread while the Tk thread waits. All twelve `threading.Thread(` sites went through it with nothing else about them changed: main.py 3 (the laser watch's two starts, the blocking home), ui_dialogs.py 7 (polygon-draw overlay open, calibration MPos poll, calibration home, calibration camera open, capture-dialog camera open, run-dialog home, live-camera open), falcon_sender.py 1 (the stream worker), toner_engine.py 1 (the mic-check query). A module of its own, not a function in config.py, because falcon_sender and toner_engine import it and neither imports config (the sender is Tk- and settings-free on purpose); it has no project imports.

**Every other place the Tk thread blocks on a worker, reviewed.** `CameraCalibrationDialog._port_lock`: the `@_holds_port` buttons acquire it blocking on the Tk thread while the MPos poll worker holds it for `connect()` + `get_status()` (0.3 to 0.5 s of pyserial allocation): exposed, now `threads.GcHeldRLock`, whose holder has the collector off (the worker posts its result with `after()` only after releasing, checked). `FalconSender._lock`: the stream worker takes it for every write and read, the Tk thread in `send_realtime`, `jog`, `disconnect`, `is_connected`: exposed, now `GcHeldRLock` (one line; the holds are microseconds). `FalconSender.stop()`'s `join(timeout=2.0)` and `start_stream()`'s `join(timeout=0.5)` on the Tk thread: exposed, now inside `gc_held()` (two lines each; nothing streamed changed, both recordings identical). `toner_engine.check_mic_quality()`'s 5 s join on the Tk thread: exposed, now `gc_held()` round start and join. Not exposed: the three home workers (the Tk thread polls `is_alive()` with `after()` under `wait_variable`, so the event loop runs and a worker's Tcl call is served); workers posting with `after()` (the worker waits on the Tk thread, not the reverse; a `time.sleep(1.0)` on the Tk thread in Reset Falcon delays it, no more); `sleep_lock`'s subprocess wait; `wait_window` and `grab_set`.

**The garbage, measured** (collector off, dialogs opened and closed in a loop, `tk.Variable` objects counted, then one collection): Sizing Rules (`OptionsWindow`, 58 Variables) leaves 10 per open, the calibration dialog (5 Variables) leaves 2 per close (`_status_var`, `_instructions_var`); a collection frees none of either, so they are not in cycles but still referenced: the destroyed dialog object stays alive through the callbacks it registered with the interpreter (bound methods behind `command=`, which the collector cannot see). A leak of one dialog object per open, not collector fuel, and no cheap cut (no `trace_add` to remove on destroy). The Variable the CI collection finalised came from elsewhere in that suite's run; the helper covers it wherever it comes from.

**Reproducing it.** `tools/test_threads.py` builds, in child processes, Variables in cycles aged into the oldest generation and dropped, arms the collector with `gc.set_threshold(k, 1, 1)` for k = 1..12, starts a thread the old way, and bounds each child with 8 s; where a k hangs, the same k through `start_worker` must return. On Python 3.14 (Windows, the development machine) no k hangs: 3.14's collector is incremental and its `Thread.start` allocates differently from 3.11's, where CI saw the collection land in `_set_tstate_lock`; the check says so and passes on the scan and the unit checks (an AST scan: no `threading.Thread(` in a root module outside threads.py, no suite that owns a Tk root starting a raw thread; `start_worker` holds the collector off across `start()` and gives it back; holds nest and count across threads; a collector that was off stays off; `GcHeldRLock` is off while held, re-entrant, and a failed non-blocking acquire changes nothing). On the committed tree 01071f5 the suite is 1/7, naming the twelve sites. Only 3.14 was installed on the development machine; CI's 3.11 is where the reproduction can bite.
