# Nesting and Scrap Mode: decisions and history

This file holds the why and the history behind the rules in the CLAUDE files, and the full detail they summarise: what was tried, measured, rejected and decided, with dates and the user's own words. The paragraphs were moved here verbatim from the CLAUDE files on 2026-11-10 (HEAD 01071f5); each section names where it came from. Add new decisions to the matching section, dated.

## Nesting

*Moved from CLAUDE-engines.md, section "Engines: Pad Generation, G-code, Tuner, Tooling > Nesting" (2026-11-10).*

### Vectorized scan paths (v2.40+)

**Vectorized scan paths (v2.40+)**: the radial-bias rectangle scan (`_scan_radial_numpy`) and both polygon scans (`_find_best_polygon_large_numpy`, `_find_best_polygon_small_numpy`) build a numpy candidate grid, compute distances/scores in one bulk op, mask occupied cells via per-pad bounding-box updates, then `argmin` to pick the closest valid cell. ~100× faster than the Python loop on real-world inputs; bit-identical placements (`argmin`'s first-index-of-min matches the Python reference's strict-less-than y-then-x tie-break). A Python reference (`_scan_radial_python`, `_find_best_polygon_*_python`) is preserved verbatim as the parity target and as the runtime fallback when numpy is unavailable (a source checkout without numpy — every shipped build has had numpy since 2026-10-06; try-import at the top of `svg_engine.py` sets `_HAS_NUMPY`). `tools/test_nesting_parity.py` (rectangle) and `tools/test_polygon_parity.py` (polygon) assert exact-match placements across all 9 edge biases, every polygon shape, and max-quantity fills.

### The linear scan is vectorized too (2026-09-20)

**The linear scan is vectorized too (2026-09-20).** The cardinal biases (N/S/E/W) and "off" — the state the center button toggles to, so effectively *no bias* — use a row-by-row first-free-cell scan, not the radial one, and it was the last scan still running the pure-Python loop: O(cells × placed) per disc. Matt hit it with 120 felt pads on a sheet typed as 15.5 × 15.5 in: 94 s per nest on his ThinkPad, and the generate flow nested twice, so Windows logged `Application Hang` and he force-closed the app three times. `app.log` showed nothing because nothing raised — when a "crash" leaves no traceback, check `Get-WinEvent -LogName Application` for `Application Hang` / `AppHangB1` events before assuming the exception hook missed it. `_scan_linear_numpy` builds the occupancy mask with the shared `_build_occupancy_grid`, flips the axes into the reference's visit order (reversed scans are anchored at the far edge, so their grid only lines up with the forward grid when the free span is a whole number of mm — `_linear_axis_cells` reproduces the exact cells the loop visits), and takes the first free cell with `argmax`. `_scan_linear_python` is the verbatim closure, kept as the parity reference and numpy-less fallback. Same nest now takes 0.1 s. Guards live in `test_nesting_parity`: direct parity across all five linear biases (including obstacles on the first/last cell, a blocked row, and a fully covered sheet), end-to-end parity including the fail-to-place case, and a `< 5 s` regression bound on Matt's exact batch.

### Nesting Preview

**Nesting Preview**: `NestingPreviewWindow` in ui_dialogs.py shows the nested layout before file generation. Works in standard mode (one material at a time) and scrap mode. The generate flow nests first via `nest_with_zones()`, shows the preview, then writes files via `generate_svg_from_placed()` / `generate_gcode_from_placed()` — no double-nesting. The fit check is the `fixed_placed == fixed_total` pair that same call returns; the three flows (SVG, G-code, Frame & Cut) used to call `can_all_pads_fit()` afterwards, which is a second full nest, and that doubled every nesting time until 2026-09-20. `can_all_pads_fit()` still exists for tests and one-shot callers — don't reintroduce it next to a `nest_with_zones()` call. Frame & Cut (machine integration, v2.62) reuses the same window before the head moves — it passes `proceed_label="Continue →"` (it streams to the laser rather than writing files, so "Save Files" would mislead) and a cancel there consumes nothing.

## Polygon Shape Tool

*Moved from CLAUDE-engines.md, section "Engines: Pad Generation, G-code, Tuner, Tooling > Polygon Shape Tool" (2026-11-10).*

Users can draw custom polygon shapes for irregular leather skins. Grid size: default 17×17 inches (1" squares) or 43×43 cm (1cm squares); auto-grows in `PolygonDrawWindow.__init__` to at least `ceil(max(laser_bed_x_max, laser_bed_y_max) / mm_per_unit)` so a user with a 500mm bed gets a 20-inch grid even if their stored `polygon_draw_grid_size_in` setting is smaller. The polygon nesting algorithm (`_nest_discs_polygon()`) uses ray-casting for point-in-polygon checks and distance-to-edge calculations for circle fitting. The rectangle algorithm remains the fast path when no custom shape is defined.

**Vertex placement**: free-floating (`_canvas_to_grid` returns floats), not snapped to integer grid intersections — 1-inch granularity is too coarse for accurate scrap tracing. Hand-drawn AND camera-captured polygons share this float convention; downstream nesting + machine-coord round-trip handle non-integer points natively.

### Live camera overlay

**Live camera overlay** (v2.5+): `PolygonDrawWindow._render_overlay` warps the live camera feed (via `cv2.warpPerspective`) onto the polygon canvas at 1:1 grid scale, anchored at machine `(0, 0)` by default (canvas BL = bed origin). Users can trace their scrap by eye on top of the camera image, or click "Get from camera" for auto-detection via `CameraCaptureDialog`.

## Scrap Mode

*Moved from CLAUDE-engines.md, section "Engines: Pad Generation, G-code, Tuner, Tooling > Scrap Mode" (2026-11-10).*

### Live pad list (2026-09-20)

**Live pad list (2026-09-20)**: the pad list box stays editable during a session and is re-read on every Generate / Frame & Cut. `_scrap_pads_for_this_scrap(pads)` merges duplicate lines, stores the merged list as `original_pads`, and returns `remaining_pads` = the list *now* minus the session's `done` tally per size, so a size added, raised, lowered or removed mid-session simply takes effect on the next scrap, and lowering below what's already cut clamps to zero. `_scrap_record_result(remaining)` credits a finished scrap to `done` as the drop from the pre-scrap list; all three commit sites (SVG, G-code, `_frame_cut_scrap_advance`) route through it, so it must run before anything overwrites `remaining_pads`. The Done column of the remaining-pads window reads `done` directly rather than original minus remaining, so it stays honest when a quantity is lowered below the cut count. Before this, the session copied the list at its start and ignored the box until the session ended; a user who added sizes to fill a half-empty last scrap got a scrap without them and no message. Deliberately *not* changed: a `max` line still fills the first scrap only (pre-existing, pinned by the test), and the session's `hole_dia` is still fixed at session start. Tests: `tools/test_scrap_live_list.py`.

### Pending scrap (2026-10-26)

**Pending scrap (2026-10-26)**: until this date the window knew only Remaining and Done, and both moved at one point, the commit after a completed cut or a written file. From the preview opening until the laser stopped it still read "0 / 60 pads complete" with every pad in Remaining, which reads as pads being dropped: Matt hit it in the shop on a leather scrap whose nest placed the five 52s and the small sizes and skipped 5x50, 10x39 and 10x36 (correctly: after the 65 mm discs took the wide parts, the arms were too narrow for a 49-63 mm disc once the 5 mm camera inset and 1 mm spacing came off). The session now keeps `pending` = `{size: count}` of what the current scrap's nest placed, set by `_scrap_set_pending(placed)` at the end of `_scrap_begin_partial`. The window subtracts it from Remaining, lists it in the middle column and heads itself "{n} on scrap #{k}, {done} / {total} cut"; the main-pane status says "{left} left, {n} on this scrap". `_scrap_record_result` (the one commit point) clears it as it credits `done`. `_scrap_abandon_pending` puts it back and is called from a `finally` in `_generate_gcode_scrap_mode`, `_generate_svg_scrap_mode` and `on_frame_and_cut`, so every way out that is not a commit (preview Adjust, folder prompt cancelled, jog or framing dialog cancelled, stopped or errored cut, exception) restores Remaining without each path having to remember to. Tests: `tools/test_scrap_pending.py` (bookkeeping with the real window, and the Generate button with the preview stubbed to Adjust then Save).

### No large-batch optimizer (removed 2026-09-20)

**No large-batch optimizer (removed 2026-09-20).** v2.5 shipped an opt-in "large-batch optimization" for scrap mode: with ≥ 75 pads remaining, a prompt offered a multistart nest (largest-first, smallest-first, three seeded shuffles) and kept the best. It first kept the result with the most *pads*, which systematically picked smallest-first and left the big discs for later — Matt measured 63% of a leather scrap used against 70% from the plain nest. Re-ranked by material used, largest-first was the winner on every real scrap tried, and 22 orderings moved usage by 0 / 0.3 / 1.3% on Matt's actual 120-pad list. The reason is geometric: the interstice between three touching ~60 mm leather discs is under 10 mm, and the smallest pad on that list is a 29 mm disc, so no ordering can use those gaps. Put a dozen 10.0 mm pads (18 mm leather discs) in the same list and plain largest-first drops all twelve into the gaps (70.5% → 73.6% / 76.0%), still with no reordering. So the lever is the sizes in the list, not the order, and the feature was removed rather than kept as a code path with a prompt that couldn't earn its keep. The ordering-override parameter on both nesters went with it. Don't reintroduce an ordering search without a measured win on a real list.
